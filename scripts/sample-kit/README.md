# サンプルシナリオの道具と共通の決まり

サンプルシナリオを扱う2つのスキルが、最初に読む共通の資料。

| スキル | 作業 |
|---|---|
| `.claude/skills/sample-scenario-write/` | 新しいサンプルを書く |
| `.claude/skills/sample-scenario-maintain/` | 既存のサンプルを新しい機能に追従させる・点検する |

このフォルダの中身:

| ファイル | 内容 |
|---|---|
| `README.md` | このファイル。置き場所・準備・道具の使い方・合格条件・してはいけないこと |
| `source-format.md` | 原本（body.md / data.json / thumb.js）の書き方 |
| `features.md` | 機能ごとの見せ方（どの場面で、何のために使うか）。`kit.js` の `FEATURES` と対応する |
| `systems.md` | エモクロアと CoC6 の書き分け |
| `kit.js` | ブラウザ側の道具（検査・組み立て・画像・網羅・読み込み直し） |
| `run.js` | Playwright 側の入口。`driver.js` を読み込んで実行するだけ（全文が毎回出力に出ないように小さくしてある） |
| `driver.js` | Playwright 側の本体（工程の実行・書き出し・PDF・スクリーンショット） |

## 1. サンプルとは何か

サンプルには役目が2つある。両方を満たさないものはサンプルとして出さない。

1. **機能の見本。** 利用者が読み込んで「この記法は、こういう場面でこう使う」を知るためのもの。機能を並べただけの試験データでは、使いどころが伝わらない。
2. **そのまま遊べるシナリオ。** GMが今夜これを回せる完成度にする。見本として読まれる以上、筋が破綻していると、記法の使い方まで信用されなくなる。

2つがぶつかったら**物語を優先する**。不自然な場所に機能を押し込まず、自然に使える場面を作るか、使わなかった理由を報告に書く。

## 2. 置き場所

```
samples/                      ← .gitignore 済み。この端末だけに置き、リポジトリには入れない
├── <slug>.json               ← 完成品（アプリの「読み込み」で開くファイル）
└── <slug>/
    ├── body.md               ← 本文の原本
    ├── data.json             ← NPC・情報・場面カード・基本情報・巻末・画像の指定・meta の原本
    ├── thumb.js              ← サムネイルの絵（任意）
    ├── outline.md            ← 承認を得た骨子（2026-10-05 に作った初版の2本には無い。骨子を作る前の作り方だったため）
    ├── try.md                ← 案の試し描きに使う一時ファイル（try の工程用。試し終えたら消す）
    └── <slug>.pdf / shots/   ← 検証の副産物
```

- slug は `sample-<システムid>-<ローマ字の短い名前>`（例: `sample-emoklore-amayadori`）。data.json の `id` と同じにする。
- **原本は body.md と data.json。完成品のJSONは毎回ここから作り直す。** JSON を手で直すと、次に作り直したときに消える。
  画像は種（`meta.seed`）を固定して描くので、作り直してもほぼ同じ絵になる（描くたびに、目で区別できない程度の揺れが出ることがある。`diff` はその程度を同じとみなす）。

## 3. 準備（作業の最初に）

1. **記法と項目を、記憶ではなく文書で確かめる。** 記法は版ごとに増える。点検だけのときは省いてよい（記法の誤りは道具が検査する）。
   - 記法の一覧（正）: `docs/01_要件定義書.html` §4
   - 記法の意図と落とし穴: `docs/04_記法設計書.html`
   - 基本情報: `docs/08_シナリオ基本情報設計書.html`／巻末: `docs/09_巻末設計書.html`／場面カード: `docs/06_場面ツリー設計書.html`
2. **ローカルサーバーを確かめる。** `curl -s -o /dev/null -w "%{http_code}" http://localhost:8000/index.html` が 200 でなければ、
   リポジトリ直下で `python -m http.server 8000` をバックグラウンド実行する（`run_in_background`）。file:// では道具が動かない。
3. **Bash の作業場所をリポジトリ直下から動かさない。** `cd` でサブフォルダへ移ると、フックが相対パスで見つからず、Bash・Write・Edit がすべて止まる。
   パスは絶対パスか、リポジトリ直下からの相対パスで書く。
4. Windows の Python で日本語を出力すると文字化けする。`python -X utf8` を付けるか、結果を UTF-8 のファイルに書いて Read で読む。

## 4. 道具の使い方

組み立てと検証は、この道具で行う。手でコードを書かない（初版のサンプルではその場で書き、何も残らなかった）。

1. `browser_navigate` で次を開く:
   `http://localhost:8000/index.html?kit=<slug>&steps=<工程をカンマ区切り>`
2. `browser_run_code_unsafe` を `filename: scripts/sample-kit/run.js` で実行する。結果がJSONで返る。

工程は、書いた順ではなく常に下の表の順で実行する。途中の工程が失敗するとそこで止まり、結果の `failed` に工程名が入る。

| 工程 | すること |
|---|---|
| `lint` | 原本の静的な検査。参照切れ・段落の切り方・判定の結果行・場面カードと見出しの対応・接続の輪など。**エラーがあると build 以降は動かない** |
| `build` | 立ち絵とサムネイルを描き、アプリに取り込んで開く。`appVersion` にアプリの版が返る |
| `verify` | プレビューを調べる。`problems`（参照切れ・変換されずに残った記法・右の段だけの行など）、`coverage`（使っていない機能）、`variety`（使っていない成功段階・色・記号など）、`drift`（原本を作った版より新しいリリース・どの機能にも対応しない操作・記法の一覧の表との突き合わせ） |
| `diff` | 今ある完成品（`samples/<slug>.json`）と、いま原本から作ったものを比べる。id・日時・座標は比べない。画像は目で区別できない揺れを同じとみなす。**export で上書きする前に**回す |
| `export` | アプリの書き出しで `samples/<slug>.json` を上書きする |
| `roundtrip` | 書き出したJSONだけで読み込み直し、プレビューが完全に一致するか、立ち絵とサムネイルが戻るかを見る（export の後に） |
| `pdf` | `samples/<slug>/<slug>.pdf` を作り、ページ数と目次のリンク数を数える |
| `shots` | `samples/<slug>/shots/` に要所のスクリーンショットを撮る（表紙・目次・場面図・セリフ・NPCカード・判定・共鳴/SAN・情報・TIPS・FAQ・巻末・場面ツリー） |
| `section` | `&shot=<見出しの題名>`（繰り返し可）の場面だけを `shots/section-<題名>.png` に撮る。直した場面を確かめるときに使う |
| `try` | `samples/<slug>/try.md` に書いた断片を、そのサンプルのNPC・情報のまま描き、行の組み方（`layout`）と問題（`problems`）を返し、`shots/try.png` に撮る。**原本を変えずに案の見え方を確かめる**ときに使う。描いたあとプレビューは元に戻る。build 済みであること |
| `system` | `&system=<id>` のシステム定義（技能名・成功段階・感情・SANの既定など）を返す。kit は不要 |
| `force` | lint のエラーを無視して続ける（原因を見たいときだけ） |

- 書いている途中は `lint,build,verify`、仕上げは `lint,build,verify,diff,export,roundtrip,pdf,shots`。
- `verify` に `&detail=1` を付けると、網羅の全行（使った数つき）が返る。
- 書き出しのたびに `.playwright-mcp/` にも同じJSONが自動で保存される。gitignore 済みで害は無い。
- 道具が動かない・判定がおかしいときは、道具を直してよい（`kit.js` はアプリの関数を直接呼ぶので、アプリの変更で壊れうる）。直したら報告に書く。
- 道具の結果は長いので、読むべき所を決めて読む: `lint.errors` → `verify.problems` → `verify.coverage.unused` → `verify.drift` → `diff.same` → `roundtrip.samePreview`。
- `verify.drift` の見方:
  - `newerReleases`: `meta.builtWith` より新しいリリースノート
  - `unknownActions`: アプリの操作（`ACTIONS`）のうち、`kit.js` の `FEATURES` のどれにも対応しないもの
  - `docRows.unmapped`: 記法の一覧（`docs/01_要件定義書.html` §4.1 の表）の行のうち、`kit.js` の `DOC_ROWS` に無いもの。ボタンの無い書き方は `unknownActions` に出ないので、ここで見つける
  - `docRows.changedAfter`: 原本を作った版の日付より後に、日付の注記が付いた行。規則が変わったかもしれない確認候補
  - `docRows.sameDay`: 同じ日付の行。同じ日に何版も出すことがあるので、その版にすでにあったかもしれない。`newerReleases` の項目に関係する行だけ確かめればよい
- `variety` の未使用（成功段階・色・記号・場面の種別など）は**参考情報**で、合格条件ではない。自然に使える場所があるときだけ使う。
- PDF は中身を目で見られない（Read で PDF を開くための pdftoppm が無い）。ページ数と、リンク数が目次の項目数（`verify.counts.tocItems`）と同じことで確かめる。

## 5. 合格条件

新規・追従は仕上げのときに、点検は結果として、すべてを確かめる。満たせないものは理由を報告に書く。

- [ ] `lint.errors` が0件。`lint.warnings` は1件ずつ読み、直すか、残す理由を報告に書く
- [ ] `verify.problems` が0件
- [ ] `verify.coverage.unused` が空。空でなければ、使わなかった理由を報告に書く（`notApplicable` はシステムに無い機能なので対象外）
- [ ] `roundtrip.samePreview` と `contentMatchesBody` が true、`avatarsRestored` が全員、`thumbnailRestored` が true
- [ ] `console` が空（エラー・警告なし）
- [ ] `shots` を Read で目で見た。最低でも表紙・場面図・セリフ・場面ツリー（崩れ・見切れ・文字化けが無いか）
- [ ] 新規・追従のときは、data.json の `meta.builtWith` を `build.appVersion` に更新した（点検だけのときは更新しない。新しい機能を見ていないため）

## 6. してはいけないこと

- **ルールブックやサプリメントの文章・データを書き写さない。** 怪物や神格のデータ、呪文、公式のNPC・シナリオ、表の中身が対象。
  `knowledge/` を gitignore しているのもこのためで、サンプルは人に渡すこともある。技能名・用語・判定の仕組みを使うのは問題ない。怪異や神話存在は自作する。
- **権利表記は仮の文で置く。** 公式ガイドラインの文面は自分で作らない。「公式ガイドラインの権利表記に差し替える」と報告に書く。
- **samples/ をコミットしない。** gitignore 済み。公開したいと言われたら、公開範囲（CLAUDE.md「公開範囲」）をユーザーと確認する。
- **サンプルの作業の中でアプリ本体（index.html）を直さない。** 不具合を見つけたら報告する。サンプルの作業とアプリの修正は、確かめ方もコミットも別にするため。
- **完成品のJSONを手で直さない。** 原本を直して作り直す。
