# リリースノート生成

対象バージョン: `$ARGUMENTS`

## 前提

- **コードの差分は絶対に見ない。** コミット件名の一覧だけを情報源とする。
  差分が膨大になり、要約の質も上がらないため、`git diff` やファイル内容の読み込みは行わない。
- 読者は**このプロダクトの利用者**であり、開発者ではない。

## 手順

1. **引数チェック**
   `$ARGUMENTS` が空、または `v` から始まるバージョン表記（例: `v0.14.0`）でない場合は、
   バージョン番号を引数で指定するよう促して終了する（例: `/release-notes v0.14.0`）。

2. **コミット件名の取得**
   リリース元・先ブランチを確認する（既定は `main..develop`。`git branch -a` で実在を確認し、
   無ければユーザーに尋ねる）。

   ```
   git log --no-merges --pretty=format:"%s" main..develop
   ```

   ここで得られる件名一覧だけを根拠にする。

3. **分類・除外**
   Conventional Commits の prefix（`feat` / `fix` / `perf` / `refactor` / `test` / `chore` /
   `docs` / `style` / `ci` / `build`。scope付きも含む）を手がかりに分類する。

   - **含める候補**: `feat`（新機能）、`fix`（不具合修正）、`perf`（性能改善）など、
     利用者が体感しうる変更。
   - **除外する**: `refactor` / `test` / `chore` / `docs` / `style` / `ci` / `build` など、
     内部整備。
   - prefixだけで機械的に判断しない。内部的な最適化や型安全化など利用者から挙動が
     見えないものは `fix`/`perf` でも除外してよい。逆に `refactor` 名義でも実質的に
     UIや挙動が変わっているものは含めてよい。
   - **判断に迷うものは除外する側に倒す。** 実際には変わっていない項目を載せる方が、
     載せ漏らすより害が大きい。

4. **文章化**
   「新機能」「不具合修正」「改善」などの見出しでグルーピングする。
   開発者向けの件名をそのまま転記せず、利用者向けの平易な日本語に言い換える
   （内部の関数名・テーブル名・技術用語は書かない）。該当が1件も無い見出しは省略する。

5. **出力**
   `release-notes/<バージョン>/<バージョン>.md` に書き出す（ディレクトリが無ければ作成）。
   冒頭に `# <バージョン> (YYYY-MM-DD)` の見出しを入れる。

6. 書き出し後、生成した内容をそのままチャットにも表示する。
