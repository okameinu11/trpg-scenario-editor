# 新しいサンプルシナリオを書く

**最初に `scripts/sample-kit/README.md` を読む。** サンプルの役目・置き場所・準備・道具の使い方・合格条件・してはいけないことは、すべてそこにある（追従・点検のスキルと共通なので、ここには書かない）。

このスキルが受け持つのは、その上での**書く手順**である。いちばん高くつく失敗は「1万字書いたあとで、題材や構成がずれていたと分かる」ことなので、骨子の承認を挟み、書きながら検証を回す。

## 読むもの

| いつ | 何を |
|---|---|
| 最初に | `scripts/sample-kit/README.md` |
| 骨子を書く前に | [references/writing-guide.md](references/writing-guide.md)（遊べる完成度にするための指針）、`scripts/sample-kit/features.md`（機能ごとの見せ方）、`scripts/sample-kit/systems.md`（システムの書き分け）、`docs/01_要件定義書.html` §4（記法の一覧） |
| 原本を書く前に | `scripts/sample-kit/source-format.md`（body.md / data.json / thumb.js の書き方）。基本情報・巻末・場面カードを書くときは `docs/08`・`docs/09`・`docs/06` の該当箇所 |

## 1. 条件を聞く

AskUserQuestion で聞く。「おまかせ」と答えられても進められるように、選択肢には具体案を入れる。

- **システム**: `GAME_SYSTEMS` にあるもの（今はエモクロア・CoC6）
- **題材**: 筋が決まっていなければ、一行の売り文句つきで3案を出す。舞台だけ指定されたとき（「雪の山荘で」など）は、その舞台の中で3案を出す。
  案を出す前に、既存サンプルの `samples/*/data.json` の `meta.premise`（舞台・怪異・結末の型の要約）を見て、重ならないようにする。premise が無いサンプルだけ、outline.md か本文を読む
- **長さ**: 中編（本文6,000字前後・`#` 見出し8〜9）／長編（11,000字前後・`#` 見出し11〜13）。見出しの数はGM向けの章とエンディングを含む。字数は空白を除いて数える
- **人数とHO**: エモクロアならHOの有無と数、CoCなら人数の幅

指定済みの条件は聞き直さない。

## 2. 骨子を書いて承認を得る

1. `system` 工程（`http://localhost:8000/index.html?steps=system&system=<id>`）で、技能名・成功段階・感情・SANの既定・場面の種別・レベルの記号・文字色を確かめる（index.html を探しに行かなくてよい）。
2. [assets/outline-template.md](assets/outline-template.md) に沿って `samples/<slug>/outline.md` を書く。特に次の2つの表は省かない。
   - **手がかりの鎖**: 結論ごとに手がかりが3つ以上・2か所以上あるか。ここで鎖が切れていると、本文をいくら直しても詰まる
   - **機能の対応表**: どの機能を、どの場面で、何のために使うか。無理な配置はここで見つけて直す
3. **チャットに骨子の全文を出し、承認を得てから本文に進む。** 直しを求められたら直して出し直す。

## 3. data.json を先に、本文を後に書く

本文は NPC の名前・情報の題名・場面カードの題名を**完全一致**で参照する。先に data.json で名前を決めておくと、参照のずれが起きない。

1. `samples/<slug>/data.json` を書く（meta・NPC・情報・場面カード・基本情報・巻末・画像の指定）。
   `meta.seed` は日付などの数字で決めて固定する。`meta.targetLength` に目標字数、`meta.premise` に舞台・怪異・結末の型の要約を入れる（次に新しいサンプルを書くとき、重なりを確かめるのに使う）。
   slug は既存のものと紛らわしくない名前にする（例: 「霧笛 muteki」があるので「霧氷」は `muhyou` ではなく別の語にする）。
2. `samples/<slug>/body.md` を、骨子の場面の順に書く。長いので章ごとに分けてよい（最初に Write、続きは Edit で末尾に足す）。
3. **1〜2章書くごとに `lint` を回す。** 誤りが溜まってから直すと、どこで崩れたか追いにくい。
4. サムネイルを凝りたいときは `thumb.js` を書く。無ければ data.json の `thumbnail`（色と模様）で描かれる。

## 4. 検証を回す

1. `lint,build,verify` を、`lint.errors` と `verify.problems` が0件になるまで回す。
2. `verify.coverage.unused` に残った機能は、骨子の対応表に戻って自然に入る場面を探す。無ければ使わない理由を控える。
3. `verify.variety` の未使用（成功段階・色・記号など）は、全部を埋める必要は無い。エモクロアの奇跡的成功・災厄級成功のように、判定の設計上めったに書かないものもある。
4. 字数が目標に届かないときは、水増しせず、手がかり・NPCのセリフ・失敗時の扱いなどGMの役に立つものを足す。
5. [references/writing-guide.md](references/writing-guide.md) §10 の見直し表で、自分でも一度読み直す。

## 5. GMの目で読ませる

書いた本人は、自分の書いた筋の穴に気づきにくい。何を書いたつもりかを知っているので、書いていないことまで補って読めてしまう。

Agent ツールで `subagent_type: scenario-gm-reviewer` を呼び、次を渡す:
題名・システム・人数・想定時間・`samples/<slug>/body.md` と `data.json` のパス。**outline.md は渡さない**（読むと本文に無い意図を補ってしまう）。

指摘を受け取ったら:

- 「進行が止まる」「判断に困る」は必ず直す
- 「気になる」は採るかどうかを決め、採らなかったものは理由を報告に書く
- 直したら `lint,build,verify` を回し直す
- 大きく直したとき（場面を足した・結末を変えた）は、もう一度読ませる

## 6. 仕上げて報告する

1. `lint,build,verify,diff,export,roundtrip,pdf,shots` を回し、README §5 の合格条件をすべて確かめる。
2. data.json の `meta.builtWith` を `build.appVersion` に更新する。
3. 骨子と本文がずれていたら、outline.md を本文に合わせて直す（追従・点検で読み返すため）。
4. 日本語で報告する:
   - **作ったもの**: 題名・システム・人数・想定時間・あらすじ（2〜3文）・完成品のパス（`samples/<slug>.json`）
   - **規模**: 字数・場面数・NPC数・情報数・判定数・PDFのページ数
   - **使った機能**: coverage と variety の要点。使わなかったものはその理由
   - **検証の結果**: 合格条件の各項目
   - **GMの目で読んだ結果**: 直したもの・直さなかったものと理由
   - **確かめてほしいこと**: 権利表記の差し替え、仮の内容、迷った判断
   - **アプリについて気づいたこと**: 書いている途中に見つけた不具合や使いにくさ（直さずに報告だけ）
