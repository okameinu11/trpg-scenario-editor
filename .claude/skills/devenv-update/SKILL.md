# devenv の更新を取り込む

## 何をするスキルか

届いた更新パックを読み、**このプロジェクトの事情に合わせて**取り込む。

パックには「何がどう変わったか」だけでなく「なぜ変えたか」「導入先で何をすべきか」が
書いてある。それを読んだうえで、**このプロジェクトにとって取り込むべきかを判断する**のが
このスキルの仕事である。全部を機械的にコピーすることではない。

```
[大元の基盤]  更新パックを生成
                 ↓  ユーザーが手で運ぶ
[このリポジトリ]  ← いまここ
                 ↓  摩擦があれば
              /devenv-feedback で記録し、また基盤へ持ち帰る
```

## 前提

パックは `devenv-update-<版>/` というフォルダで、リポジトリ直下に置かれている。

| | |
|---|---|
| `UPDATE.md` | 変更のレポート。**最初にこれを通読する** |
| `MANIFEST.json` | 変更ファイルの一覧と、**変更前の内容のハッシュ** |
| `files/` | 追加・変更されたファイルの実体 |
| `VERSION` | 新しい版 |

## 手順

### 1. 版を突き合わせる

```bash
perl scripts/devenv/setup.pl --version    # このリポジトリの版
```

`UPDATE.md` の「<前の版> → <新しい版>」と照らす。

- **前の版が一致** — そのまま進める
- **こちらの方が古い** — 間の版の変更が抜ける。基盤側で `--from <こちらの版>` を指定した
  パックを作り直してもらう。**推測で進めない**
- **こちらの方が新しい** — 適用済み。ユーザーに伝えて終了する

### 2. `UPDATE.md` を通読する

**破壊的変更を先に把握する。** これを見落とすと、ファイルを置き換えた後で
「動いているように見えて実は追従できていない」状態になる。

### 3. ハッシュ照合で「置換してよいもの」を確定する

`MANIFEST.json` の各エントリについて、このリポジトリの現物と突き合わせる。

```bash
git hash-object <ファイルパス>
```

| 結果 | 意味 | 扱い |
|---|---|---|
| `before` と一致 | 導入以降このファイルを触っていない | **そのまま置換してよい** |
| 一致しない | このプロジェクトが手を入れている | **`統合` に格下げする** |
| ファイルが無い | 雛形と実体で名前が違うか、新規追加 | 下の対応表を見る |

**一致しないことは異常ではない。** そのプロジェクトが手を入れた証拠である。
`UPDATE.md` の区分が `置換` でも、**照合結果が優先される**。
手入れを消さずに、新しい変更だけを取り込むこと。

> 改行コードの違いで一致しないことがある（`git hash-object` は改行変換を通すので
> 通常は問題ないが、`.gitattributes` の設定次第では起きうる）。
> その場合は差分を見て、実質的な変更が無ければ `置換` として扱ってよい。

### 4. 置換する

無改変と確定したものを `files/` から上書きコピーする。
`UPDATE.md` に削除ファイルが挙がっていれば、それも消す。

新しい**雛形**（`*.example.json` など）が増えていた場合は、置いたあとに
`perl scripts/devenv/setup.pl` を実行すると実体化される（既存ファイルは触られない）。

> **フックの `.pl` と `.js` は必ず対で扱う。**
> 片方だけを改変していると、照合結果は「`.js` は置換・`.pl` は統合」に割れる。
> そのまま進めると**同じ役割の2実装が別物になる**（判定が食い違っても誰も気づかない）。
> 片方でも `統合` になったら、**もう片方も `統合` として扱い、2つが同じ挙動になるまで揃える**。
> 揃えたら、同じ入力を両方に流して出力が一致することを確かめること。

### 5. 統合する

1ファイルずつ、**このプロジェクトの内容を残したまま**新しい変更を取り込む。

| ファイル | 判断のしかた |
|---|---|
| `devenv.config.json` | 新しい設定キーの多くは**書かなくても既定値で動く**。挙動を変えたいものだけ足す。パックの `devenv.config.example.json` は書き方の参照であって、コピー元ではない |
| `CLAUDE.md` | ゲート一覧は手で直さず `perl scripts/devenv/check-doc-sync.pl --summary` の出力を貼り直す。プロジェクト固有の節には手を触れない |
| `.claude/settings.json` | Perl版とNode版のどちらを使っているかはこのリポジトリの事情。フックの構成が変わった場合だけ反映する |
| `.gitignore` / `.gitattributes` | 追記部分のマーカー（`--- devenv (claude_basement) ---`）以降だけを見る |

### 6. 任意の機能はユーザーに諮る

新機能を**勝手に有効化しない**。「この機能はこういう問題を解く。このプロジェクトでは
こう使えそうだが、入れるか」と聞く。要らない機能を設定に足すと、
**存在しないパスを見張る死んだルール**が増えるだけになる。

### 7. 破壊的変更に追従する

`UPDATE.md` の「導入先でやること」を実施する。
このリポジトリのドキュメントや手順書に古い記述が残っていないかも確認する。

### 8. 版を更新する

パックの `VERSION` を `scripts/devenv/VERSION` へコピーする。
**取り込みが終わってから**にすること。途中で更新すると、次回どこまで進んだか分からなくなる。

### 9. 動作確認する

**省略しない。** 置き換えたのはコミットゲートとフックそのものである。

```bash
perl scripts/devenv/check-doc-sync.pl          # エラー無く終わるか
perl scripts/devenv/check-doc-sync.pl --summary # ルール一覧が出るか
```

そのうえで、**意図的にルールへ引っかけて block が実際にコミットを止めることを1つ確かめる**。
フックは Claude Code を再起動しないと反映されないことがある。

### 10. 適用記録を残す

`scripts/devenv/UPDATES.md` に追記する（無ければ作る）。

```markdown
## <版>（<日付> 適用）

前の版: <前の版>

### 取り込んだ
- <項目>

### 取り込まなかった
- **<項目>** — <理由>

### このプロジェクト向けに変えて取り込んだ
- **<ファイル>** — <何を残し、何を取り込んだか>
```

**「取り込まなかった」を必ず書く。** 理由が残らないと、次の更新のたびに同じ判断を
やり直すことになる。「このプロジェクトには要らない」も立派な判断であり、記録に値する。

### 11. パックを片付ける

`devenv-update-<版>/` を削除する。役目を終えた配布物をリポジトリに残すと、
次に届いたものとどちらが新しいか分からなくなる。**記録は `UPDATES.md` に残っている。**

### 12. 摩擦を記録する

取り込みの過程で「レポートに書いていなくて詰まった」「区分が実態と合わなかった」が
あれば `/devenv-feedback` で記録する。それは**基盤側のレポートの書き方の問題**であり、
持ち帰る価値がある。

## 雛形と実体の対応

導入時に名前が変わるファイルがある。パックにあるのに手元に無い場合はこれを見る。

| パックのファイル | このリポジトリの実体 | 扱い |
|---|---|---|
| `CLAUDE.template.md` | `CLAUDE.md` | 常に `統合`（雛形は導入時に消えている） |
| `devenv.config.example.json` | `devenv.config.json` | 例はそのまま置いてよい。実体は `統合` |
| `devenv.feedback.example.json` | `devenv.feedback.json` | 実体は触らない（記録が入っている） |
| `.claude/settings.hooks-perl.json` / `-node.json` | `.claude/settings.json` | 実体は `統合` |
| `gitignore.append` / `gitattributes.append` | `.gitignore` / `.gitattributes` | マーカー以降だけ見る |

## 注意事項

- **一度統合したファイルは、以後ずっと `統合` 扱いになる。**
  ハッシュが基盤の配布物と一致しなくなるためで、これは正しい動作である。
  そのファイルはこのプロジェクトのものになったということ。
- **`docs/` や `src/` には触らない。** このスキルが扱うのは devenv の配布物だけである。
- 取り込みは1コミットにまとめる必要はない。むしろ
  「置換だけ」「設定の統合」「破壊的変更への追従」を分けた方が、後から追える。
