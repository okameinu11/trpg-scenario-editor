# docs/ のHTMLドキュメント作成

## なぜHTMLか

構造化により情報密度が高く、人間・エージェントの双方が内容を把握しやすいため。
Markdownでは「これは警告」「これは推奨/非推奨の対比」といった**意味づけ**が表現できず、
長文になるほど重要度の差が潰れる。共通CSSの意味づけコンポーネントを使うことで、
斜め読みでも重要箇所が拾える状態を保つ。

**HTMLを直接編集する運用とし、Markdown原稿との二重管理はしない。**

## 手順

1. **既存ドキュメントを先に読む**
   `docs/00_INDEX.html` で各ドキュメントの役割分担を確認する。
   **書こうとしている内容が既存ドキュメントの守備範囲なら、新規作成せず追記する。**
   同じ説明を2箇所に書こうとしているなら、それは集約先が不足しているサイン。

2. **番号を決める**
   `docs/NN_名前.html` の連番。既存の並びの意味（要件→設計→運用 等）を壊さない位置に置く。

3. **`docs/_TEMPLATE.html` を雛形にする**
   `<link rel="stylesheet" href="assets/style.css">` を相対パスで参照する。
   **CSSファイルは複製しない。**

4. **コンポーネントを使い分ける**

   | クラス | 用途 |
   |---|---|
   | `header.hero` + `.eyebrow` + `.lead` | ページ冒頭。何を定めるドキュメントか |
   | 番号付き `h2` / `h3` | セクション構成。参照時に「§3.2」と指せるようにする |
   | `.callout` | 補足・注意。読み飛ばすと事故になる情報 |
   | `.callout.warn` | 中間の警告。踏むと手戻りするが、直せるもの |
   | `.callout.danger` | 強い警告。取り返しのつかない操作・法令や課金に関わるもの**だけ** |
   | `.do-dont`（`.do` / `.dont`） | 推奨/非推奨の対比。理由も添える |
   | `.badge`（`required` / `recommended` / `optional`） | 表の中で必須度を示す |
   | `.checklist` | 実行前・実行後に確認する項目 |
   | `.card-grid` + `.card` | 複数ドキュメント・項目への入口 |
   | `table` | 構造化データ |
   | `ol.steps` | 順序のある手順 |

   使う前に `docs/` 内を grep して既存の使われ方を確認すること。
   **`.callout.danger` を乱発しない。** 全部が危険だと表示されると、本当の危険が埋もれる。
   強弱は「補足 / 警告 / 危険」の3段ある。中間が要るときに `danger` へ寄せると、
   段階そのものが潰れて使えなくなる。迷ったら `.callout.warn` を選ぶこと。

5. **「なぜ」を残す**
   テーブル定義やAPIシグネチャは他のドキュメントが受け持つ。設計書が担うのは
   **なぜその設計にしたか**である。具体的には:
   - 検討した代替案と、却下した理由
   - 想定した失敗・攻撃と、その防御
   - 将来拡張の入り口（どこを変えれば拡張できるか）

6. **`docs/00_INDEX.html` に登録する**
   `card-grid` にカードを追加する。番号・タイトル・一行説明を埋める。

7. **末尾を整える**
   `.pagenav`（前後のドキュメントへのリンク）と `.pagefoot`（最終更新日）を更新する。

## 注意事項

- 日本語ファイル名を使ってよい。pre-commitのチェックは `core.quotepath=false` で
  日本語パスを扱えるようにしてある。
- ドキュメントを追加・削除したら `docs/00_INDEX.html` も同じコミットに含めること。
