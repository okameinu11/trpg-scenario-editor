# 既存のサンプルシナリオを点検する・追従させる

**最初に `scripts/sample-kit/README.md` を読む。** サンプルの役目・置き場所・準備・道具の使い方・合格条件・してはいけないことは、すべてそこにある。

このスキルは2つの作業を受け持つ。どちらも「今のアプリで原本を作り直し、道具の結果を読んで、分類して直す」点は同じで、違うのは何を探すかである。

| 作業 | 探すもの | 言われ方 |
|---|---|---|
| **点検** | 壊れているところ（参照切れ・記法の誤り・表示崩れ・原本と完成品のずれ） | 「点検して」「壊れていないか見て」 |
| **追従** | アプリに増えたのに、サンプルが使っていない機能 | 「最新にして」「新機能を入れて」、機能を足した・リリースした直後 |

どちらか分からなければ両方やる。点検で壊れていないことを確かめてから追従するほうが、直した原因を切り分けやすい。

## 1. 対象を決めて回す

1. `samples/*/data.json` を一覧する。指定が無ければ全サンプルが対象。
   完成品のJSON（`samples/<slug>.json`）だけがあり原本のフォルダが無いものは、原本を作れないので報告に書いて飛ばす。
2. **点検でも追従でも、最初に点検の一式を回す**: `lint,build,verify,diff,export,roundtrip,pdf,shots`。
   - `diff` は、export で完成品を上書きする前に、原本と完成品がずれていなかったかを見るため
   - 表示崩れは shots でしか見られないので、何も直さないときでも撮る
   - 追従では、壊れていないことを先に確かめておくと、追従で直した結果と切り分けられる。drift もこの verify の結果で読む
3. 点検では本文を通読しない。道具の結果（lint・problems・diff）に出た箇所と、その前後だけを読む。筋や矛盾を確かめるのは、求められたときに `scenario-gm-reviewer` で行う（自分で通読しても、書いた側と同じ読み方になりやすい）。

## 2. 点検：見つかったものを分ける

| 分類 | 例 | すること |
|---|---|---|
| **機械的な誤り** | lint のエラー、`verify.problems`（参照切れ・残った記法・右の段だけの行・見出しに残った #）、roundtrip の不一致 | その場で原本を直し、回し直す |
| **原本と完成品のずれ** | `diff.same` が false（完成品だけ手で直された、原本を直したのに作り直していない） | どちらが正しいかを `diff.changedFields`・`contentFirstDiff` で確かめる。完成品の側が正しければ原本に移してから作り直す。判断がつかなければ報告する |
| **内容に関わるもの** | `coverage.unused`、lint の警告のうち判断が要るもの、長さ | 直し方の案をつけて報告し、承認を得てから直す |
| **参考** | `variety` の未使用 | 報告に1行で書く。自然に入る場所があるときだけ案を出す |
| **道具の誤り** | 正しい原本なのに lint が誤って指摘する、verify が落ちる | `scripts/sample-kit/` を直し、何を直したか報告する |
| **アプリの不具合** | アプリの表示がおかしい | 直さずに報告する（README §6） |

求められたら、`scenario-gm-reviewer` エージェントにGMの目で読ませる（呼び方は `sample-scenario-write` §5 と同じ）。

## 3. 追従：アプリに増えたものを見つける

`verify.drift` を読む。

- `newerReleases`: 原本を作った版（`meta.builtWith`）より新しいリリースノート。`[新機能]` と `[改善]` が主な手がかり
- `unknownActions`: アプリの操作（`ACTIONS`）のうち、道具の機能一覧（`kit.js` の `FEATURES`）のどれにも対応しないもの。**新しい記法がある、という合図**
- `docRows.unmapped`: 記法の一覧の表（`docs/01_要件定義書.html` §4.1）にあるのに、道具が知らない行。**ボタンの無い新しい書き方は、ここでしか見つからない**
- `docRows.changedAfter`: 原本を作った日より後に注記の付いた行。その行を docs/01 で読み、サンプルの書き方が今の規則に合っているかを確かめる
- `docRows.sameDay`: 原本を作った日と同じ日付の行。その版にすでにあったものが多い。`newerReleases` の項目に関係する行だけ確かめる
- `coverage.unused`: 道具は知っているのに、サンプルが使っていない機能（追従し損ねた機能がここに残る）
- `unknownSystems`: 道具が知らないシステム。`scripts/sample-kit/systems.md` の「新しいシステムが増えたら」に従う

変更を1つずつ分類する。

| 分類 | 例 | すること |
|---|---|---|
| 新しい記法・データ | 新しいブロック記法、基本情報の新しい種類、`docRows.unmapped` の行、`coverage.unused` の機能 | サンプルで使う（§4）。道具が知らないものは、`kit.js` の `FEATURES`（表の行なら `DOC_ROWS` も）と `features.md` に1行ずつ足し、網羅で数えられるようにする |
| 既存の記法のふるまいの変更 | 表示や段落の扱いの変更 | `shots` で意図どおりに見えるか確かめる。崩れたら原本を直す |
| 画面の操作だけ | 元に戻す、ショートカット、パネルの並び | サンプルのデータに残らないので、何もしない。`unknownActions` に出ていたら `kit.js` の `APP_ONLY_ACTIONS` に足す |
| 不具合の修正 | | 不具合を避けるために書いていた不自然な書き方があれば、素直な書き方に戻す |

1つの変更が2つの分類にまたがることがある。たとえば不具合の修正で、新しい書き方ができるようになった場合。**サンプルで使える書き方が増えたなら、リリースノートの見出しが「不具合修正」でも「新しい記法」として扱う。**

新しい記法の書き方は、リリースノートではなく `docs/01_要件定義書.html` §4 と `docs/04_記法設計書.html` で確かめる（リリースノートは利用者向けの要約なので、細部が書いていない）。

## 4. 追従：どこに足すかを決めて承認を得る

1. 足す機能ごとに、**どのサンプルの、どの場面に、どう足すか**を決める。
   `scripts/sample-kit/features.md` の「自然に使える場所」を手がかりにし、新しく場面を作るより、既存の場面で自然に使える所を探す。
   機能のための場面を足すと、筋が間延びする。
   既存の文を分ける・並べ替えるだけで見本になるなら、それがいちばんよい（新しい文を足さないので、筋に影響しない）。
2. **案の見え方を `try` で確かめる。** 足す断片を `samples/<slug>/try.md` に書いて `try` を回し、`layout` と `shots/try.png` を見る。原本は変えない。試し終えたら try.md は消す。
3. 案をチャットに出して、**承認を得てから原本を直す。** 案には try の結果（行の組み方）を添える。案の形:

   | サンプル | 場面（見出し） | 足す機能 | 足す内容（1〜2文） |
   |---|---|---|---|

4. 足した内容は、そのサンプルの文体・NPCの口調・既存の手がかりと矛盾しないようにする。
   `samples/<slug>/outline.md` があれば読み、対応表にも行を足す。

## 5. 仕上げる

1. 直したサンプルごとに `lint,build,verify,diff,export,roundtrip,pdf,shots` を回し、README §5 の合格条件を確かめる。
   直した場面は `section&shot=<見出しの題名>` で撮って必ず見る（shots は要所ごとに最初の1つしか撮らないので、直した場面が写るとは限らない）。
2. **追従を終えたサンプルの `meta.builtWith` を `build.appVersion` に更新する。** 何も足さなかったサンプルも更新する。
   更新しないと、次の追従でまた同じリリースノートを読み直し、同じ判断をやり直すことになる。
   **点検だけのときと、承認待ちで止めたときは更新しない。** どちらも追従を終えていないので、更新すると次の追従で、その間に増えた機能を見落とす。

## 6. 報告

日本語で、サンプルごとにまとめる。

- **点検の結果**: 合格条件の各項目。直した機械的な誤り。`diff` の結果（ずれの有無）
- **追従の結果**: 見た版の範囲（`builtWith` → `appVersion`）、変更ごとの分類と判断。足したもの（場面と内容）。**何も足さなかったなら「変更不要」とその理由**
  - 点検だけのときは、drift に出ていることを「次に追従するときの材料」として短く書く（分類の見立てまででよく、`builtWith` は上げない）
- **承認が要るもの**: 内容に関わる指摘と直し方の案
- **道具を直したなら**: 何をなぜ直したか
- **アプリについて気づいたこと**: 直さずに報告だけ
