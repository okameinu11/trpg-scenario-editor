# 実行記録の点検

## なぜやるか

記録を取る仕組みだけがあって読む手順が無いと、「記録はあるが誰も見ない」状態になる。
オートモードは権限プロンプトを自動承認する運用なので、**実行された事実を後から確認する場が
ここしかない**。取っただけの記録は保険になっていない。

## 記録の形

`.claude/logs/<年-月>/agent-actions-<年-月-日>.log` に日付ごとに分かれている。

```
2026/8/31 14:23:05 [!SQL-WRITE]
      psql "$DATABASE_URL" -c "UPDATE public.users SET role = 'admin'"

2026/8/31 14:25:11 [ ]
      npm run build

2026/8/31 14:26:02 [FILE:WRITE(新規)] src/lib/auth.ts
```

- **1行目が見出し**（日時と印）、**本文は6文字ぶん字下げ**されている。この違いが点検の要になる。
- `[ ]` は印なし。`[!LABEL]` が「あとから見返したい」操作。
- 印の種類は `devenv.config.json` の `auditLog.extraLabels` と
  `.claude/hooks/audit-log.*` の `DEFAULT_LABELS` で決まる。

## 手順

### 1. 範囲を決める

前回の点検位置を探す。**行頭の日時に固定して検索すること。**

```bash
grep -rn "^[0-9].*AUDIT-CHECKPOINT" .claude/logs/ | tail -5
```

見つかったら、その日時以降だけを見る。見つからなければ全ファイルが対象になる。

```bash
ls .claude/logs/*/          # 日付ごとのファイル一覧
```

日付でファイルが分かれているので、**前回の点検日より新しいファイルだけを開けばよい**。

### 2. 印の付いた操作を、危険度の高い順に見る

上から順に確認する。**この順序は「戻せなさ」の順**である。

| 順 | 見るもの | 探し方 |
|---|---|---|
| 1 | 本番DBへの書き込み | `SQL-WRITE` / `DB-WRITE` の印。接続先が本番かローカルかを必ず確認する |
| 2 | 権限を迂回する鍵の使用 | `DB-KEY` の印。読み取りだけだったかを本文で確かめる |
| 3 | Git履歴の操作 | `GIT` / `PUSH` の印。`reset --hard` `rm` `push` は取り返しがつかないことがある |
| 4 | 削除・一括置換 | `FS` / `FS-WRITE` / `INLINE-SCRIPT` の印 |
| 5 | プロジェクト外への書き込み | 本文中の絶対パス・`..` を含むパス |
| 6 | 外部サービスへの送信 | `NET-WRITE` の印。何を送ったかを本文で確かめる |
| 7 | 秘密情報の露出 | 鍵・トークンが**値のまま**本文に写っていないか |

```bash
LOG=.claude/logs/2026-08/agent-actions-2026-08-31.log
grep -n "^[0-9].*\[!" "$LOG"           # 印の付いた見出しだけ
grep -n -A3 "^[0-9].*SQL-WRITE" "$LOG" # 印と本文をまとめて
```

### 3. 現在の状態を突き合わせる

記録は「実行した」ことしか示さない。**結果がどうなったかは別に確認する。**

```bash
git status
git log --oneline -20
```

記録にある破壊的操作が、実際に何を壊したか（あるいは壊していないか）をここで判断する。

### 4. 報告する

見つからなかったときも「無かった」と明示する。危険度順に、次を書く。

- 何を実行したか（日時とコマンドの要点）
- それが何に影響したか（現在の状態と突き合わせた結果）
- 対処が要るか

### 5. 点検位置に印を残す

最後に、点検し終えた位置を記録へ書き込む。次回はここから再開できる。

```bash
printf '%s [AUDIT-CHECKPOINT] ここまで点検済み\n\n' "$(date '+%Y/%-m/%-d %H:%M:%S')" >> "$LOG"
```

## 落とし穴

- **`AUDIT-CHECKPOINT` を単純な文字列検索で探さないこと。**
  この印を書き込むコマンド自体も記録に残るため、素の `grep AUDIT-CHECKPOINT` は
  **本文側の出現**を拾う。それを前回位置と誤認すると、その手前の未点検範囲を丸ごと
  読み飛ばす。見出し行は行頭が日時なので、`^[0-9]` を必ず付ける。

- **印が無いこと＝安全ではない。**
  印は「見返す優先度」であって危険度の判定ではない。既定の印は生SQL・git・削除など
  形の決まった操作しか拾わない。アプリのスクリプト経由の書き込みは印が付かないことがある。
  印の付いた操作を見終えたら、`[ ]` の側も件数と傾向くらいは眺めること。

- **誤検知は「印の設計が悪い」合図。**
  同じ種類の誤検知を2回以上見つけたら、点検を続ける前に
  `devenv.config.json` の `extraLabels` に `requires` / `unless` を足して潰す。
  誤検知だらけの印は目印として機能しなくなり、点検そのものが形骸化する。
  基盤側の問題なら `/devenv-feedback` で記録して持ち帰る。

- **記録はローカル専用。** `.claude/logs/` は gitignore 済みで、成果物ではない。
  点検結果をリポジトリに残したいなら、ログではなくドキュメントに書く。
