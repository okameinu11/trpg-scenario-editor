HTML出力設計書

台本（プレビューの紙面）を、それだけで開けるHTMLファイル1枚に書き出す機能について、 何を残して何を外すか・CSSと画像をどう持たせるか・書き出したファイルで何が動くかを、なぜその形にしたかとともに残す。 プレビューにボタンなどの操作を足すとき、プレビューのCSSの書き方を変えるとき、コピーの処理を直すときに読むこと。

1. 守備範囲

それまでの書き出しは PDF（ブラウザの印刷）だけだった。PDFでも目次の項目は見出しへのリンクとして残る （04 記法設計書 §10）が、情報（[情報:題名]）と探索可能箇所のコピーのボタンは紙に出さないので、 受け取った人の手元では使えない。2026-10-10 に「コピーや目次のジャンプが死んでしまう」との要望を受け、HTMLでの書き出しを足した。

知りたいこと読む場所
何を残し、何を外すか§2
紙面のCSSの拾い方§3
書き出す前の確認§4
書き出したファイルで動く処理（コピー・目次・印刷）§5
立ち絵・サムネイルの持たせ方§6
入口（ヘッダーの「📤 出力」）§7
プレビューのダブルクリック・原文の小窓（書き出しでは外すもの）11 プレビュー連携設計書

処理は index.html の exportScenarioHtml() から始まる。PDF出力（triggerPrint()）と同じく、 原文の小窓の書き換えを確定し、プレビューを描き直してから写す（打った直後はデバウンス待ちでプレビューが古いことがあるため）。

2. 残すものと外すもの

書き出すファイルの読み手は、配られた台本でセッションを回すGMである。Kotroで書くための仕掛けは要らず、 読む・回すためのものだけを残す。中身はプレビューの紙面（.preview-paper）をそのまま写す。

プレビューにあるもの書き出し理由
目次の項目（見出しへのリンク）残す読み手が長い台本を行き来するためのもの。PDFでも残している
情報・探索可能箇所の「📋 コピー」残すセッション中にチャットへ貼るためのもの。HTML出力を足した理由そのもの
立ち絵・サムネイル・場面図・レーダーチャート残す紙面の一部。画像はファイルに埋め込む（§6）
未登録のNPC・情報の警告残す（PDFと同じ）紙面を変えないかわりに、書き出す前に知らせる（§4）
ダブルクリックで原文へ・書いた画面を開く、マウスを乗せたときの点線の枠外すKotroの本文やモーダルへ戻る仕掛けで、書き出したファイルには戻る先が無い
原文の小窓外す同上。書き出す前に確定するので、紙面には残らない
未登録の情報の「＋ 登録する」外す情報一覧へ登録する入口。読み手には登録する先が無い
目次が空のときの案内文（「行頭に # を付けた段落が…」）外す書き手への使い方の案内
情報一覧（Alt+L のパネル）付けない本文の中の各情報にコピーのボタンがあり、コピーはそれで足りる。紙面の上に操作の部品を増やさない（2026-10-10 に利用者と決めた。§8）
スクロールの連動・本文とプレビューの並べ方外す本文の欄が無い

2.1 残すものを選んで拾う

紙面のうち操作の部品は、どれも .no-print（紙に出さない）が付いている。 書き出しでは .no-print の要素をすべて外し、EXPORT_KEEP_SELECTOR に当たるもの（コピーのボタン）だけを残す。 あわせて data-* の属性（原文での位置 data-src・出どころ data-origin など）も、 書き出し用の data-copy（§5.1）を除いてすべて落とす。

DO

プレビューに書き手向けの部品を足すときは .no-print を付ける。書き出しには何もしなくても出ない。 読み手も使う操作を足すときは、EXPORT_KEEP_SELECTOR に足し、書き出したファイルで動く処理を §5 の形で用意する。

DON'T

外すものを並べて消す形（ブラックリスト）にしない。書き手向けの部品を足したときに書き出しの側を直し忘れると、 押しても何も起きないボタンが配った台本に残る。残すものを選ぶ形なら、直し忘れても「出ない」側に倒れる。

3. 紙面のCSSの拾い方

紙面のCSSは index.html の1つの <style> の中に、アプリの画面のCSSと混ざって散らばっている （#preview-area の規則だけでも十数か所に分かれ、.info-target のように情報一覧と共有していて #preview-area を付けていない規則もある）。書き出しでは、ブラウザが読み込んだスタイルシート（CSSOM）を規則ごとに見て、 次のどれかに当たるものだけを拾う（collectExportCss()）。

拾う規則理由
セレクタに #preview-area か .preview-paper を含むホバー・コピー済み（.copied）など、書き出す時点では当たっていない状態の規則も拾うため
書き出す紙面のどれかの要素に当たる（querySelector で確かめる）.info-target・.level-symbols のような共有の規則や * を拾うため。ホバーなどの状態と疑似要素はセレクタから外してから確かめる（EXPORT_SELECTOR_STATE_RE）。外すと書けなくなるセレクタ（:hover だけ など）は、どこにでも当たりうるので拾う
:root色の変数（--preview-text・成功度の色など）

@media・@supports の中も同じ基準で拾う（印刷用の @media print も入る。§5.3）。 @keyframes は、拾った規則が名前を使っているものだけ載せる。 アプリの body の規則（画面の割り付け・暗い背景・overflow: hidden）は紙面のどの要素にも当たらないので入らず、 かわりに白い背景とアプリと同じ字体だけの土台を置く（字体は getComputedStyle(document.body) から写す）。

書き出すファイルの構造は <body> 直下に .preview-paper > #preview-area で、アプリと同じなので、 拾った規則はそのまま当たる。2026-10-10 に、エモクロアとCoCのサンプルで、紙面の全要素（571個・610個）の位置・大きさ・文字色・背景・字体が アプリのプレビュー（プレビューだけの表示、1280px）と一致することを確かめた。違ったのはスクロールバーの幅だけである （アプリのプレビュー欄は細いスクロールバー、書き出したファイルはブラウザ標準のもの。紙面の幅に上限がある 1080px 以上では差が出ない）。

紙面の部品のCSSは、これまでどおり #preview-area を付けて書くこと。付けずに書いた状態の規則 （例: .npc-card.open のような、書き出す時点では当たっていないクラスの規則）は拾われない。 当たっている要素がある規則（共有のクラスなど）は、付けなくても拾われる。

3.1 却下した案

案却下した理由
アプリの <style> を丸ごと写すアプリの body の規則（height: 100vh・overflow: hidden・暗い背景）が紙面を壊し、打ち消す規則を書き出し側で持ち続けることになる。画面のCSSの大半（モーダル・パネルなど）も無駄に入る
紙面のCSSを別の <style id> に移し、それを写す契約としては一番分かりやすいが、十数か所に散った規則を動かすとカスケードの順序（同じ詳細度の規則の勝ち負け）が変わり、プレビューの見た目が気づかない形で変わりうる。上の方式は規則の場所を変えずに済む
写すクラスを手で並べた一覧を持つ紙面に部品を足すたびに一覧の更新が要り、忘れると書き出しだけ崩れる。#preview-area と「当たるかどうか」で決めれば一覧が要らない

4. 書き出す前の確認

状況扱い理由
本文で使っているのに登録されていないNPC・情報がある 名前を並べて「このまま書き出しますか？」と確認する（exportMissingRefs()）。書き出したファイルの紙面はPDFと同じで、警告もそのまま出る HTMLは配るための形なので、配る前に気づけるようにする。紙面から黙って消すと、NPCカードや情報があるはずの場所が空になり、書き手も読み手も欠けに気づけない（2026-10-10 に利用者と決めた）
本文が空 書き出さずに知らせる 空のプレビューには書き手向けの案内文（「テキストを入力すると…」）が出ており、そのまま書き出しても意味が無い
原文の小窓を開いている 確定してから書き出す。確定できなければ止める PDF出力と同じ（11 §4.5）。書き出したつもりで小窓の中身だけが残るのを防ぐ

未登録のものは、プレビューに出ている警告から拾う（NPCカードの .npc-missing、NPCのセリフの .npc-speech-missing、 情報の .info-missing）。本文の記法を読み直さないのは、書き出す紙面に出ているものと確認の中身を必ず一致させるため。

5. 書き出したファイルで動く処理

5.1 コピー

コピーする文面は、書き出すときに作ってボタンの data-copy に持たせる。 アプリでは情報の文面を情報一覧のデータ（currentInfos）から作るが、書き出したファイルにはそのデータが無い。 情報は infoCopyText()、探索可能箇所は searchListCopyText() で作る（どちらもアプリのコピーと同じ関数なので、文面がずれない）。

押したときの処理（クリップボードへ書く・押したボタンに「✓ コピーしました」を1.5秒出す）は、アプリの copyTextToClipboard()・legacyCopy()・copyWithFeedback() を、関数の文字列（toString()）のまま埋め込む。 同じ処理を書き出し用に書き直すと、片方だけ直す事故が起きるため。

この3つの関数は、書き出したファイルの中ではこの3つだけで動く。中でほかの関数やアプリの変数（showAppToast() など）を使うと、 アプリでは動くのに、書き出したファイルでだけコピーが壊れる。直したら、書き出したファイルでボタンを押して確かめること。

file:// で開いたとき（受け取った人がファイルをダブルクリックで開く）も、Chrome は安全な文脈として扱うので Clipboard API が使える。 使えない環境では、アプリと同じく legacyCopy() に落ちる。

5.2 目次のリンク

書き出したファイルでは、リンク本来の動き（href="#toc-h-…" で飛び、アドレスに # が付く）に任せ、スクリプトを持たせない。 html { scroll-behavior: smooth } で、アプリと同じくなめらかに移る。

アプリでは # を付けないようにしている（再読み込みのたびに飛ぶのを避けるため。initTocLinks()）。 書き出したファイルは読むための文書なので、# が付けばブラウザの「戻る」で目次へ戻れる利点のほうが大きい。

5.3 印刷

受け取った人が書き出したファイルを印刷・PDF化しても、アプリのPDF出力と同じ組み方になる。 印刷用の規則（@media print の @page・段組み・色の印刷）も §3 の基準で拾われ、 コピーのボタンは .no-print の規則で紙には出ない。

6. 立ち絵・サムネイル

画面に出している立ち絵とサムネイルは blob: URL で、そのタブの中でしか読めない。 書き出すときに data URL へ置き換え、ファイル1枚で画像まで出るようにする（inlineObjectUrls()）。 画像を別のファイルに分けないのは、「渡せば即開ける」ことを優先したため（Kotro自体を1枚構成にしたのと同じ理由。CLAUDE.md）。 立ち絵は長辺1024px、サムネイルは1600pxに縮めて保存しているので、ファイルが大きくなりすぎることはない（サンプルで約230KB）。

置き換えには、blob: URL を fetch せず、URLを作ったときに控えた Blob を使う（objectUrlRegistry を URL → Blob の対応にした）。 file:// で開いたときに fetch を拒否される環境があるため（dataUrlToBlob() を自前で書いたのと同じ理由）。 Blob は blob: URL が掴んでいるので、控えに持ってもメモリは増えない。

字体は Google Fonts をアプリと同じリンクで読む。オフラインでは、アプリと同じく端末の字体に落ちる。

7. 入口

ヘッダーの「🖨 PDF出力」を「📤 出力」にし、押すと「PDF出力」「HTML出力」を選ぶメニューが出る形にした。 ヘッダーは幅が尽きており（07 操作の入口設計書 §3.6）、ボタンを足すと狭い画面で入口の名前が消える段へ進むため。 メニューの仕組みは下部パネルの「🗺 場面図・目次」と同じ PANEL_MENUS / panelMenu（07 §3.7）で、 ボタンが画面の上半分にあるときはメニューをボタンの下に出す。

コマンドパレットでは「PDF出力」「HTML出力」が別々の操作として出る（どちらも既定のキーは無し。場面図の表示中も使える）。 ボタンの ▾ は下部パネルと同じく右上の角に重ねる。名前の横に並べると、768px でヘッダーの左側が11pxはみ出した。 重ねる形にしてからは、エモクロア・CoCとも 1280px・768px で、詰める段は「PDF出力」のボタンだったときと同じである。

8. 見送った案

案見送った理由
情報一覧（場面ごとにまとめた情報のコピー・その情報への移動）も書き出したファイルに付ける本文の中の各情報のコピーで足りる。紙面の上に開閉する部品が増える。必要になったら §9 の入り口から足す（2026-10-10 に利用者と決めた）
ヘッダーに「HTML出力」のボタンを別に足す§7。1手で出せるが、ヘッダーが詰まる
コマンドパレットからだけ使える形にするボタンが無いと存在に気づかれない（目次で実際に指摘を受けた。07 §3.2）
未登録の警告を、書き出したファイルからは消す§4。欠けに気づけなくなる

9. 将来拡張の入り口

やりたいこと変える場所
読み手も使う操作を紙面に足す（例: 判定の結果をコピー） 部品に .no-print を付け、EXPORT_KEEP_SELECTOR に足す。押したときの処理は、文面を buildExportHtml() で data-copy に持たせればコピーの処理をそのまま使える。別の処理が要るなら、§5.1 と同じく単独で動く関数にして埋め込む
情報一覧を付ける（§8 で見送ったもの） renderInfoDrawer() の場面ごとのまとめ方を、書き出すときに静的なHTML（コピーのボタンと、情報への # リンク）として組み、紙面の外に置く。開閉の処理は §5.1 と同じく埋め込む
どこからでも目次へ戻るボタン・常に見える目次 buildExportHtml() で紙面の外に置く。[目次] を書いていないシナリオでも出すなら、collectTocHeadings() と appendixTocEntries() から組む
書き出すシナリオを一覧から選ぶ（いま開いているもの以外） いまはプレビューを写しているので、開いているシナリオしか書き出せない。一覧から書き出すなら、そのシナリオを読み込んで描いてから写す必要がある
