操作の入口設計書

記法の挿入や画面の操作を呼び出す入口（下部パネル・コマンドパレット・ショートカットキー）を、 なぜその形にしたかを残す。操作を足すとき・パネルの見た目を変えるときに読むこと。

1. 守備範囲

このアプリの操作には、同じものを呼び出す入口が3つある。 下部パネルのボタン（タッチ・マウス向け）、コマンドパレット（名前で探す）、 ショートカットキー（覚えた人向け）である。 このドキュメントは、この3つをどう作り分け、どう揃えているかを扱う。

想定している利用者は3通りいる。キーボードの無いタブレットで書く人、 キーボードはあるがショートカットを覚えていない人、すべて覚えている人である。 どの人も、ほかの人のための入口に邪魔されないことが、以降の判断の軸になっている。

知りたいこと読む場所
パネルに何のボタンがあるか（機能要件）01 要件定義書 §2.3
記法そのものの形・変換の順序04 記法設計書
システム固有の記法の入口とパーサの扱い04 記法設計書 §6
場面図を見ている間にキー操作を止める理由06 場面ツリー設計書 §6.1

2. 操作を1つの表にまとめた理由（ACTIONS）

2026-10-05 の改修まで、1つの操作の情報は5箇所に散らばっていた。 パネルのボタン（HTMLに直書き）、ボタン名の表（updateAssistantPanelShortcutLabels()）、 キー操作の振り分け（executeShortcutAction() の switch）、 既定のキーと設定画面の名前（DEFAULT_SHORTCUTS）、 システムによる出し分け（applySystemToUI() と SYSTEM_DEPENDENT_SHORTCUT_TEXT）である。

実際に、この散らばりが原因で次のずれが起きていた。

  • SANチェックはキー操作の側でシステムを確かめていたが、共鳴判定は確かめていなかった。 そのためCoCのシナリオでも Alt+7 で共鳴判定の画面が開き、CoCには無い記法を挿入できた。
  • 入口を1つ増やすたびに5箇所を直す必要があった。コマンドパレットを足すと、これが6箇所になる。

そこで、index.html の ACTIONS に1操作1行で持つ形にした。 パネルのボタン・パレットの候補・設定画面の行・キー操作の受け付けは、すべてこの表から作る。

項目役割区分
idショートカット設定（trpg_shortcuts）の保存キー。変えると利用者の割り当てが失われる必須
groupACTION_GROUPS のどれに属するか。パネルとパレットの並び順・見出しになる必須
icon / name / desc表示名と、何が起きるかの説明。関数でもよい（DL情報／KP情報のようにシステムで変わるもの）必須

key既定のショートカット。null なら未割り当て任意
availableそのシステムで使えるか。false を返すと3つの入口のすべてから消える任意
panelfalse ならパネルに出さない（ヘッダーに既にボタンがある保存・PDF出力・HTML出力など）任意
inModal / inSceneModeモーダル表示中・場面図表示中にも受け付けるか（§5）任意

2.1 ショートカット設定にはキーだけを保存する

以前は trpg_shortcuts に表示名（label / desc）も一緒に書き出しており、 読み込むたびに最新の名前で上書きしていた。表示名は利用者の設定ではないので、 キーの組み合わせだけを保存し、名前は毎回 ACTIONS から引く形に改めた。 旧版が保存した表示名は、読み込み時に pickShortcut() が捨てる。

後の版で操作を足したとき、保存済みの設定にはその操作が無い。 loadShortcuts() は既定のキーを補うが、そのキーを利用者が別の操作に割り当て済みなら、利用者の割り当てを優先して未割り当てにする。 コマンドパレットの Ctrl+K を足したときに、既に Ctrl+K を使っていた人の操作を奪わないため。

3. 下部パネル

ボタンが12個まで増え、各ボタン名の後ろに (Alt + 1) のようなキー表記が付いていたため、 1個あたりの幅が約2倍になっていた。横スクロールしないと右端の「NPC管理」などが見えず、 ショートカットを覚えていない人ほど不便な状態だった。

3.1 現在の形

  • 分類（構成・本文・判定・資料）のタブにする（2026-10-14〜）。左にタブを並べ、開いているタブのボタンだけを右に並べる（Word のリボンと同じ形。理由は §3.2）。 どのタブを開いていたかは、この端末の設定（localStorage の trpg_panel_tab）として覚え、次に開いたときも同じタブにする。既定は「本文」。 タブにマウスを乗せると、そのタブにある操作の名前が並んで出る（開かなくても、どこに何があるかが分かるように）。
  • アイコンの下に名前を置く縦組みにして、1個あたりの幅を詰めた。
  • キー表記はボタン名から外し、マウスを乗せたときの吹き出しに出す。吹き出しには何が起きるかの説明も出す。ショートカットは、開いているタブに関係なく効く。
  • 末尾に「🔎 すべての操作」を置き、そのボタンにだけはキー（Ctrl+K）を常に表示する。存在を知らなければ使われないため。
  • タブもボタンと同じく mousedown で切り替え、本文のカーソルと選択を動かさない（§3.4）。

3.2 分類のタブにした理由と、幅が足りないときの詰め方

2026-10-14 まで、パネルは全部のボタンを1列に並べていた（分類名は縦書きにしてボタンの間に挟んでいた）。 ボタンを足すたびに幅が尽き、名前を削る・操作をメニューに隠す・パネルに置かない、のどれかを選ぶしかなかった（下の経緯）。 「📊 表」（13）を独立したボタンとして足したとき、CoCの1280pxで20px、768pxではボタンを最小の幅にしても45pxはみ出した。 利用者から「セクションごとにまとめてしまえば良いのでは」と提案があり、分類をタブにする形を選んだ（2026-10-14）。

  • 1つのタブに並ぶのは2〜7個なので、どの画面幅でも幅に余裕がある。ボタンを足しても、そのタブの中で収まるかを見ればよい。
  • 代わりに、別の分類の操作はタブを押してからの2手になる。§3.5 で却下した「分類ごとのドロップダウン」と違い、 同じ分類の操作を続けて使うあいだは1手のまま（タブは開いたまま残る）。本文を書いているあいだは「本文」タブを開いておけば、 情景描写・セリフ・情報・DL情報・TIPS・文字色・表がすべて1手で押せる。
  • 場面図と目次は、幅を空けるために「🗺 場面図・目次」のメニューにまとめていた（§3.7）。タブにして幅が空いたので、「構成」タブの2つのボタンに戻した。

幅が足りないときは、data-density を full（正式名）→ short（短い名前。パレットのキー表記も消す）→ tight（パレットの文字も消し、ボタンとタブをタップ領域の下限44pxまで詰める）の順に詰める。 どの段で収まるかは実際にはみ出しているかを測って決める（fitAssistantPanel()）。 開いているタブ・システム（共鳴判定とSANチェックは片方しか出ない）・名前の長さで変わるため、決め打ちの画面幅では合わない。 タブにしたときに、分類名を消すだけの段（nocaption）は要らなくなったので外した。

画面幅構成本文判定資料
1024px 以上fullfullfullfull
768px（タブレット縦）shortshortfullfull

（2026-10-14 時点。エモクロア・CoC とも同じ。768px の「構成」「本文」は正式名だと 89px・133px はみ出す。）

ボタンを足したら、そのタブを 1280px と 768px で、エモクロアとCoCの両方で測り直すこと。 tight のボタンの最小幅は、すでにタップ領域の下限44pxまで詰めてある。1つのタブが tight でも収まらなくなったら、 余白をさらに削るのではなく、分類を分ける（タブを1つ増やす）か、頻度の低い操作をパネルから外す（コマンドパレットからは引き続き使える）ことを検討する。

経緯（1列に並べていた頃）: 「NPCのセリフ」を足したときに1280pxで13pxはみ出し、パネル・グループ・ボタンの余白を少しずつ削って収めた。 「情報」を足したときは余白では足りなくなったので、正式名を削るより先に分類名を消す段（nocaption）を挟んだ。 v1.9.0 では1280pxだけを確かめていて、768pxでは tight でも902pxになり、横スクロールが出ていた（v1.9.1 で修正）。 「📘 シナリオ基本情報」（2026-10-05）は、この時点で768pxの残りが14pxしかなかったため、パネルには置かなかった（panel: false）。 入口はヘッダーのタイトル欄の隣・コマンドパレット・Alt+B にした（08 §6）。 続く巻末（FAQ・あとがき・権利表記）も同じ理由で、基本情報の隣の「📕 巻末」1つにまとめた（FAQは Alt+A。09 §4）。 タブにして幅は空いたが、この2つは表紙と巻末という「本文の外のもの」の入口で、タイトル欄の隣にあるほうが探しやすいので、ヘッダーに残している。 ヘッダーに入口を足すときは §3.6 の詰め方に従う。 本文とプレビューの並べ方（「プレビューを広げる」「本文を広げる」。2026-10-07）は、ヘッダーにもパネルにも置かず、 本文とプレビューの境界にボタンを置いた（キーは Alt+P。11 §2.4）。 スクロールの連動の入切（2026-10-09）も同じく境界のボタンとコマンドパレットに置いた（既定のキーは無し。11 §5.4）。 「🔖 目次を挿入」（2026-10-05）は最初パネルに置かず、ボタンが無いと気づけないと指摘を受けて、「場面図を挿入」と1つのボタン（メニュー）にまとめた（§3.7）。

パネルの高さを固定してはいけない。 横スクロールバーが出ると、その分だけボタンが潰れる。固定していたときは41pxまで縮み、 タップ領域の下限44px（01 要件定義書 §5）を割っていた。 ボタン側に min-height: 44px を持たせ、パネルは中身に合わせて伸びるようにしてある。 同じ理由で、ボタンとグループは flex-shrink: 0 にしてある（縮むと名前がボタンの外へはみ出して重なる）。

3.3 吹き出しをパネルの外に置く理由

パネルは横スクロールのために overflow を指定している。 その中に吹き出しを置くと、パネルより上へ出る部分が切り取られる。 そのため body 直下に #panel-tip を1つだけ置き、ボタンの位置を測って重ねている。 吹き出しはマウスのときだけ出す。タッチで出すと、指を離した後も残って邪魔になる。

3.4 ボタンは mousedown で実行する

クリックで実行すると、押した瞬間にボタンへフォーカスが移り、本文の選択範囲が外れる。 文字色のように「選んだ文字を囲む」操作が成り立たなくなるので、 mousedown で既定動作を止めてから実行している。 Tabキーで移ってきて Enter / Space を押した場合は mousedown が起きないので、 click のうちキーボード由来のもの（detail === 0）だけを別に拾う。

案却下した理由
ボタンを2段に折り返す 本文の高さが削られる。タブレットで画面キーボードを出したときに特に厳しい。
分類ごとのドロップダウンにまとめる 最も頻繁に使う挿入が、毎回1タップ増える。（頻度の低い挿入だけをまとめるのは §3.7 で採った。 分類ごとのタブ（§3.2）は、同じ分類の操作を続けて使うあいだは1手のままなので、これとは別に採った）

3.6 ヘッダーも測って詰める（2026-10-05 追加）

ヘッダーにも入口（📘 基本情報・📕 巻末）を置いたので、パネルと同じ問題が起きた。 当初は画面幅のブレークポイント（1400px・1100px・900px）で名前を消していたが、FAQを足した時点で 1101〜1250pxの間だけ収まらなくなった。収まるかどうかはシステム名の長さ（「エモクロア」と「CoC 6版」）やボタンの数でも変わるため、 決め打ちの画面幅では追いつかない。そこで fitHeader() が実際に測り、次の順に1段ずつ詰める。

段詰めるもの
header-compact-1「ショートカット設定」の名前（名前が最も長く、使う頻度は最も低い。コマンドパレットからも開ける）
header-compact-2「シナリオ一覧」を「一覧」に縮める（枠と 📂 があれば、短くしても何のボタンかは伝わる）
header-compact-3アプリの名前「Kotro」と、左側の要素の間隔（12px → 8px）
header-compact-4「執筆／場面図」「基本情報／巻末」の名前
header-compact-5「保存」「出力」の名前と、ボタン・ヘッダーの余白
header-compact-6「一覧」の文字。それでも収まらない画面（768px未満）では、左側を横スクロールにする

左上はアプリの名前と版番号、その隣がシナリオ一覧の入口である（2026-10-09 変更）。 それまでは左端の「📂 一覧」が一覧の入口だったが、ロゴと同じグラデーションの文字で枠が無く、押せるボタンに見えなかった。 そこで、一覧の入口はほかのボタンと同じ枠付きの「📂 シナリオ一覧」にし、空いた左端にはアプリの名前を置いた。 名前は飾りで、押しても何も起きない（押せそうな見た目にしない）。版番号はリリースノートの唯一の入口なので隠さない。

名前は入口の名前より先に譲る（header-compact-3）。ブラウザのタブ名には残るので、画面から消えても困らない。 逆に「執筆／場面図」「基本情報／巻末」の名前より後に譲ると、1280pxで入口がアイコンだけになる。 名前を足したことで、1280pxは header-compact-1 から header-compact-3 になった（名前は隠れ、入口の名前は残る）。 名前が出るのは、エモクロア・CoCとも1366px以上である。

  • はみ出しはヘッダー全体ではなく .header-left の中で測る。 左側は縮めるために min-width: 0 を持つので、収まらなくてもヘッダーの幅は変わらず、右側のボタンの下に潜り込むだけになる。 ヘッダー全体の scrollWidth で測ると、重なっていても「収まっている」と判定される（実際にこれで768pxの重なりを見落とした）。
  • 幅が足りないとき最初に縮むのはタイトル欄である（下限100px）。収まっていても、タイトル欄が170px（全角10文字ほど）を切るなら次の段へ進む。 この値は、1280pxでエモクロア・CoCとも「執筆／場面図」「基本情報／巻末」の名前を残せるように決めた。
  • 保存状態の表示は2行まで折り返し、幅は固定する（中身の長さでヘッダーの収まり方が変わらないように）。 header-compact-3 以降はこれも縮み、収まらない行は隠れる。
  • 測り直すのは、ヘッダーの大きさが変わったとき（ResizeObserver）・Webフォントが届いたとき・システムを切り替えたとき。
  • 測っているあいだは transition を止める（header-measuring）。ボタンは余白を transition で動かすので、 段を切り替えた直後に測ると変わる前の幅が返り、直前の段によって結果が1段ずれていた（2026-10-09 に修正）。
ヘッダーに要素を足したら、1280px と 768px で、エモクロアとCoCの両方を測ること。 見るのは「左側の最後の要素の右端」と「右側のボタンの左端」の間が0以上あるかと、どの段になったか。 1280pxで header-compact-4 以降になったら、入口の名前が消えて分かりにくくなっていないかを確かめる。

3.7 1つのボタン（メニュー）にまとめる仕組み（2026-10-05 追加）

パネルが1列だった頃は768pxで幅が尽きていた（§3.2）。それでも、ボタンが無い操作は存在に気づかれない（目次で実際に指摘を受けた）。 そこで、シナリオに1回入れれば済む挿入（場面図・目次）を「🗺 場面図・目次」の1つのボタンにまとめ、 押すと選ぶメニューが出る形にした。v1.17.0 では「表を挿入」も同じメニューに入れていた。

2026-10-14 にパネルを分類のタブにして幅が空いたので、下部パネルではこのまとめ方を使わなくなった（場面図・目次は「構成」タブの2つのボタン、表は「本文」タブの「📊 表」）。 仕組みは、ヘッダーの「📤 出力」（下の段落）で使っているので残してある。タブの中で再び幅が尽きたときにも使える。

  • ACTIONS の各操作に panelMenu を書くと、同じ値の操作がパネルで1つのボタンにまとまる。 ボタンの名前・短い名前・説明は PANEL_MENUS に書く。 コマンドパレット・ショートカット・設定画面では、今までどおり別々の操作として出る（Alt+Z の場面図もそのまま使える）。 メニュー用の偽の操作を ACTIONS に足さなかったのは、パレットとショートカット設定に「メニューを開く」だけの重複した行が出るため。
  • 組のうちそのシステムで使えるものが1つしか無ければ、メニューにせずそのボタンを出す。
  • メニューを開くボタンには右上に ▾ を付け、押すと選べることを示す。開いている間はボタンを押された状態に見せる。
  • メニューは吹き出しと同じく body 直下に1つだけ置き、ボタンの真上に重ねる（§3.3 と同じ理由）。 項目もパネルのボタンと同じく mousedown で実行する（本文のカーソルを動かさないため。§3.4）。 外側を押す・Esc・パネルのスクロール・画面の大きさの変化で閉じる。キーボードで開いたときは先頭の項目へフォーカスを移し、↑↓で選べる。
頻繁に使う挿入をメニューに入れないこと。 §3.5 で「分類ごとのドロップダウン」を却下したのと同じ理由で、毎回1タップ増えると書く手が止まる。 メニューに入れてよいのは、シナリオに1回か数回しか使わない挿入だけである。

ヘッダーの「📤 出力」も同じ仕組みで作っている（2026-10-10）。HTML出力を足すときに、「PDF出力」と1つのボタンにまとめた （PANEL_MENUS の export。どちらの操作も panel: false なのでパネルには出ず、ボタンはヘッダーのHTMLに直接書いてある）。 ヘッダーのボタンは画面の上半分にあるので、メニューはボタンの真下に出す（togglePanelMenu() がボタンの位置で上下を決める）。 PDF出力は1手増えるが、書き出しは執筆の途中で何度も押すものではないので、上の注意には当たらない。 ▾ はパネルと同じく右上の角に重ねる。名前の横に並べると、768px でヘッダーの左側が11pxはみ出した（§3.6 の段は「PDF出力」のボタンのときと同じに保ってある）。 理由と見送った案は 12 HTML出力設計書 §7・§8。

4. コマンドパレット

Ctrl+K（既定）または パネル末尾の「🔎 すべての操作」で開く。 操作を名前で絞り込み、Enter で実行する。パネルに無い操作（保存・PDF出力・HTML出力・シナリオ一覧・ショートカット設定など）も含む。

狙いは、ショートカットを覚えていない人と、覚えた人の間をつなぐことである。 キーボードから手を離さずに済み、候補の横にその操作のキーが出るので、使ううちにキーを覚えられる。 記法がいくつ増えても、パネルのように幅で破綻しない。

4.1 絞り込みの規則

  • 検索語と候補の両方を、カタカナ→ひらがな、全角英数→半角、大文字→小文字に揃えてから比べる（normalizeForSearch()）。
  • keywords に読みをひらがなで持つ。日本語入力は変換前の文字でも入力欄の値が変わるので、 「はんてい」と打った時点で「技能判定」「共鳴判定」が残る。
  • 空白で区切ると、すべての語を含むものに絞る。名前・読みの頭から一致するものを先に並べる。
  • 未入力のときは分類ごとに見出しを付けて全件を出す。何ができるかを一覧する画面を兼ねる。
日本語入力の変換中の Enter・矢印キーは拾わない（isComposing を見る）。 拾うと、変換を確定したつもりの Enter で候補が実行されてしまう。 NPCの技能欄など、ほかの入力欄と同じ扱いである。

4.2 モーダルの仕組みに載せた理由

パレットは .modal として作っている。 × ボタン・背景クリック・Esc で閉じる処理（01 要件定義書 §2.6）と、 開いている間ほかのショートカットを止める処理を、既存のモーダルとそのまま共用できるため。 候補を実行するときは先にパレットを閉じてから実行する。 開いたままだと、実行した操作が開くモーダル（技能判定など）と重なる。

4.3 却下した案

案却下した理由
行頭で / を打つと候補が出る（スラッシュメニュー） 日本語入力がオンのとき、/ キーは「・」になる。 「・」で反応させると、行頭に箇条書きの「・」を打つたびにメニューが開く。 「/」だけに反応させると、日本語で書いている大半の時間は使えない。
パレットの候補を「最近使った順」に並べる 並びが毎回変わると、矢印キーの回数で覚えた操作が使えなくなる。まずは固定の並びで出した（§7）。

5. いつ受け付けるか

キー操作とパレットは、同じ判定（canRunAction()）で受け付けるかを決める。 片方だけ緩いと、「キーでは止まるがパレットからは本文が書き換わる」ずれが生まれるため。

状況受け付けるもの理由
そのシステムに無い操作 なし（available） 入口を出さないのと同じ扱いにする。記法そのものは常にパースする（04 記法設計書 §6）
モーダル表示中 保存だけ（inModal） 誤爆を防ぐ。保存が効かないほうが驚かれる
場面図の表示中 保存・画面の切り替え・パレット・シナリオ一覧・PDF出力・HTML出力・ショートカット設定（inSceneMode） 本文を書き換える操作を止める。隠れた本文に記法が入っても気づけない（06 場面ツリー設計書 §6.1）
文字を入力する欄の中（2026-10-06 追加） 元に戻す・やり直す（Ctrl+Z / Ctrl+Y）は横取りしない（nativeInText） 欄の中ではブラウザ標準の取り消しに任せる。欄の外で押したときだけ、アプリの履歴でシナリオ全体を戻す（10 元に戻す設計書）

同じキーに複数の操作が割り当たっている場合（旧版のデータなど）は、受け付けない操作を飛ばして、受け付ける操作に譲る。

6. 操作を足すときに触る場所

  • ACTIONS に1行足す（パネル・パレット・設定画面・キー操作はここから自動で作られる）
  • 既定のキーを付けるなら、既存の割り当てと重ならないか確かめる（§2.1 の補い方は、既存利用者の重複しか避けない）
  • システム固有なら available を書く（GAME_SYSTEMS のフラグを見る）
  • 本文を書き換えない操作なら inSceneMode: true を付ける
  • 実行の前に何かを選ぶ必要がある操作（どのNPCの発言か、など）は、run で選ぶ画面を開く形にする。 ACTIONS は引数を取れないため。選ぶ画面はコマンドパレットの見た目に揃え、 ↑↓・Enter・クリックの処理は bindChooserList() を使う（例: npc-speech → openSpeechModal()）
  • パネルにボタンが増えるなら、そのボタンの分類（group）のタブを、1280px（正式名のまま収まるか）と768px（tight で収まるか）の両方で、エモクロアとCoCで確かめる（§3.2。片方だけ見て見落とした実例がある）
  • タブの中で収まらないなら、分類を分ける（ACTION_GROUPS に1つ足すと、タブが1つ増える）か、使う頻度の低い操作をメニュー（panelMenu。§3.7）にまとめる
  • 記法を挿入する操作なら、記法側の変換も要る（04 記法設計書 §7）
既存の操作の id を変えないこと。 id はショートカット設定の保存キーなので、変えると利用者が割り当てたキーが黙って失われる。 保存の操作が今も cloud-save という名前なのはこのためである（クラウド保存は2026-08-31に撤去済み）。

7. 将来拡張の入り口

やりたいこと変える場所
