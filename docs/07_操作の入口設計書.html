操作の入口設計書

記法の挿入や画面の操作を呼び出す入口（下部パネル・コマンドパレット・ショートカットキー）を、 なぜその形にしたかを残す。操作を足すとき・パネルの見た目を変えるときに読むこと。

1. 守備範囲

このアプリの操作には、同じものを呼び出す入口が3つある。 下部パネルのボタン（タッチ・マウス向け）、コマンドパレット（名前で探す）、 ショートカットキー（覚えた人向け）である。 このドキュメントは、この3つをどう作り分け、どう揃えているかを扱う。

想定している利用者は3通りいる。キーボードの無いタブレットで書く人、 キーボードはあるがショートカットを覚えていない人、すべて覚えている人である。 どの人も、ほかの人のための入口に邪魔されないことが、以降の判断の軸になっている。

知りたいこと読む場所
パネルに何のボタンがあるか（機能要件）01 要件定義書 §2.3
記法そのものの形・変換の順序04 記法設計書
システム固有の記法の入口とパーサの扱い04 記法設計書 §6
場面図を見ている間にキー操作を止める理由06 場面ツリー設計書 §6.1

2. 操作を1つの表にまとめた理由（ACTIONS）

2026-10-05 の改修まで、1つの操作の情報は5箇所に散らばっていた。 パネルのボタン（HTMLに直書き）、ボタン名の表（updateAssistantPanelShortcutLabels()）、 キー操作の振り分け（executeShortcutAction() の switch）、 既定のキーと設定画面の名前（DEFAULT_SHORTCUTS）、 システムによる出し分け（applySystemToUI() と SYSTEM_DEPENDENT_SHORTCUT_TEXT）である。

実際に、この散らばりが原因で次のずれが起きていた。

  • SANチェックはキー操作の側でシステムを確かめていたが、共鳴判定は確かめていなかった。 そのためCoCのシナリオでも Alt+7 で共鳴判定の画面が開き、CoCには無い記法を挿入できた。
  • 入口を1つ増やすたびに5箇所を直す必要があった。コマンドパレットを足すと、これが6箇所になる。

そこで、index.html の ACTIONS に1操作1行で持つ形にした。 パネルのボタン・パレットの候補・設定画面の行・キー操作の受け付けは、すべてこの表から作る。

項目役割区分
idショートカット設定（trpg_shortcuts）の保存キー。変えると利用者の割り当てが失われる必須
groupACTION_GROUPS のどれに属するか。パネルとパレットの並び順・見出しになる必須
icon / name / desc表示名と、何が起きるかの説明。関数でもよい（DL情報／KP情報のようにシステムで変わるもの）必須
run実行する処理必須
short幅の足りないパネルで使う短い名前推奨
keywordsパレットの絞り込み用の読み（ひらがな）と別名推奨
key既定のショートカット。null なら未割り当て任意
availableそのシステムで使えるか。false を返すと3つの入口のすべてから消える任意
panelfalse ならパネルに出さない（ヘッダーに既にボタンがある保存・PDF出力など）任意
inModal / inSceneModeモーダル表示中・場面図表示中にも受け付けるか（§5）任意

2.1 ショートカット設定にはキーだけを保存する

以前は trpg_shortcuts に表示名（label / desc）も一緒に書き出しており、 読み込むたびに最新の名前で上書きしていた。表示名は利用者の設定ではないので、 キーの組み合わせだけを保存し、名前は毎回 ACTIONS から引く形に改めた。 旧版が保存した表示名は、読み込み時に pickShortcut() が捨てる。

後の版で操作を足したとき、保存済みの設定にはその操作が無い。 loadShortcuts() は既定のキーを補うが、そのキーを利用者が別の操作に割り当て済みなら、利用者の割り当てを優先して未割り当てにする。 コマンドパレットの Ctrl+K を足したときに、既に Ctrl+K を使っていた人の操作を奪わないため。

3. 下部パネル

ボタンが12個まで増え、各ボタン名の後ろに (Alt + 1) のようなキー表記が付いていたため、 1個あたりの幅が約2倍になっていた。横スクロールしないと右端の「NPC管理」などが見えず、 ショートカットを覚えていない人ほど不便な状態だった。

3.1 現在の形

  • 分類ごとにまとめる（構成・本文・判定・資料）。分類名は縦書きにして、ボタン1個分の幅も取らないようにした。
  • アイコンの下に名前を置く縦組みにして、1個あたりの幅を詰めた。
  • キー表記はボタン名から外し、マウスを乗せたときの吹き出しに出す。吹き出しには何が起きるかの説明も出す。
  • 末尾に「🔎 すべての操作」を置き、そのボタンにだけはキー（Ctrl+K）を常に表示する。存在を知らなければ使われないため。

3.2 幅が足りないときの詰め方

パネルは data-density を full（分類名＋正式名）→ nocaption（分類名を消し、余白を少し詰める）→ short（短い名前）→ tight（パレットの文字も消し、ボタンをタップ領域の下限44pxまで詰める）の順に詰める。 どの段で収まるかは実際にはみ出しているかを測って決める（fitAssistantPanel()）。 ボタンの数はシステムで変わり（共鳴判定とSANチェックは片方しか出ない）、名前の長さも変わるため、 決め打ちの画面幅では合わない。 1280px はタブレットの横向きやノートPCで多い幅なので、ここで正式名のまま収まることを目安にしている。 v1.9.1 時点（ボタン15個）では、エモクロア・CoC とも 1280px で nocaption、768px（タブレット縦）で tight に収まる。 それより狭い画面だけ、最後の手段として横スクロールに任せる。

経緯: 「NPCのセリフ」を足したときに1280pxで13pxはみ出し、パネル・グループ・ボタンの余白を少しずつ削って収めた。 「情報」を足したときは余白では足りなくなったので、正式名を削るより先に分類名を譲る段（nocaption）を挟んだ。 分類名は、ボタンの並びと区切り線である程度読み取れるが、正式名を短くすると何のボタンか分かりにくくなるため。

ボタンを足したら、1280px と 768px の両方で測り直すこと。 v1.9.0 では1280pxだけを確かめていて、768pxでは tight でも902pxになり、横スクロールが出ていた（v1.9.1 で修正）。 tight のボタンの最小幅は、すでにタップ領域の下限44pxまで詰めてある。これ以上ボタンが増えて収まらなくなったら、 余白をさらに削るのではなく、頻度の低い操作をパネルから外す（コマンドパレットからは引き続き使える）ことを検討する。

適用例: 「📘 シナリオ基本情報」（2026-10-05）は、この時点で768pxの残りが14px、1280pxの nocaption でもCoCで残りが27pxしかなかったため、 パネルには置かなかった（panel: false）。シナリオごとに一度書けば済む頻度の低い操作なので、 入口はヘッダーのタイトル欄の隣・コマンドパレット・Alt+B にした（08 §6）。 続く巻末（FAQ・あとがき・権利表記）も同じ理由で、基本情報の隣の「📕 巻末」1つにまとめた（FAQは Alt+A。09 §4）。 ヘッダーに入口を足すときは §3.6 の詰め方に従う。 「🔖 目次を挿入」（2026-10-05）も、シナリオに1回書けば済む操作なので、パネルには置かずコマンドパレットからだけ使える形にした（既定のキーも付けていない）。

パネルの高さを固定してはいけない。 横スクロールバーが出ると、その分だけボタンが潰れる。固定していたときは41pxまで縮み、 タップ領域の下限44px（01 要件定義書 §5）を割っていた。 ボタン側に min-height: 44px を持たせ、パネルは中身に合わせて伸びるようにしてある。 同じ理由で、ボタンとグループは flex-shrink: 0 にしてある（縮むと名前がボタンの外へはみ出して重なる）。

3.3 吹き出しをパネルの外に置く理由

パネルは横スクロールのために overflow を指定している。 その中に吹き出しを置くと、パネルより上へ出る部分が切り取られる。 そのため body 直下に #panel-tip を1つだけ置き、ボタンの位置を測って重ねている。 吹き出しはマウスのときだけ出す。タッチで出すと、指を離した後も残って邪魔になる。

3.4 ボタンは mousedown で実行する

クリックで実行すると、押した瞬間にボタンへフォーカスが移り、本文の選択範囲が外れる。 文字色のように「選んだ文字を囲む」操作が成り立たなくなるので、 mousedown で既定動作を止めてから実行している。 Tabキーで移ってきて Enter / Space を押した場合は mousedown が起きないので、 click のうちキーボード由来のもの（detail === 0）だけを別に拾う。

3.5 却下した案

案却下した理由
ボタンを2段に折り返す 本文の高さが削られる。タブレットで画面キーボードを出したときに特に厳しい。
分類ごとのドロップダウンにまとめる 最も頻繁に使う挿入が、毎回1タップ増える。
エディタ横のアイコンだけの縦帯 絵文字だけでは意味が伝わりにくい（🗺 が「場面図を挿入」と「場面図への切り替え」で重複している）。本文の横幅も削る。

3.6 ヘッダーも測って詰める（2026-10-05 追加）

ヘッダーにも入口（📘 基本情報・📕 巻末）を置いたので、パネルと同じ問題が起きた。 当初は画面幅のブレークポイント（1400px・1100px・900px）で名前を消していたが、FAQを足した時点で 1101〜1250pxの間だけ収まらなくなった。収まるかどうかはシステム名の長さ（「エモクロア」と「CoC 6版」）やボタンの数でも変わるため、 決め打ちの画面幅では追いつかない。そこで fitHeader() が実際に測り、次の順に1段ずつ詰める。

段詰めるもの
header-compact-1「ショートカット設定」の名前（名前が最も長く、使う頻度は最も低い。コマンドパレットからも開ける）
header-compact-2「執筆／場面図」「基本情報／巻末」の名前
header-compact-3「保存」「PDF出力」の名前と、ボタン・ヘッダーの余白
header-compact-4「一覧」の文字。それでも収まらない画面（768px未満）では、左側を横スクロールにする
  • はみ出しはヘッダー全体ではなく .header-left の中で測る。 左側は縮めるために min-width: 0 を持つので、収まらなくてもヘッダーの幅は変わらず、右側のボタンの下に潜り込むだけになる。 ヘッダー全体の scrollWidth で測ると、重なっていても「収まっている」と判定される（実際にこれで768pxの重なりを見落とした）。
  • 幅が足りないとき最初に縮むのはタイトル欄である（下限100px）。収まっていても、タイトル欄が170px（全角10文字ほど）を切るなら次の段へ進む。 この値は、1280pxでエモクロア・CoCとも「執筆／場面図」「基本情報／巻末」の名前を残せるように決めた。
  • 保存状態の表示は2行まで折り返し、幅は固定する（中身の長さでヘッダーの収まり方が変わらないように）。 header-compact-3 以降はこれも縮み、収まらない行は隠れる。
  • 測り直すのは、ヘッダーの大きさが変わったとき（ResizeObserver）・Webフォントが届いたとき・システムを切り替えたとき。
ヘッダーに要素を足したら、1280px と 768px で、エモクロアとCoCの両方を測ること。 見るのは「左側の最後の要素の右端」と「右側のボタンの左端」の間が0以上あるかと、どの段になったか。 1280pxで header-compact-2 以降になったら、名前が消えて入口が分かりにくくなっていないかを確かめる。

4. コマンドパレット

Ctrl+K（既定）または パネル末尾の「🔎 すべての操作」で開く。 操作を名前で絞り込み、Enter で実行する。パネルに無い操作（保存・PDF出力・シナリオ一覧・ショートカット設定など）も含む。

狙いは、ショートカットを覚えていない人と、覚えた人の間をつなぐことである。 キーボードから手を離さずに済み、候補の横にその操作のキーが出るので、使ううちにキーを覚えられる。 記法がいくつ増えても、パネルのように幅で破綻しない。

4.1 絞り込みの規則

  • 検索語と候補の両方を、カタカナ→ひらがな、全角英数→半角、大文字→小文字に揃えてから比べる（normalizeForSearch()）。
  • keywords に読みをひらがなで持つ。日本語入力は変換前の文字でも入力欄の値が変わるので、 「はんてい」と打った時点で「技能判定」「共鳴判定」が残る。
  • 空白で区切ると、すべての語を含むものに絞る。名前・読みの頭から一致するものを先に並べる。
  • 未入力のときは分類ごとに見出しを付けて全件を出す。何ができるかを一覧する画面を兼ねる。
日本語入力の変換中の Enter・矢印キーは拾わない（isComposing を見る）。 拾うと、変換を確定したつもりの Enter で候補が実行されてしまう。 NPCの技能欄など、ほかの入力欄と同じ扱いである。

4.2 モーダルの仕組みに載せた理由

パレットは .modal として作っている。 × ボタン・背景クリック・Esc で閉じる処理（01 要件定義書 §2.6）と、 開いている間ほかのショートカットを止める処理を、既存のモーダルとそのまま共用できるため。 候補を実行するときは先にパレットを閉じてから実行する。 開いたままだと、実行した操作が開くモーダル（技能判定など）と重なる。

4.3 却下した案

案却下した理由
行頭で / を打つと候補が出る（スラッシュメニュー） 日本語入力がオンのとき、/ キーは「・」になる。 「・」で反応させると、行頭に箇条書きの「・」を打つたびにメニューが開く。 「/」だけに反応させると、日本語で書いている大半の時間は使えない。
パレットの候補を「最近使った順」に並べる 並びが毎回変わると、矢印キーの回数で覚えた操作が使えなくなる。まずは固定の並びで出した（§7）。

5. いつ受け付けるか

キー操作とパレットは、同じ判定（canRunAction()）で受け付けるかを決める。 片方だけ緩いと、「キーでは止まるがパレットからは本文が書き換わる」ずれが生まれるため。

状況受け付けるもの理由
そのシステムに無い操作 なし（available） 入口を出さないのと同じ扱いにする。記法そのものは常にパースする（04 記法設計書 §6）
モーダル表示中 保存だけ（inModal） 誤爆を防ぐ。保存が効かないほうが驚かれる
場面図の表示中 保存・画面の切り替え・パレット・シナリオ一覧・PDF出力・ショートカット設定（inSceneMode） 本文を書き換える操作を止める。隠れた本文に記法が入っても気づけない（06 場面ツリー設計書 §6.1）

同じキーに複数の操作が割り当たっている場合（旧版のデータなど）は、受け付けない操作を飛ばして、受け付ける操作に譲る。

6. 操作を足すときに触る場所

  • ACTIONS に1行足す（パネル・パレット・設定画面・キー操作はここから自動で作られる）
  • 既定のキーを付けるなら、既存の割り当てと重ならないか確かめる（§2.1 の補い方は、既存利用者の重複しか避けない）
  • システム固有なら available を書く（GAME_SYSTEMS のフラグを見る）
  • 本文を書き換えない操作なら inSceneMode: true を付ける
  • 実行の前に何かを選ぶ必要がある操作（どのNPCの発言か、など）は、run で選ぶ画面を開く形にする。 ACTIONS は引数を取れないため。選ぶ画面はコマンドパレットの見た目に揃え、 ↑↓・Enter・クリックの処理は bindChooserList() を使う（例: npc-speech → openSpeechModal()）
  • パネルにボタンが増えるなら、1280px（正式名のまま収まるか）と768px（tight で収まるか）の両方を、エモクロアとCoCで確かめる（§3.2。片方だけ見て見落とした実例がある）
  • 記法を挿入する操作なら、記法側の変換も要る（04 記法設計書 §7）
既存の操作の id を変えないこと。 id はショートカット設定の保存キーなので、変えると利用者が割り当てたキーが黙って失われる。 保存の操作が今も cloud-save という名前なのはこのためである（クラウド保存は2026-08-31に撤去済み）。
