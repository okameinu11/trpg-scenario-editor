開発計画・設計書

本エディタの技術構成、データベース設計、API設計、および段階的な開発スケジュールを定める。実装に着手する前に、対象フェーズの節を読むこと。

1. 技術スタック

個人利用として手軽に運用でき、かつAndroidタブレットで高速に動作するWebアプリを実現するため、 以下の技術を採用する。

レイヤー技術／サービス役割
フロントエンド HTML5, CSS3, Vanilla JavaScript (ES6) UIレイアウト、Markdownパース、エディタ制御、LocalStorage自動保存、印刷スタイル設定
バックエンド Google Apps Script (GAS) APIサーバー（doGet / doPost によるJSONデータ送受信）
データベース Google スプレッドシート シナリオ本文およびNPCデータの保存用データベース
ホスティング GAS ウェブアプリ (HTML Service) アプリケーション全体の配信（Googleのクラウド環境で直接実行）
移行後はフロントエンドの行だけが残る。バックエンドとデータベースは無くなり、 ホスティングは GitHub Pages（静的配信）になる。 「フレームワーク・ビルドツールを使わない単一ファイル構成」という方針自体は変わらない。

2. データベース・スプレッドシート設計

1つのGoogleスプレッドシート内に以下の2つのシートを用意し、 シナリオデータとNPCデータをリレーショナルに管理する。

2.1 scenarios シート（シナリオデータ）

各シナリオの基本情報と、Markdown形式の本文を保存する。

カラム名型説明
id文字列 (UUID)シナリオを一意に特定するID（主キー）
title文字列シナリオのタイトル
content文字列 (TEXT)Markdown形式のシナリオ本文
created_at日時シナリオ作成日時
updated_at日時最終保存日時

2.2 npcs シート（NPCデータ）

シナリオに紐づくNPCのステータス情報などを保存する。

カラム名型説明
id文字列 (UUID)NPCを一意に特定するID（主キー）
scenario_id文字列 (UUID)紐づくシナリオのID（外部キー）
name文字列NPC名
avatar_url文字列立ち絵などの画像URL
status_json文字列 (JSON)能力値やステータス（HP/MP/共鳴度/技能）のJSONデータ
memo文字列 (TEXT)NPCのプロフィールやセリフ例などの自由メモ
created_at日時NPC作成日時
updated_at日時最終更新日時
この設計に起因する既知の不具合がある。 スプレッドシート側のカラム名は status_json だが、フロントエンドの API.saveScenario() は localStorage 経路で status（オブジェクト）というキーで保存する。 一方 selectScenario() は読み込み時に statusJson を読もうとするため、 localStorage経路ではNPCの能力値が復元されない。 保存層に手を入れる際に必ず併せて直すこと。

3. アプリケーション設計

3.1 GASバックエンド (API) 設計

Webアプリとスプレッドシートを繋ぐAPIを実装する。 全て ContentService を利用してJSON形式でクライアントとやり取りする。

エンドポイント定義

  • doGet(e) — 画面初期表示用のHTMLファイルを返却する（WebアプリとしてのURL）。
    • action=listScenarios — 保存されているシナリオのIDとタイトルの一覧を取得。
    • action=loadScenario&id={id} — 指定されたIDのシナリオ本文および関連するNPCリストを取得。
  • doPost(e) — クライアントからのデータ保存および削除リクエストを処理する。
    • action=saveScenario — シナリオ本文およびNPCデータをスプレッドシートに保存（存在すれば更新、なければ新規追加）。
    • action=deleteScenario&id={id} — 指定されたIDのシナリオとNPCデータをスプレッドシートから物理削除。
実装は Code.gs にある。ただし実際の実装は上記の action パラメータ方式ではなく、 google.script.run による関数直接呼び出しになっている（設計と実装のずれ）。 いずれにせよ撤去対象のため、このずれを解消する作業は不要。

3.2 フロントエンド・アーキテクチャ

  • Markdownパーサの自作
    • 重い外部ライブラリを避けるため、正規表現を用いた軽量なカスタムMarkdownパーサをJavaScriptで記述する。
    • 改行コードや >> の位置に基づいて段落を切り分け、左右のカラム（row クラス）に自動でマッピングして出力する。
  • LocalStorage同期
    • 入力エリアへの input イベントを検知し、数秒間入力が止まった段階（デバウンス処理）で現在データをキャッシュする。
  • PDF出力制御
    • window.print() 実行時に、ナビゲーションや編集UIを display: none にし、印刷用レイアウトを有効化する。
この節は移行後も有効である。 外部ライブラリを持たない自作パーサという判断が、GitHub Pages への静的配信をそのまま可能にしている。 ビルド工程が無いため、index.html を置くだけで動く。

4. 開発ロードマップ（フェーズ分け）

Androidタブレットでの実用性を確認しながら進められるよう、段階的に開発を行う。

フェーズ1 — エディタの基本機能 ＆ プレビュー・PDF化の実装

目標: まずはスタンドアロンで動くエディタを作り、Markdown入力から美しいプレビュー、PDF出力ができる状態を作る。

  • HTML/CSS/JSによるエディタ＋プレビュー画面の実装。
  • 2カラムレイアウト（段落ごとの >> 紐付け）のパース処理実装。
  • 印刷用CSSの作成とPDF出力テスト。

フェーズ2 — GAS・スプレッドシート連携 ＆ シナリオ管理

目標: GAS上でWebアプリを公開し、スプレッドシートとの保存・読込・一覧管理機能を実現する。

  • GASのセットアップと、スプレッドシートの作成。
  • scenarios シートの保存・読込用APIの実装。
  • クラウド保存ボタン、シナリオ一覧切り替え画面の実装。
  • LocalStorage自動保存とクラウド保存のデータ調停処理。

フェーズ3 — エモクロアTRPG専用の入力支援 ＆ アシスタントパネル

目標: タッチ操作支援パネルと、エモクロアに特化した判定・共鳴の入力支援機能を実装する。

  • 執筆アシスタントパネルUIの実装。
  • 各種Markdown記法の一発挿入機能。
  • エモクロア標準技能（リスト選択）や共鳴判定ダイアログの実装。
  • 判定ブロックのカラーバッジ（ミラクル〜カタストロフィ）の自動レンダリング実装。

フェーズ4 — NPC管理機能の実装

目標: シナリオと連動したNPCシートの登録・管理機能を追加する。

  • npcs シートの保存・読込用APIの実装。
  • エディタ画面と切り替え可能な「NPC管理」タブ、またはモーダルUIの作成。
  • NPCのステータス・技能・画像登録フォームの実装。

フェーズ5 — 最終調整 ＆ タブレット実機でのUX最適化

目標: Androidタブレットでの動作をチェックし、タップしやすさ、フォントの綺麗さ、動作の軽さを磨き上げる。

  • タブレットの仮想キーボード出現時のレイアウト崩れ対策。
  • 印刷設定（A4・余白なし等）でのPDFレイアウトの最終確認。
  • 各種不具合の修正とコードクリーンアップ。

フェーズ6 — GAS脱却とGitHub Pagesでの公開（2026-08-31 追加）

目標: バックエンドを撤去して静的アプリ化し、別端末からも使える状態にする。

  • API オブジェクトから isGas 判定と google.script.run の分岐を撤去する。
  • NPCの status / statusJson のキー不整合を修正する（§2.2 の既知不具合）。
  • シナリオデータのJSONエクスポート／インポート機能を追加し、端末間の持ち運び手段とする。
  • localStorage の容量超過（QuotaExceededError）を検知して利用者に伝える。
  • GitHub Pages（publicリポジトリ）で公開する。公開範囲は事前に確認すること。
