TRPG SCENARIO EDITOR / 設計

開発計画・設計書

本エディタの技術構成、データベース設計、API設計、および段階的な開発スケジュールを定める。実装に着手する前に、対象フェーズの節を読むこと。

2026-08-31: フェーズ6（GAS脱却）を完了した。 バックエンドとスプレッドシートは撤去済みで、アプリは index.html 1枚の静的Webアプリになっている。 §2 と §3.1 は撤去された旧構成の記録として残してあり、現行の実装ではない。 §3.2 のフロントエンド設計は引き続き有効。

1. 技術スタック

個人利用として手軽に運用でき、かつAndroidタブレットで高速に動作するWebアプリを実現するため、 以下の技術を採用する。

レイヤー技術／サービス役割
フロントエンド HTML5, CSS3, Vanilla JavaScript (ES6) UIレイアウト、Markdownパース、エディタ制御、LocalStorage自動保存、印刷スタイル設定
バックエンド なし サーバー処理を持たない。2026-08-31 に Google Apps Script を撤去した。
データの保存先 ブラウザの localStorage シナリオ本文およびNPCデータ。端末間の移動はJSONの書き出し／読み込みで行う。
ホスティング GitHub Pages 静的ファイルの配信のみ。ビルド工程は無く、index.html を置くだけで動く。
実質的にフロントエンドの行だけが本体である。 「フレームワーク・ビルドツールを使わない単一ファイル構成」という当初の方針は、 GAS脱却後もそのまま維持されている。むしろサーバーが無くなったことで、 index.html をダブルクリックするだけでも動くようになった。

2. データベース・スプレッドシート設計（撤去済み・記録）

この節は 2026-08-31 に撤去された旧構成の記録である。現行の実装ではない。 1つのGoogleスプレッドシート内に以下の2つのシートを用意し、 シナリオデータとNPCデータをリレーショナルに管理していた。

2.1 scenarios シート（シナリオデータ）

各シナリオの基本情報と、Markdown形式の本文を保存する。

カラム名型説明
id文字列 (UUID)シナリオを一意に特定するID（主キー）
title文字列シナリオのタイトル
content文字列 (TEXT)Markdown形式のシナリオ本文
created_at日時シナリオ作成日時
updated_at日時最終保存日時

2.2 npcs シート（NPCデータ）

シナリオに紐づくNPCのステータス情報などを保存する。

カラム名型説明
id文字列 (UUID)NPCを一意に特定するID（主キー）
scenario_id文字列 (UUID)紐づくシナリオのID（外部キー）
name文字列NPC名
avatar_url文字列立ち絵などの画像URL
status_json文字列 (JSON)能力値やステータス（HP/MP/共鳴度/技能）のJSONデータ
memo文字列 (TEXT)NPCのプロフィールやセリフ例などの自由メモ
created_at日時NPC作成日時
updated_at日時最終更新日時
この設計に起因していた不具合は 2026-08-31 に修正済み。 スプレッドシート側のカラム名が status_json であったのに対し、 localStorage 経路の保存は status（オブジェクト）というキーを使っており、 読み込み側の selectScenario() は statusJson を読もうとしていた。 キーが食い違うため、シナリオを読み直すとNPCの能力値が失われていた。

現在は normalizeNpc() が両方の形式を受け付けて status に正規化する。 旧GAS版から書き出したデータや、外部で作られたJSONを読み込んでも能力値が保持される。

3. アプリケーション設計

3.1 GASバックエンド (API) 設計（撤去済み・記録）

この節は撤去された旧構成の記録である。 Webアプリとスプレッドシートを繋ぐAPIを実装し、 ContentService を利用してJSON形式でクライアントとやり取りしていた。

エンドポイント定義

  • doGet(e) — 画面初期表示用のHTMLファイルを返却する（WebアプリとしてのURL）。
    • action=listScenarios — 保存されているシナリオのIDとタイトルの一覧を取得。
    • action=loadScenario&id={id} — 指定されたIDのシナリオ本文および関連するNPCリストを取得。
  • doPost(e) — クライアントからのデータ保存および削除リクエストを処理する。
    • action=saveScenario — シナリオ本文およびNPCデータをスプレッドシートに保存（存在すれば更新、なければ新規追加）。
    • action=deleteScenario&id={id} — 指定されたIDのシナリオとNPCデータをスプレッドシートから物理削除。
実装は Code.gs にあった。実際には上記の action パラメータ方式ではなく、 google.script.run による関数直接呼び出しになっており、設計と実装がずれていた。 2026-08-31 に index.html 側の呼び出しを撤去したため、 Code.gs はどこからも使われていない。

3.2 フロントエンド・アーキテクチャ

  • Markdownパーサの自作
    • 重い外部ライブラリを避けるため、正規表現を用いた軽量なカスタムMarkdownパーサをJavaScriptで記述する。
    • 改行コードや >> の位置に基づいて段落を切り分け、左右のカラム（row クラス）に自動でマッピングして出力する。
  • LocalStorage同期
    • 入力エリアへの input イベントを検知し、数秒間入力が止まった段階（デバウンス処理）で現在データをキャッシュする。
  • PDF出力制御
    • window.print() 実行時に、ナビゲーションや編集UIを display: none にし、印刷用レイアウトを有効化する。
この節は移行後も有効である。 外部ライブラリを持たない自作パーサという判断が、GitHub Pages への静的配信をそのまま可能にしている。 ビルド工程が無いため、index.html を置くだけで動く。

3.2.1 ゲームシステムの抽象化（2026-09-01 追記）

複数のTRPGシステムに対応するため、システムごとに違うものを GAME_SYSTEMS という1つの定義オブジェクトに集約している。 画面側はこの定義だけを見て描画し、システム名で分岐しない。

定義項目内容使う場所
abilities能力値のキーと表示名、入力の上下限NPC編集の能力値欄
derived派生値の定義（HP・SAN等）NPC編集の派生値欄
autoCalc派生値の計算式と、その元になる能力値recalcDerived()
skills分類ごとの技能一覧技能判定モーダル
rollTiers判定ブロックの成功段階renderRollTiers()
badgesキーワードとバッジ色の対応getBadgeInfo()
hasEmotions / hasResonanceRollエモクロア固有機能の有無NPC編集・下部パネル
DO

システム固有の値が必要になったら GAME_SYSTEMS に項目を足し、 描画側は currentSystem() 経由で読む。 画面を切り替える処理は applySystemToUI() に集約する （シナリオの新規作成・読み込み・起動時の3箇所から呼ばれる）。

DON'T

if (currentSystemId === 'coc6') のような分岐を描画コードに書く。 システムが3つ目に増えたときに、分岐を書いた場所を全部探し直すことになる。

エモクロアの abilities は公式ルールと一部食い違っている。 公式の8能力値は「身体／器用／精神／五感／知力／魅力／社会/運勢」だが、 実装は「身体／敏捷／器用／精神／五感／知性／魅力／社会」で、 運勢が無く、代わりに敏捷がある。 既に保存されているNPCデータのキーがこの形なので、揃えると既存の能力値が失われる。 修正する場合はデータ移行とセットで行うこと。

同様に、エモクロアのHP/MP自動計算は実装が「身体×2／精神×2」で、 公式ルール（HP=身体+10、MP=精神+知力）と異なる。 これも既存NPCの数値に影響するため、判断を保留して現状を維持している。

3.2.2 レイアウトが崩れる定番の原因（2026-08-31 追記）

入力値の長さによって表示が崩れる不具合が複数見つかり、原因はいずれも次の2つだった。 新しくフォームや一覧を追加するときは、最初からこの2点を入れておくこと。

DO

flex／grid の子に min-width: 0 を指定する。 既定の min-width: auto は「中身の最小幅より縮まない」という意味なので、 入力欄を含む子は親を突き破って画面外へ出る。

利用者が入力した文字列を表示する場所には overflow-wrap: anywhere を指定する。 URLのような区切りの無い文字列は既定では折り返されない。

DON'T

flex: 1 だけ書いて縮むと思い込む。 幅を % で指定して box-sizing: border-box を忘れる （padding のぶんだけ親からはみ出す）。

利用者の入力をHTMLに埋め込むときは、必ず escapeHTML() を通すこと。 NPCカードのメモ欄だけエスケープが漏れており、HP<5で逃走 のような ごく普通の記述で文字が消え、<b> はタグとして解釈されて要素が生成されていた （2026-08-31 修正）。 改行を <br> に変換する場合はエスケープしてから変換する。 順序が逆だと <br> 自体が無効化される。

4. 開発ロードマップ（フェーズ分け）

Androidタブレットでの実用性を確認しながら進められるよう、段階的に開発を行う。

フェーズ1 — エディタの基本機能 ＆ プレビュー・PDF化の実装

目標: まずはスタンドアロンで動くエディタを作り、Markdown入力から美しいプレビュー、PDF出力ができる状態を作る。

  • HTML/CSS/JSによるエディタ＋プレビュー画面の実装。
  • 2カラムレイアウト（段落ごとの >> 紐付け）のパース処理実装。
  • 印刷用CSSの作成とPDF出力テスト。

フェーズ2 — GAS・スプレッドシート連携 ＆ シナリオ管理

目標: GAS上でWebアプリを公開し、スプレッドシートとの保存・読込・一覧管理機能を実現する。

  • GASのセットアップと、スプレッドシートの作成。
  • scenarios シートの保存・読込用APIの実装。
  • クラウド保存ボタン、シナリオ一覧切り替え画面の実装。
  • LocalStorage自動保存とクラウド保存のデータ調停処理。

フェーズ3 — エモクロアTRPG専用の入力支援 ＆ アシスタントパネル

目標: タッチ操作支援パネルと、エモクロアに特化した判定・共鳴の入力支援機能を実装する。

  • 執筆アシスタントパネルUIの実装。
  • 各種Markdown記法の一発挿入機能。
  • エモクロア標準技能（リスト選択）や共鳴判定ダイアログの実装。
  • 判定ブロックのカラーバッジ（ミラクル〜カタストロフィ）の自動レンダリング実装。

フェーズ4 — NPC管理機能の実装

目標: シナリオと連動したNPCシートの登録・管理機能を追加する。

  • npcs シートの保存・読込用APIの実装。
  • エディタ画面と切り替え可能な「NPC管理」タブ、またはモーダルUIの作成。
  • NPCのステータス・技能・画像登録フォームの実装。

フェーズ5 — 最終調整 ＆ タブレット実機でのUX最適化

目標: Androidタブレットでの動作をチェックし、タップしやすさ、フォントの綺麗さ、動作の軽さを磨き上げる。

  • タブレットの仮想キーボード出現時のレイアウト崩れ対策。
  • 印刷設定（A4・余白なし等）でのPDFレイアウトの最終確認。
  • 各種不具合の修正とコードクリーンアップ。

フェーズ6 — GAS脱却とGitHub Pagesでの公開（2026-08-31 追加）

目標: バックエンドを撤去して静的アプリ化し、別端末からも使える状態にする。

  • ✅ API から isGas 判定と google.script.run の分岐を撤去する
  • ✅ NPCの status / statusJson のキー不整合を修正する（normalizeNpc() が両形式に対応）
  • ✅ シナリオデータのJSON書き出し／読み込み機能を追加する（全件・単体の書き出しとマージ読み込み）
  • ✅ localStorage の容量超過を検知して利用者に伝える（writeStore() で QuotaExceededError を捕捉）
  • ⬜ GitHub Pages（publicリポジトリ）で公開する — 未着手
移行時に併せて直したもの。 明示保存の完了メッセージが、直後に走る自動保存の表示に上書きされ、 保存できたかどうかが利用者に伝わっていなかった。呼び出し順を入れ替えて修正した。

また旧保存キー trpg_mock_db_scenarios から trpg_db_scenarios へ 自動移行する処理を入れてある。GAS併用時代のローカルデータが失われることはない。
Googleスプレッドシート側に残っているデータは自動では移らない。 GAS版で保存したシナリオがスプレッドシートにある場合、アプリからは読めなくなっている。 必要であればスプレッドシートから本文を手作業で取り出すこと。
