プレビュー連携設計書

本文とプレビューの並べ方（片方を隠す・境界を動かす）、プレビューから原文へ戻る仕組み （ダブルクリックで飛ぶ・その場で原文を書き換える小窓）、左右のスクロールの連動を、なぜその形にしたかとともに残す。 プレビューの描き方（parseMarkdown()）を変えるとき・本文を書き換える処理を足すときに読むこと。

1. 守備範囲

2026-10-07 に、利用者から次の2つの困りごとが挙がった。

  • プレビューを大きく見たいのに、本文と半々に並んだまま変えられない。
  • プレビューに出ている文章が、本文のどこに書いたものかを探すのが大変。プレビューの側から直せるとなおよい。

これに対して、3つを順に入れた。

2. 本文とプレビューの並べ方

2.1 3つの表示と境界

表示body[data-layout]入口
並べる（既定）both境界をドラッグして本文の幅を 20〜80% の間で変える。ダブルクリックで半々に戻す。フォーカスして矢印キーでも動く
プレビューだけpreview境界の ◀（縦画面では ▼）、コマンドパレットの「プレビューを広げる」、Alt+P（もう一度で戻る）
本文だけeditor境界の ▶（縦画面では ▲）、コマンドパレットの「本文を広げる」（既定のキーは無し）

境界のボタンは「境界をその向きへ1段動かす」意味で、preview ⇄ both ⇄ editor の順に移る。 片方を隠しているあいだ、境界はボタン1つ分の帯になり、戻す向きのボタンだけが残る。 表示と幅の割合は この端末の設定として localStorage の trpg_layout に持つ （{ mode, ratio, sync }。sync はスクロールの連動の入切で §5。03 保存方式設計書 の設定の行）。 シナリオのデータではないので、書き出したJSONには入らない。

2.2 隠し方は display: none

採った

隠す側を display: none にする。フォーカスを受け取れないので、隠れた本文に文字が入ることが構造上起きない。

却下

本文の欄を幅0にして残す。本文の書き換えが取り消しの記録に残る利点はあるが、モーダルを閉じたときなどに editor.focus()（12か所ある）で見えない本文へフォーカスが戻り、打った文字やスペースが見えないまま本文に入る。

display: none にするとスクロールの位置が捨てられるので、隠す前に覚えておき、出したときに戻す（paneScroll）。 取り消しの記録を残す必要がある書き換え（原文の小窓の確定）だけは、書き換える一瞬だけ欄を画面の外に出す（§4.3）。

2.3 紙面の幅に上限を付ける

プレビューだけを表示すると、紙面が画面の幅いっぱいに広がり、1行が長すぎて読みにくい。 .preview-paper に max-width: 1080px を付けて中央に置く。並べる表示でも、広い画面ではこの上限が効く。 印刷では上限を外す（用紙の幅いっぱいに組むため）。

2.4 入口を境界に置いた理由

  • ヘッダーと下部パネルは、すでに幅が尽きている（07 §3.2・§3.6）。
  • プレビューは台本の紙面を見る場所で、操作のボタンを置かない（08 §6）。紙面の上に浮かぶボタンも同じ理由で採らなかった。
  • 境界は、本文とプレビューの両方に関わる操作の置き場所として意味が通る。ドラッグできることも、そこに目が行けば分かる。

ボタンは境界の高さの真ん中に置き、プレビュー側の余白（40px）へはみ出させる。 本文側へはみ出すと、本文の欄のスクロールバーに重なる。タッチでは押す場所の下限 44px を守る （01 §5。境界の帯も広げ、はみ出しを余白の中に収める）。

2.5 隠れている側を使う操作

3. プレビューから原文へ

3.1 プレビューの要素に原文での範囲を書き込む

parseMarkdown() は本文を空行で区切った段落ごとに描いている。区切るときに原文での位置も持ち（splitSourceBlocks()）、 描いた要素に書き込む。区切り方は以前の split(/\n{2,}/) と同じで、同じ段落が同じ順に並ぶ。

属性中身付ける要素
data-src段落全体の範囲 開始-終了（本文での文字の位置）。原文の小窓で書き換える単位見出し・目次・場面図・段組みの本文の段（.main-content）・右の段の各要素
data-part>> で分かれる段落の、その段だけの範囲。クリックした文字を探す範囲を絞る>> を含む段落の本文の段・右の段
data-origin（＋ -id / -field）本文の外で書いたものの出どころ（npc / info / cover / faq / bm / rights）NPCカード・情報・表紙・FAQの行・あとがきなどの見出しと本文・権利表記
右の段の要素は、包む要素を足さずに先頭のタグへ属性を書き足す（withSrcAttrs()）。 包むと .side-content > * + * のような子の並びを見るCSSが崩れる。 parseMarkdown() に新しい全幅のブロックや段の作り方を足すときは、その要素にも data-src を付けること。付け忘れると、その部分はダブルクリックしても何も起きない。

3.2 段落の中の位置は推し量る

プレビューの文字は記法を外して組み直したものなので、クリックした文字の原文での位置は計算では引けない。 クリックした所の前後の数文字（10文字ずつ → 5文字ずつ → 後ろ6文字 → 前6文字 → 3文字）を原文の範囲から探し、 1か所にだけ見つかったものを採る（locateClickInSource()）。

クリックした所着く場所
地の文・情景描写・セリフ・備考・判定の結果の文・TIPS・文字色を付けた文その文字（色の記法 {赤:…} を挟んでも、記法の内側の文字で探すので合う）
同じ言い回しが同じ段落に2回以上ある最初に見つかった所（長い手がかりで1か所に決まらないとき）
記法から組み立てた文字（「🎲 判定：」「探索可能箇所：」など）その段（または段落）の先頭

外れても段落の先頭に着くだけで、本文は変わらない。完全に合わせることより、外れたときに害が無いことを優先した。

3.3 ダブルクリックにした理由

  • 1回のクリックは、プレビューの文章を選んでコピーするのと、目次のリンクに使われている。
  • VS Code の Markdown プレビューや Overleaf（PDFからソースへ）もダブルクリックで同じことをしており、知っている人がいる。
  • タブレットではダブルタップになる。Android の Chrome は width=device-width のページでダブルタップによる拡大をしないので、ダブルタップがダブルクリックとして届く想定である（2026-10-07 時点で実機では未確認。PCのブラウザの自動操作でのみ確かめた）。

マウスのときは、ダブルクリックで開ける範囲に薄い点線の枠を出す（入れ子では一番内側だけ）。 ボタン・リンク・入力欄の上のダブルクリックは、それぞれ本来の動きに任せる。

3.4 本文の外で書いたものは、書いた画面を開く

プレビューの要素開く先
NPCカード（大・小）NPC管理で、そのNPCを選んだ状態
情報（[情報:題名] で出したもの）情報一覧で、その情報を編集する状態
表紙シナリオ基本情報
FAQの質問・回答巻末の FAQ タブで、その欄にフォーカス
あとがきなどの見出し・本文、権利表記巻末のあとがきタブで、その欄にフォーカス

NPCのセリフは本文に書いたものなので、本文へ飛ぶ（アイコンと名前はNPCのデータから描いているが、[セリフ:名前] は本文にある）。 未登録のNPC・情報の警告も本文へ飛ぶ（直す場所は本文の記法だから）。

3.5 打った直後のダブルクリック

プレビューは打つ手が止まって 500ms 後に描き直すので、その前にダブルクリックされると data-src が古い本文での位置になっている。 最後に描いた本文（previewRenderedText）と今の本文が違えば、先に描き直し、同じ座標の要素を引き直してから使う。

3.6 飛んだ先の示し方

採った

カーソルだけを置き、段落の上に帯を重ねて一瞬光らせる（flashEditorRange()）。textarea の中の文字には色を付けられないので、同じ字送りの隠し要素で位置を測って帯を重ねる。

却下

段落全体を選択して示す。目立つが、そのまま文字を打つと段落がまるごと置き換わる。

4. 原文の小窓

4.1 プレビューを直接書き換える形（WYSIWYG）にしなかった理由

プレビューは記法から組み立てたもので、原文と1対1に対応していない（判定ブロック・NPCカード・文字色・段組み）。 プレビューの上で書き換えた結果を本文に戻すには、HTMLを記法に戻す変換が要る。 この変換が不完全だと原文を壊し、しかも「見た目は直ったのに原文が別物になっている」形で起きるので気づけない。

代わりに、ダブルクリックした段落の原文の文字列そのものを、段落のすぐ下に開いた入力欄で書き換える。 確定すると、本文のその範囲を差し替えるだけなので、記法に戻す変換は要らない。

4.2 プレビューだけの表示でだけ開く

並べる表示では、本文へ飛べば同じことができる（§3）。小窓が要るのは、本文の欄が隠れていて飛ぶ先が無いときだけなので、 ダブルクリックの動きを表示で分けた。小窓の「本文で開く」は、書き換えを確定して並べる表示に戻し、本文の欄のその位置へ移る。

4.3 取り消しの記録に残す

確定は editEditorRange() を通す（10 §2）。 ただしプレビューだけの表示では本文の欄が display: none で、フォーカスできず insertText が効かない。 そのままだと値の代入になり、ブラウザの取り消しの記録が捨てられる（並べる表示に戻したあと、本文の中の Ctrl+Z が効かなくなる）。 そこで、書き換える一瞬だけ body.editor-offstage で欄を画面の外（left: -10000px）に出し、 書き換えてフォーカスを外し、隠し直す。この間に描画は挟まらないので、画面には現れない。

Ctrl+Z を押した場所戻るもの
小窓の中小窓の入力（ブラウザ標準）
入力欄の外確定した書き換え（アプリの履歴。確定はボタン・Enter の区切りで記録される）
並べる表示に戻したあとの本文の中確定した書き換え（ブラウザ標準。上の仕組みで記録に残っている）

4.4 開いているあいだの記法の入れ先

下部パネル・ショートカット・判定などのモーダルから記法を入れると、小窓のカーソル位置に入る。 カーソル位置を見て記法を入れる処理は、本文の欄を直接見ずに insertionTarget() を使う （insertAtCursor()・replaceRange()・文字色・NPCのセリフ）。 タブレットで小窓を使うとき、パネルのボタンで記法を入れられないと不便なため。

カーソル位置を見て記法を入れる処理を足すときは、editor.selectionStart / editor.value を直接読まず、 insertionTarget() の欄から読むこと。直接読むと、小窓を開いているあいだに隠れた本文の位置を使って、小窓のほうへ書き込んでしまう。

4.5 開いているあいだの扱い

起きたこと扱い理由
プレビューの描き直し（NPC管理を閉じた・記法を入れた など）しない。頼まれたことを覚えておき、小窓を閉じたときに描く（previewPending）描き直すと小窓ごと消え、書きかけが失われる
表示の切り替え・場面図への切り替え・保存・PDF出力・HTML出力確定してから行う保存・印刷・書き出ししたつもりで小窓の中身だけが残るのを防ぐ
別の段落をダブルクリック書きかけがあれば、開いている小窓を光らせて止める。無ければ閉じて、新しい段落で開く黙って捨てても、黙って確定しても驚かれる
Esc・「取り消す」書き換えていれば確認してから閉じるEsc は打ち間違えやすい
開いたあとで本文が変わった（アプリの元に戻す・情報の題名の変更）開いたときの原文を本文から探し直し、1か所に決まればそこを書き換える。決まらなければ知らせて、小窓は開いたまま残す位置がずれたまま差し替えると、別の段落を壊す
シナリオを開き直した・作った・消した確定せずに捨てる「上書きされますがよろしいですか」の確認を通ってきている

4.6 却下した案

案却下した理由
小窓からフォーカスが外れたら確定する判定などのモーダルを開くとフォーカスが外れる。記法を入れる途中で確定されてしまう
小窓をモーダル（画面の中央）にするプレビューの文脈が隠れる。下部パネルもモーダルの背景に覆われ、記法を入れられない
段落を隠して、その場所に小窓を入れる書き換える前の見た目と見比べられない。右の段だけを書き換えるときの扱いも複雑になる

5. スクロールの連動（2026-10-09 追加）

2026-10-09 に「同じ場所を左右で常に見比べたい」という要望が挙がった。§3 のダブルクリックは、1か所を探すには足りるが、 読み進めながら見比べるには毎回ダブルクリックが要る。そこで、並べる表示（both）のあいだ、 どちらをスクロールしても、もう片方が同じ段落を見せるようにした。

5.1 段落ごとの組で対応をとる

採った

段落ごとに「本文の欄でその段落の頭が上端に来る scrollTop」と「プレビューで同じ段落の頭が上端に来る scrollTop」の組を作り、 組と組のあいだは比例で埋める（buildScrollSyncMap() / mapPaneScroll()）。段落の頭どうしは、どこでもぴったり揃う。

却下

全体の割合（本文の 40% の位置ならプレビューも 40%）で合わせる。本文の1行（[NPC:名前]）がプレビューでは大きなカードになるなど、 高さの比が段落ごとに大きく違うので、長いシナリオの途中で画面1枚分以上ずれる。

  • 目印はプレビューの要素の data-src（§3.1）。同じ段落の要素が複数あれば（段組みの本文の段と右の段）、最初のものの高さを使う。
  • 本文の欄での高さは、§3.6 と同じ隠し要素で測る。段落の数だけ測るので、本文を1回だけ流し込み、段落の頭ごとに目印を挟んで一度に測る（textareaOffsetTops()）。
  • 両方とも先へ進む組だけを使う。空行のあとの >> だけの段落は、プレビューでは前の段落の横（上）に戻るので外れる。外れても、前後の組のあいだの比例で埋まる。
  • 組の表は、本文・描き直しの回数・両方の大きさが変わったときだけ作り直す（スクロールのたびには作らない）。

5.2 表紙と巻末

表紙（基本情報）と巻末（FAQ・あとがき・権利表記）は本文に無い。 本文の先頭はプレビューの本文の始まり（目次など、表紙の後ろ）に、本文の末尾はプレビューの本文の終わり（巻末の前）に合わせる。 表紙・巻末はプレビューを動かしたときだけ見え、そのあいだ本文は端で止まる。

当初は先頭どうし・末尾どうし（スクロールの端どうし）を組にしていた。これだと本文を末尾まで送ったとき、プレビューは巻末まで進み、 本文の最後の場面が画面の外へ出る。シナリオは末尾に場面を書き足していくことが多く、そのとき書いている所がプレビューに見えないので改めた。

5.3 どちらに合わせるか

起きたこと合わせ方理由
利用者がどちらかをスクロールした動かした側に、もう片方を合わせる。次の描画の前にまとめて1回（requestAnimationFrame）スクロールは1フレームに何度も届く
本文に文字を打った本文を基準にする。プレビューが描き直されたら、プレビューを本文に合わせ直す打っているのは本文。描き直しのたびに本文が動くと打てない
打った直後（プレビューがまだ古い）合わせない。描き直したあとに合わせるdata-src が古い本文での位置なので、組がずれる
画面の大きさ・境界の位置が変わった、プレビューの画像が読み込まれた最後に動かした側に、もう片方を合わせ直す（ResizeObserver）高さが変わると、同じ scrollTop でも見えている段落が変わる
片方だけの表示から並べる表示に戻したそれまで見えていた側に合わせる利用者が読んでいたのはそちら
プレビューをダブルクリックして原文へ飛んだ（§3）プレビューを動かさず、本文をプレビューに合わせる。合わせた位置でカーソルが欄に入らないときだけ、従来どおり本文を送るプレビューが動くと、いまダブルクリックした場所を見失う

こちらから動かした側でも scroll は起きる。それを利用者の操作として扱うと、合わせ返して往復が止まらなくなる。 そこで動かした値を覚えておき（syncExpect）、その値の scroll は1回だけ無視する。 時間で区切る（動かしてから数十ms は無視する）形にしなかったのは、そのあいだの利用者の操作まで捨ててしまうため。

5.4 入口と設定

  • 入切の入口は、境界の ◀ と ▶ のあいだの鎖のボタン（入のときは押された色、切のときは鎖に斜線）と、コマンドパレットの「スクロールの連動」（既定のキーは無し）。 本文とプレビューの両方に関わる操作なので、§2.4 と同じ理由で境界に置いた。片方を隠しているあいだは連動しようがないので、ボタンも出さない。
  • 既定は入。入切は trpg_layout の sync に持つ（§2.1）。
  • 場面図の表示中・片方だけの表示・原文の小窓（プレビューだけの表示でしか開かない）では連動しない。

5.5 却下した案

案却下した理由
本文からプレビューへの一方向だけにするプレビューを読み進めながら、本文の該当箇所を見比べたい場面も同じくらいある（要望は「左右で常に比較できる」）
本文のカーソルがある段落へ、プレビューを追従させる読み比べたいのは画面に見えている範囲で、カーソルの位置とは限らない。入力のたびにプレビューが動き、読んでいる場所を見失う
入切を設けず、常に連動する書いている場所と離れた段落（登場人物の一覧など）を開いたまま書きたいことがある

6. 将来拡張の入り口

やりたいこと変える場所
本文のカーソル位置に合わせて、プレビューを追従させる（逆方向） data-src でカーソル位置を含む要素を引き、scrollIntoView()。入力のたびに動くと読んでいる場所を見失うので、カーソルの移動（クリック・矢印キー）でだけ動かすこと。 スクロールの連動（§5）と同時に入れると、どちらに合わせるかがぶつかる。入れるなら連動とは別の入切にし、§5.3 の表に行を足すこと
スクロールの連動を、段落の頭ではなく画面の真ん中で揃える syncScrollFrom() で、両方の scrollTop に欄の高さの半分を足してから表を引き、引いた値から半分を引く。端の扱い（§5.2）も合わせて見直すこと
プレビューの文字を拡大する #preview-area の font-size を設定にし、trpg_layout に倍率を足す。紙面の幅の上限（§2.3）も倍率に合わせる
並べる表示でも小窓を使えるようにする initPreviewToSource() の分岐。設定で選べるようにするなら、ダブルクリックと Alt+ダブルクリックで分けるなど
小窓で書いている内容を、その場でプレビューに出す 小窓の入力ごとに、その段落だけを parseElement() で描いて見せる。ただし段落が分かれた・見出しになったときの扱いを先に決めること
