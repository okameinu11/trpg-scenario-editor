1. このドキュメントの守備範囲

リリースノートは利用者に向けた告知であり、開発の記録ではない。 コミット履歴と違い、書く相手も粒度も違うため、機械的に生成して終わりにはできない。 一方で「毎回どこを直すのか」が残っていないと、版を上げるたびに書き換え漏れが出る。

2. 文面はどこにあるか

同じ文面が2箇所にある。役割が違うので、どちらか片方だけを直すと食い違う。

場所役割区分
release-notes/<版>/<版>.md 文面の原文。/release-notes スキルが生成する。リポジトリを見る人・配布先の告知に流用する 正本
index.html の RELEASE_NOTES アプリが実際に表示する実体。ヘッダーのバージョン表記もここの先頭から描く 必須
なぜ .md を読みに行かないのか。 このアプリは index.html 1枚で配布し、file:// で開いても動くことを前提にしている。 fetch() でリポジトリ内のファイルを読む作りにすると、 ローカルで開いた瞬間に読み込みが失敗し、リリースノートが空になる。 「渡せば即動く」という単一ファイル構成の前提のほうが優先される （理由は CLAUDE.md の「なぜ1枚構成なのか」にある）。
二重管理は放置すると必ず乖離する。 そのため release-notes/ を変更したコミットに index.html が 含まれていない場合、コミットゲート（release-notes-sync）が警告を出す。 ブロックにしていないのは、文面の推敲だけを先にコミットする場合があるため。

3. 版を上げるときの手順

  1. /release-notes v<新しい版> を実行し、release-notes/<版>/<版>.md を生成する。
  2. 生成された文面を §4 の基準で見直す（開発者向けの言い回しが残っていないか）。
  3. index.html の RELEASE_NOTES の先頭に同じ内容を追加する。日付は公開日。
  4. ブラウザで開き、ヘッダーのバージョン表記が新しい版になっていることを確認する。
ヘッダーの数字を直接書き換える場所は無い。 index.html のHTML側には版番号を持たせず、renderVersionTag() が RELEASE_NOTES[0].version から描いている。 以前のように2箇所に数字があると、片方だけ上げた状態が普通に起こるため。
  • release-notes/<版>/<版>.md と RELEASE_NOTES の文面が一致しているか
  • RELEASE_NOTES の先頭が新しい版になっているか（並び順は新しい版が上）
  • 利用者から見て何も変わらない項目が混ざっていないか

4. 何を載せ、何を載せないか

読者はこのエディタを使うGMであって、開発者ではない。 コミット件名をそのまま並べると、内部の整理まで「変わったこと」として並んでしまう。

DO

画面の操作や結果が変わったものだけを、利用者の言葉で書く。
例:「技能判定の結果に複数行の説明を書いたとき、2行目以降が表示されなかった問題を直しました」

DON'T

内部の関数名・保存先の名前・リファクタリングを載せる。
例:「parseRollResultLines() を追加」「ピッカーを共通部品化」
触っても画面が変わらない項目が混ざると、リリースノート全体が読まれなくなる。

迷ったら載せない側に倒す。 実際には変わっていない項目を載せるほうが、載せ漏らすより害が大きい （利用者が探しても見つからず、記述そのものが信用されなくなる）。

5. 過去の版をどう区切ったか

v1.7.0 で閲覧UIを作った時点で、過去の版のリリースノートは存在しなかった。 そこで各コミット時点の index.html のバージョン表記を読み、 表記が変わる直前までのコミット件名をその版の内容として再構成した。

v1.2.1 が最古である。 リポジトリの初回コミットの時点ですでに v1.2.1 と表記されており、 それ以前の変更内容はどこにも残っていない。遡って書き足すことはできないので、 v1.2.1 の項目は「初期リリース以降に分かっている範囲」として扱う。

6. 却下した案

案却下の理由
index.html から release-notes/*.md を fetch() して表示する file:// で開くと必ず失敗し、配布した相手の環境でリリースノートが空になる。単一ファイルで渡せる前提が崩れる
.md を作らず RELEASE_NOTES だけを持つ 二重管理は消えるが、リポジトリを見る人と配布先の告知に流用できる原文が無くなる。生成する道具（/release-notes）の出力先とも噛み合わない
ビルド時に .md から RELEASE_NOTES を生成する 乖離は機械的に防げるが、このプロジェクトはビルド工程を持たないことを制約として選んでいる。生成を挟むと、配布と改造の敷居が上がる
別ページ（docs/ 配下のHTML）へのリンクにする アプリを配布した相手はリポジトリを持たない。エディタ単体で読めないと、告知として届かない

7. 将来拡張の入り口

やりたいこと触る場所
版ごとの項目を増やす・見出しを足す RELEASE_NOTES の sections（title と items の組を足すだけでよい）。補足の段落は note
初回起動時に未読の版を自動で開く openReleaseModal() と、既読の版を控えるキー（設定なので localStorage 側）
未読の自動表示は、今は入れていない。 起動直後にダイアログが出ると、書きに来た人の手が止まる。 入れるなら「開いた瞬間に塞ぐ」形ではなく、バージョン表記に印を付ける程度に留めること。
