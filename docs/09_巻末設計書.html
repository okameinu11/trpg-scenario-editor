巻末設計書

台本の最後に置く巻末（FAQ・あとがきなどの節・権利表記）を、どんな形で持ち、どの順でどう出すかと、 なぜその形にしたかを残す。巻末の見た目や入口を変えるときに読むこと。

1. 守備範囲

配布されるTRPGシナリオの最後に付くものを、本文とは別の入口で書けるようにする（2026-10-05 の要望）。

要素内容
FAQ遊ぶ人・回す人から出そうな質問と、その回答の組（「探索者が〇〇した場合は？」など）
あとがきなどの節見出しと本文の組。あとがき・謝辞・クレジット・更新履歴など、作者によって中身が違う
権利表記使ったゲームシステムや素材の権利表記。台本の一番最後に1つだけ置く

FAQはこのアプリ自体の使い方のヘルプではない。要望を受けたときに、どちらの意味かを利用者に確かめて決めた。 構成・並び順・入口・定型文の有無も、利用者に選んでもらって決めた（以下の各節）。

2. 形

faqs: [
  { id, question: "探索者が洋館から逃げ出した場合は？",
        answer:   "その時点でエンディング「雨上がり」へ進めてください。" }
],
backMatter: {
  sections: [ { id, heading: "あとがき", body: "…" }, { id, heading: "クレジット", body: "…" } ],
  rights: "本作は…"
}
  • シナリオのレコードに faqs と backMatter として持つ。保存・読込・書き出し・読み込み・移行・作業状態の復元のすべての入口で normalizeFaqList() / normalizeBackMatter() を通す。この機能より前のシナリオには無いので、空に均す。
  • FAQは先に作った機能なので、別の欄（faqs）のまま残した。巻末の画面にまとめたのは入口だけである（§4）。
  • 並び順は配列の順。編集画面の ↑ ↓ で並べ替える。
却下した案理由
「あとがき」と「権利表記」の決まった2つの欄だけを持つ 謝辞やクレジットを分けて書けない。要望が「あとがきや最後の権利表記など」で、決まった欄では足りない。
権利表記も節の1つにする（見出し「権利表記」の節） 「最後に置く」「小さめの文字で出す」が守れない。節を並べ替えると権利表記が途中に来てしまう。

3. 台本の最後に、決まった順で出す

updatePreview() が、本文の変換結果の後ろに buildFaqSectionHTML()・buildBackMatterHTML() の順で置く。 先頭の表紙（08）と同じく、本文の記法とは別の入口なので parseMarkdown() には混ぜない。

本文 → FAQ → あとがきなどの節 → 権利表記。配布シナリオで多い並びで、権利表記は奥付として一番最後に置く。

FAQの置き場所の候補判断
本文の後ろ（採用） 付録として最後に置かれることが多い。セッション中に「あの質問の答え」を探すときも、場所が決まっていれば迷わない。
表紙（基本情報）の直後 本文に入るまでが長くなる。FAQは本文を読んだ後に参照するものが多い。
本文の好きな場所に記法で置く FAQとして1か所にまとまらない。場面に結び付いた補足は、既存の [TIPS] や [DL]／[KP] で書ける。
  • 書いてあるものだけを出し、何も無ければ出さない。FAQで質問か回答の片方だけのものは「（未入力）」と薄く出す（書き忘れに気づけるように）。見出しだけの節は見出しだけを出す。
  • FAQと節の見出しはシーン見出しと同じ大きさにして、本文とは別の節に見せる（.appendix-heading）。FAQの Q と A は色の付いた丸で見分ける。
  • 権利表記は細い線で区切り、小さめの灰色の文字で出す。改行と文字色の記法はそのまま活かす。
  • 文は renderInline() を通す（04 §4 の順序）。FAQの印の丸と文は flex で並べるので、文は内側の要素で1段包む（04 §3.5）。
  • FAQの1件・権利表記の途中でページが切れないようにし、見出しの直後で改ページしないようにする。
  • 本文に目次 [目次] を書いた場合は、FAQと節の見出しも目次の最後に載る（権利表記は載せない）。そのため見出しに toc-faq・toc-bm-番号 の id を付けている（04 §10.4）。
  • プレビューに編集のボタンは置かない（プレビューは台本の紙面。08 §5 と同じ理由）。

4. 編集画面と入口

1つのモーダル「📕 巻末」の中を、タブで「FAQ」と「あとがき・権利表記」に分ける。 ヘッダーの入口は「📕 巻末」1つだけにした。

入口開くタブ
ヘッダーの「📕 巻末」（基本情報の隣）前に開いていたタブ（最初はFAQ）
コマンドパレットの「FAQ」・Alt+AFAQ
コマンドパレットの「あとがき・権利表記」あとがき・権利表記（既定のキーは無い）
  • ボタンを1つにまとめたのは、ヘッダーの幅のため。 もう1つボタンを足すと、1280pxで「執筆／場面図」「基本情報」などの名前が消えてアイコンだけになる（07 §3.6）。 FAQ・あとがき・権利表記は、どれも「台本の最後に出るもの」なので1つの画面にまとめても迷わない。 FAQを先に独立した画面（「❓ FAQ」）として作ったが、あとがきを足すときにこの形へ改めた。
  • コマンドパレットの操作 faq の ID は変えていない（ショートカット設定の保存キーなので、変えると割り当てが失われる。07 §6）。
  • 下部パネルには置かない（幅が無い。07 §3.2）。既定のキーを Alt+F にしなかったのは、ブラウザ（Chrome・Edge など）がメニューを開くキーだから。A は Answer の頭文字。
  • 「あとがき・権利表記」タブには、見出しを入れた状態で節を足す近道（あとがき・謝辞・クレジット・更新履歴）を置く。見出しが入っていれば本文の欄から打ち始める。
  • 一覧は追加・削除・並べ替えのときだけ作り直し、文字の入力は値を書き換えるだけにする（作り直すとフォーカスと入力途中の文字が失われる）。並べ替え・削除・入力の受け方はFAQと節で共用する（bindListEditor()）。中身のあるものを消すときだけ確認する。

5. 権利表記の定型文は持たない

エモクロアTRPG・クトゥルフ神話TRPGには、二次創作の権利表記の文面を定めた公式のガイドラインがある。 その文面をアプリに持たせて挿入できるようにする案もあったが、持たせないことにした（利用者が選んだ）。

  • 公式の文面は改訂されうる。アプリに持たせると、改訂に追従しない限り古い文面を挿入させることになり、権利表記として誤りになる。
  • ローカルの参考資料（knowledge/）にも公式の文面は無く、確かめられない文面を載せられない。

代わりに、入力欄の説明で「公式ガイドラインにある文面をそのまま貼る」ことを案内している。

6. 将来拡張の入り口

やりたいこと変える場所
FAQを分類ごとにまとめる normalizeFaqList() に分類の欄を足し、buildFaqSectionHTML() で分類ごとに小見出しを付ける
FAQの見出しの文言（「FAQ」「Q&A」「よくある質問」）を選べるようにする シナリオに見出しの文字列を持たせ、buildFaqSectionHTML() の見出しをそれに替える
FAQと節の並び順を入れ替えられるようにする updatePreview() の連結の順を、設定で切り替える
巻末を独立したページにする 印刷用CSSで .scenario-faq（無ければ .scenario-backmatter）に break-before: page を付ける
権利表記の定型文を挿入できるようにする §5 の判断を見直すこと。持たせるなら、文面の出典と確認した日付を一緒に残し、改訂を追う手順を決めてから
