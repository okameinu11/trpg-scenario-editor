KOTRO / 設計

場面ツリー設計書

場面をカードにして、分岐と合流を樹形図で並べる機能をなぜその形にしたかを残す。 データの持ち方・本文との対応づけ・図の描き方の判断が対象。実装に手を入れる前に読むこと。

1. 守備範囲

この機能が解こうとしているのは、書いている本人が物語の骨格を見失うという問題である。 本文は1本の長いテキストなので、分岐や合流のあるシナリオでは 「どの場面からどこへ繋がるか」が執筆者の頭の中にしか残らない。

したがって第一の利用者は執筆者本人であり、読者向けの成果物ではない。 ただし「読者に分岐を図で説明したい」場面は後から必ず来るので、 [場面図] 記法でプレビューとPDFに出せるところまでを最初から射程に入れている。 この二重の役割が、以降の判断のほとんどを決めている。

記法が画面にどう出るか（一覧）01 要件定義書 §4
データをどこに置いているか（全体像）03 保存方式設計書 §3

2. 場面をどう表すか

場面はノード（カード）とエッジ（接続）の2つで表す。 ノードは index.html の normalizeSceneNode()、 グラフ全体は normalizeSceneGraph() が形を保証する。

フィールド意味備考
idノードの識別子（UUID）必須
title本文の # 見出しと照合するキー空でよい（まだ書いていない構想カード）
summary概要メモ本文を書く前の下書き置き場
kind種別タグ（SCENE_KINDS のキー）未知の値は other に倒す
npcIds登場NPCのID配列§2.2
inDiagram[場面図] に出すか既定 true
x / y手で動かした位置null は「自動配置に従う」

2.1 なぜエッジを別配列にしたか

ノード側に parentIds を持たせても有向グラフは表せる。それでも edges: [{ id, from, to, label }] という独立した配列にしたのは、 エッジに分岐条件のラベルを載せると決めた時点で、エッジが選択・編集・削除の対象になったためである。 対象になるなら識別子が要る。

parentIds 方式では「Bの親配列の2番目」という位置による参照しか作れない。 並べ替え・再描画・取り消しのたびに参照先がずれる。 NPCの技能バッジが removeNpcSkill(index) と位置で消しているのは、 技能が単なる文字列で選択対象にならないから成立している話であって、ここには当てはまらない。

副次的な利点として、レイアウト計算（位相ソート・重心法）も線の描画も エッジを列挙する処理なので、配列がそのまま入力になる。 parentIds だと毎回 flatMap で組み直すことになる。

2.2 なぜ登場NPCは名前ではなくIDで持つのか

本文中のNPCカード記法 [NPC:名前] が名前で引いているのは、 著者がその文字列を手で打つからであって、名前照合が優れているからではない。

場面カードのNPC欄は既存のNPC一覧から選ぶ項目なので、IDで持てば改名に自動追従する。 名前で持つと、NPCを改名した瞬間に全カードの表示が壊れる。しかも本文と違って、 著者にはそれを直しに行く導線が無い（本文なら書き直せばよいが、カードは気づかない）。

IDで持っても、NPCを削除すると参照が宙に浮く。 描画側で存在しないIDを黙って無視すること（filter(Boolean)）。 削除時に全カードを走査して掃除するのは、掃除の漏れが1箇所でもあると壊れるので、 「描画側で耐える」を主、「削除時に掃除する」を従とする。

2.3 合流を許し、循環を許さない理由

「どのルートを通っても最終決戦に至る」はTRPGシナリオでごく普通の構造なので、 1つのノードが複数の親を持てることは要件そのものである。厳密な木では表せない。

一方で循環（AからBへ行き、BからAへ戻る）は許さない。 時系列を表す図で線が輪を描くと、読み手は「話が戻る」と解釈するしかないが、 それはこの図で伝えたいこと（先へ進む筋道）とは別の意味である。 同じ場所を再訪する表現が要るなら、それは別のノードとして置くほうが図として正しい。

実装上も、循環が無い（＝DAGである）ことを保証しておくと、 レイアウト計算を「無限ループしないか」を気にせず書ける。 保証する場所を normalizeSceneGraph() の1点に集約している（§4.2）。

3. どこに保存するか

3.1 シナリオのレコードの中に入れる

場面ツリーは scenarios ストアのレコードに scenes フィールドとして持つ。 立ち絵のように専用のオブジェクトストアは作らない。

DO

scenarios のレコードに同居させる。数十ノードでも数KBのJSONにしかならず、 シナリオを消せば一緒に消える。

DON'T

scenes ストアを新設する。DBのバージョンを上げる必要が出るうえ、 削除時の連動と孤児データの回収という、立ち絵と同じ問題をもう一組増やすことになる。

立ち絵を別ストアにした理由と対比すると分かりやすい。 画像を分けたのは「数MBのBlobを、本文を打つたびに書き直したくない」からである （03 保存方式設計書 §3.3）。 場面ツリーは軽いので、自動保存のたびに丸ごと書いてもその問題は起きない。 分ける理由が無いものを分けると、孤児の回収という新しい仕事だけが増える。

3.2 DBのバージョンは上げていない

既存ストアのレコードにフィールドを1つ足すだけなので、 onupgradeneeded（ストアを作る処理）に手を入れる必要が無い。 古いレコードは scenes が無いまま読み込まれ、正規化が空のグラフに均す。

将来ストアを追加したくなったときは、先に onblocked を足すこと。 現在の idbOpen() には req.onblocked が無い。 この状態でバージョンを上げると、同じアプリを別のタブでも開いている利用者は 更新処理に進めず、onsuccess も onerror も発火しないまま Promise が解決されない。起動処理はそれを待っているので、 画面は「読み込み中」のまま無言で止まり、原因が分からない。

3.3 書き出しJSONの版も上げていない

読み込み処理は format しか検証しておらず、version を見ていない。 そのため版を上げても、新しい版のファイルを古いビルドが読んだときに弾くことはできず、 scenes は黙って捨てられる。版番号を上げても防げるものが無い。

新しい版で書き出したJSONを、古いビルドで読み込んで保存し直すと、場面ツリーは失われる。 これはこの機能に固有の話ではなく、読み込み処理が 「知っているフィールドだけを写す」形になっていることの帰結である。 端末間でデータを移すときは、両方の端末を同じ版に揃えること。

4. 壊れたデータをどう均すか

4.1 入口をひとつに絞る

normalizeSceneGraph() を、保存・読込・書き出し・読み込み・移行の すべての入口に通している。受け持つのは次の5つ。

  • オブジェクトでないもの・null は空のグラフにする
  • IDが重複したノードを捨てる
  • 端点が存在しないエッジを捨てる
  • 自己ループと、同じ2点を結ぶ重複したエッジを捨てる
  • 循環を作っているエッジを捨てる（§4.2）

NPCデータを normalizeNpc() ひとつで吸収しているのと同じ考え方である。 グラフはNPCより壊れ方の種類が多い（参照関係を持つため）ので、 入口が分かれていると必ずどこかが漏れる。

4.2 循環は「戻っている辺」だけを捨てる

循環は本来、接続を足すときに拒否して作らせないのが主である （追加前に到達可能性を調べる）。ここでの処理は、手で編集したJSONや 将来の不具合に対する保険にあたる。

位相ソートで「順序に入らなかったノード」ごと捨ててはいけない。 最初にその実装（Kahn法）で書いたところ、 導入→書斎→最終決戦 と 導入→地下→最終決戦 という合流構造に 最終決戦→導入 の1本を混ぜただけで、4本すべてが消えた。 循環に巻き込まれたノードは入次数が0にならず、位相順に一切入れないためである。 捨てるべきなのは循環を成立させている辺だけで、そこに繋がっている構造ではない。

現在は深さ優先で辿り、「今たどっている途中のノード」へ戻る辺だけを落としている。 上の例なら 最終決戦→導入 の1本だけが消え、合流はそのまま残る。 再帰ではなく明示的なスタックで回しているのは、場面が深いときに 呼び出しスタックを使い切る可能性を避けるため。

5. 本文の見出しとの対応

5.1 見出しの切り出しは、プレビューと同じ規則で行う

カードは本文の # 見出しと 文字列の完全一致で対応づける。 本文側にマーカーを書かないので、既存のシナリオをそのまま使える。

行頭の # を拾う実装にしてはいけない。 parseMarkdown() は「空行2つ以上で区切ったブロックの先頭が #」のときだけ 見出しにする。行で拾うと、プレビューでは見出しになっていない行までカードの対象になり、 「カードはあるのに本文に飛べない」というずれ方をする。 extractSceneHeadings() は必ず同じ規則で切ること。

この規則の副産物として、# で書いたのに前に空行が無くて見出しになっていない行を 検出し、場面図の右側に出している。プレビューに出ないので気づきにくく、 気づかないまま長く放置されやすい書き間違いである。

改行を \r\n から \n へ正規化してはいけない。 文字数が変わり、本文へ飛ぶときに使う位置がずれる。 textarea.value の改行は仕様上 LF に揃っているので、そもそも不要である。

5.2 同期は半自動 ― 増やすのは指示されたときだけ、減らすことはしない

カードが正で、本文はその参照先である。場面図に入ったとき、または「本文を再走査」を押したときに 本文を読み直し、まだカードになっていない見出しを一覧に出すだけにしている。 取り込むかどうかは利用者が決める。

案却下した理由
本文から自動でカードを増減する 見出しの改名が「削除と新規作成」に化ける。 # 導入 を # 導入（雨） に直しただけで、 そのカードのメモ・種別・登場NPC・座標・接続がまとめて消える。 さらに自動保存は500ms間隔で走るので、# 導 まで打って手を止めれば 「導」というカードが確定してしまう
取り込みも手作業にする 既に30個の見出しがある原稿では30回の手作業になる。 整理のための道具の初期コストとしては高すぎて、使われなくなる

「自動で作る」利点と「自動で消す」危険は切り離せる。半自動は前者だけを取る。 対応する見出しが無いカードは消さず、⚠ 未執筆 の印を付けて残す。 まだ書いていないカードと、本文側で改名して切れたカードは区別しない （区別するには過去の状態を保存する必要があり、得るものに見合わない）。 改名されたときは、カードの見出し名を打ち直せば他の情報を保ったまま繋ぎ直せる。

6. 画面の切り替え

執筆と場面図は <body data-mode> 属性とCSSで出し分ける。

DO

属性を切り替え、表示・非表示はCSSに任せる。印刷用の指定から !important で確実に上書きできる。

DON'T

JSで style.display を直に書く。インラインの指定は @media print の !important にも勝ってしまい、 場面図を開いたまま印刷すると白紙になる。

本文の入力欄をDOMから外す作りにしてはいけない。 textarea を付け外しするとブラウザの取り消し履歴（Ctrl+Z）が消える。 執筆の道具でこれが効かなくなるのは、どんな利点とも交換できない。 入力中の変換・選択範囲・スクロール位置も失われる。

6.1 場面図を見ている間、挿入のキー操作を止める

下部のパネルを隠しても、キー操作の受け付けは生きている。止めないと、 場面図を見ている間に Alt+1 を押すだけで隠れた本文に # が書き込まれ、 プレビューも隠れているので気づけない。 handleGlobalKeydown() で、モーダルが開いているときと同じ形で遮っている。

通すのは本文を書き換えない操作だけ（保存・画面の切り替え・コマンドパレット・シナリオ一覧・PDF出力・ショートカット設定）。 保存が効かないほうが驚かれるし、残りは本文に触れないため。 どれを通すかは操作の表 ACTIONS の inSceneMode で決まり、 コマンドパレットの候補も同じ判定で絞られる（07 操作の入口設計書 §5）。

7. 自動レイアウト

7.1 段は「最長経路」で決める

各場面の段は「入口からの最長経路」で決める。最短経路にしてはいけない。

「導入 → 脇道 → 最終決戦」と「導入 → 調査 → 対決 → 最終決戦」が合流する形を考える。 最短経路だと最終決戦が浅い段に置かれ、深いほうの親からは上向きの線が出る。 上へ戻る線は「話が戻る」と読めてしまい、この図で伝えたいこととは別の意味になる。 最長経路なら、すべての接続で「子は親より下」が保証される。

7.2 同じ段の並び順

出発点は本文の見出しの出現順。著者は執筆の時点で既に場面を並べており、 これはこのアプリだけが持てる強い手がかりである。 そのうえで、隣の段での位置の平均に寄せる操作（重心法）を4回繰り返し、線の交差を減らす。

7.3 段を2つ以上またぐ接続には、途中に仮の点を置く

置かないと2つの問題が同時に起きる。線が途中の段のカードを突き抜けることと、 途中の段を並べ替えるときにその接続の情報がまったく効かないこと。 仮の点はそのまま線の経由点になるので、迂回する曲線も同じ仕組みで引ける。

7.4 手で動かした位置との共存

座標を持つカードはその位置を使い、持たないカードは計算した位置に置く。 「整列」で座標を捨てれば自動配置に戻る。

手で置いたカードと自動配置のカードが重なることは、割り切って許している。 自動的に避けさせる（力学モデルなど）としくみは大きくなるうえ、動きが読めなくなる。 「整列」でいつでも戻せることを逃げ道にしている。 力学モデル自体も、段が揃わないため「合流を線で示す」という目的には向かない。

8. 図の描き方と操作

8.1 画面はHTMLのカード＋背景のSVG

画面の樹形図は、カードをHTMLの要素で置き、線だけをその下に敷いたSVGで描く。

すべてSVGで描く案の問題
文字の折り返しを自分で計算する必要がある。foreignObject は印刷やPDF化での挙動が不安定で、ライブラリを入れない方針の環境で「動かない環境がある」危険は取れない
種別の色やホバーの見た目をCSS変数で書けず、属性で二重に持つことになる
ドラッグ中にSVGを作り直すと、つかんでいる要素ごと消えてポインタの追跡が切れる
既存の .btn などのCSSがまったく使えない

座標の食い違いは、カードの大きさを定数で固定することで防いでいる （SCENE_CARD_W / SCENE_CARD_H とCSSの値を一致させる）。 内容によってカードが伸び縮みすると、線の端点が浮く。

8.2 線は曲線にする

直角の折れ線にしてはいけない。 合流のある図では複数の線が同じ縦の道を通るため、折れ線だとぴったり重なって1本に見える。 「3つのルートが合流している」という、この図で最も伝えたいことが読めなくなる。 曲線なら重なっても曲がり方が違うので追える。

矢頭は marker ではなく多角形を直接置いている。 marker は理屈の上では動くが、file:// で開く使い方と印刷を組み合わせた実績が このコードベースに無く、レーダーチャートも多角形だけで組んでいるため、そちらに合わせた。

8.3 つなぐ辺は位置関係で切り替える

線を出す辺と受ける辺は、2枚のカードの中心の位置関係から決める （sceneAnchorPair()）。下・上・右・左の4通り。

「下端から上端へ」で固定してはいけない。 自動配置では常に上から下へ並ぶので気づかないが、 カードを手で横に並べ替えた瞬間に破綻する。 隣に置いただけの2枚を結ぶのに、線がいったん下へ降りて大きく回り込み、 「近くに置いた」という意図と正反対の見え方になる。

判定は、中心どうしの差をカードの幅と高さで割ってから比べる。 カードは横長（180×72）なので、差をそのまま比べると縦の判定に寄り、 横に並べたつもりでも縦につながってしまう。

制御点は辺の法線方向へ引き出し、矢頭も進む向きに合わせて描く。 向きを1つの値（dir）で持ち回しているので、 線・制御点・矢頭の3つがばらばらの向きになることがない。

手で動かしたカードが絡む接続では、経由点を使わない。 経由点は自動配置の段と段の間に置かれているので、カードを動かした後では まったく関係のない場所を通る線になる。 layoutSceneGraph() が手動配置のカードを集合で返し、描画側がそれを見て切り替える。

8.4 ドラッグ

pointerdown 系で受ける。このアプリはタブレットでの利用を想定しているので、 マウス用とタッチ用を二重に書く価値が無い。カードは描き直しのたびに作り替わるため、 イベントはキャンバスに委譲している（NPC編集欄と同じ理由）。

touch-action: none を書き忘れないこと。 無いと、タブレットではブラウザ側のスクロールが先に始まって指の動きが届かない。 PCでは再現しないので、気づくのが遅れる。

カードは「クリックで選ぶ」と「ドラッグで動かす」を兼ねるので、 動いた距離が5px未満なら選択として扱う。閾値が無いと、 押した拍子に少しずれただけで本文へ飛んでしまう。

8.5 つなぐ操作は Ctrl＋ドラッグ

カードを Ctrl（Macでは⌘）を押しながらドラッグし、相手の上で離すとつながる。 右のペインで相手を選ぶ方法も残してあるが、図を見ながら整理している最中に いちいち一覧へ目を移すのは、作業の流れを断つ。

操作中に見せるもの理由
引きかけの破線と矢頭どちらからどちらへ繋ごうとしているかが、この操作でいちばん大事な情報だから
相手のカードを緑または赤で囲む離す前につながるかどうかが分かる
つなげない理由を線の上に出す赤いだけでは理由が分からず、操作が効いていないように見える
つなげない相手は、押した時点で一度だけ調べる。 指を動かすたびに循環の判定をやり直すと、場面が増えたときに重くなる。 調べるのは「自分自身」「すでにつながっている」「逆向きに辿り着ける（＝循環になる）」の3つ。
この操作はタッチだけの環境では使えない。 指には Ctrl がない。だからタブレットのために、 右のペインから相手を選ぶ方法を残しておく必要がある。 Ctrl＋ドラッグを入れたからといって、そちらを消してはいけない。

ドラッグ中は e.target がつかんだカードに固定されるので、 相手は document.elementFromPoint() で座標から引き直す。

8.6 パンとズームは入れない

表示領域のスクロールと、倍率を選ぶだけにしている。 ブラウザ本来のスクロールは、ホイール・トラックパッド・タッチ・キーボードのすべてで最初から動き、 「今どこを見ているか」を示すスクロールバーも付いてくる。 独自のパンは、このアプリが一度も教えていない操作（中ボタンのドラッグなど）を持ち込むうえ、 ホイールやタッチを横取りするとカードのドラッグと競合する。

倍率を掛けているので、画面上の座標をそのまま図の中の座標として使うとカードが指からずれる。 換算は canvasPointFromEvent() の1本に閉じ込めてある。 別の場所で座標を扱うときも、必ずこれを通すこと。

9. [場面図] による出力

9.1 変換は parseMarkdown() に置く

parseElement() に足してはいけない。 そちらを通ると図が本文カラム（幅72%）の中に入り、 紙に出したときの有効幅が130mm程度まで狭くなる。 見出しと同じく、段組みの外に出す全幅のブロックとして扱う。 04 記法設計書 §7.1 のチェックリストは この違いを含めて書き直してある。

9.2 入口によってエスケープの状態が違う

parseElement() は先頭で1回エスケープした文字列を扱い、 parseMarkdown() のブロックは生の文字列である。 同じ [場面図:黒い&白い部屋] でも、前者では場面名が 黒い&amp;白い部屋 になる。

そのため parseElement() 側では場面名を読まない。 前後に空行が無くて段落に混ざってしまった場合に、書き方を伝える一文を返すだけにしてある。 両方で場面名を解釈すると、& を含む場面名のときだけ図が出ない、 という原因の見えにくい不具合になる。

9.3 SVGの中の文字は decorate() を通さない

これは「エスケープ → 装飾 → 改行」という順序ルールの例外である。 decorate() が作る <span> と <br> は、 どちらもSVGの中では効かない（色は fill 属性、改行は tspan である）。 通してよいのは escapeHTML() だけ。 理由を書き残さないと、順序ルールに従っていないように見えて 後から decorate() を足され、図が壊れる。

結果として、場面名やラベルに文字色の記法を書いても図には効かない。 折り返しは全角・半角の幅を積んで tspan で折っている。 日本語はどこでも改行できるので、単語の区切りを見る必要はない。

9.4 「図解に出さない」場面は通り抜ける

図から外した場面は描かないが、その前後は破線で繋ぎ直す。

DO

外した場面の親から子へ、点線の接続を引く。 細かい場面を畳んでも、ルート全体の繋がりは保たれる。

DON'T

そこで枝を切る。畳んだだけなのに 「最終決戦にたどり着かないルート」が図の上に生まれる。 示したいことの正反対になる。

実線と同じ見た目にしないのは、直接つながっていると読めてしまうため。

9.5 紙に収める

幅に合わせるだけでは足りない。 段の多い図は縦が1ページを超え、SVGはページをまたいで分割できないので 途中で切れる。高さの上限（240mm）も指定して、必ず1枚に収まるようにしてある。 収まりきらない規模のときは、[場面図:場面名] で分ける案内を図の下に出す。

画面の樹形図と違い、こちらは紙用の色ひと組だけを持つ。 レーダーチャートが画面用と印刷用で色を分けているのは、暗い背景のNPC編集画面にも出るためで、 場面図はプレビュー（常に白い紙面）にしか出ないため分ける必要が無い。

9.6 図を描けなくてもプレビューは落とさない

updatePreview() は本文全体を1回で差し替えるので、 変換の途中で例外が出るとプレビューが丸ごと空白になる。 同じ形の事故が過去に一度起きている（数値を渡して型エラーになり、プレビューが止まった）。 図の組み立て全体を try で囲み、失敗しても 「場面図を描けませんでした」の1行だけを返すこと。

10. 将来拡張の入り口

やりたくなりそうなことどこを変えるか
場面が増えたときの見通し パンとズームを足す。canvasPointFromEvent() が座標の換算を1箇所に集めてあるので、そこを直せば操作は追従する
分岐の条件をもっと構造化したい（判定の成否と結び付けるなど） 接続の label を文字列から構造に変える。正規化が1本なので、そこで旧い文字列を受け付ければ既存データは壊れない
時間の流れを横軸で示したい layoutSceneGraph() の段の決め方を差し替える。座標を返す形は変わらないので、描画側は触らずに済む
