保存方式設計書

データをどこに、どの形で置くかを定める。保存に関わる変更を入れる前に、必ずこの文書を読むこと。

2026-09-01: シナリオ本体の保存先を localStorage から IndexedDB へ移した。 設定（ショートカット・判定の自由枠）は引き続き localStorage に置く。 移行の理由と、検討して却下した案は §2 にある。

1. なぜ移したか

localStorage の容量上限はおおむね5MBである。 NPCの立ち絵画像を保存するようになった結果、この上限が現実的な制約になった。

要因内容
画像が文字列に膨らむ localStorage は文字列しか置けないため、画像を base64 の data URL に変換していた。 base64 は元データの約1.33倍になる。
同じ画像が2重に入る シナリオ保存庫（trpg_db_scenarios）と編集中の作業状態（trpg_npcs_cache）の 両方に、同じNPCデータが画像込みで入っていた。実効の上限は半分だった。
打つたびに全部書き直す 自動保存は本文とNPC全員分をまとめて文字列にして書き込む。 localStorage は同期APIなので、データが増えるほど入力中に画面が止まる。

長辺1024pxのWebP（品質0.85）は1枚あたり100〜400KB程度になる。 base64化と2重保存を踏まえると、立ち絵つきのNPCが10体前後で上限に達する計算になる。 上限を超えると QuotaExceededError が投げられ、保存が失敗する。

2.1 ローカルフォルダ指定を採らなかった理由

showDirectoryPicker() でユーザーが選んだフォルダへ直接読み書きする案は、 容量の問題を解くだけでなく「ブラウザのデータを削除しても消えない」という利点もある。 それでも唯一の保存先には採用しない。

この機能は Chromium系のデスクトップ（Windows / macOS の Chrome・Edge）にしか無い。 Chrome for Android は非対応であり、Firefox・Safari も非対応である。 本エディタはAndroidタブレットでの利用を非機能要件に掲げている （要件定義書 §5）ため、主戦場で動かない仕組みを土台にはできない。 加えて安全なコンテキストを要求するため、file:// で開いた場合も使えず、 「渡せば即動く」という本エディタの前提を崩す。

将来的には任意の追加機能として足す余地がある。 その場合の位置づけは「JSONの書き出し／読み込みを自動化したもの」であり、 これが無くても全機能が動く状態を保つこと。

IndexedDB に移しても「消えない」保証は得られない。 localStorage と同じくブラウザが管理する領域であり、 「サイトのデータを削除」で消える。シークレットウィンドウでは残らない。 空き容量が逼迫すれば退避（eviction）の対象にもなる。

解決するのは容量だけである。消失に備える手段は、 引き続きJSONの書き出しであることを利用者に伝え続けること。

3.3 立ち絵画像の持ち方

画像はシナリオとは別のストアに置き、NPCは avatarId で参照する。

DO

画像を別ストアに分ける。本文を打つたびの自動保存で、 画像を書き直さずに済む。 シナリオ本体は画像を含まないため小さく、頻繁に書き換えても軽い。

DON'T

画像をシナリオのレコードに埋め込む。 自動保存のたびに数MBを書き直すことになり、 localStorage で起きていた「入力中に固まる」問題を持ち込むだけになる。

メモリ上では、読み込み時に URL.createObjectURL() で作った blob: URL を npc.avatarUrl に入れる。 画面側（NPC一覧のサムネイル・編集欄のプレビュー・プレビューのNPCカード）は 従来どおり avatarUrl をそのまま使うため、描画コードは変わらない。

作った object URL は必ず解放すること。 blob: URL はドキュメントが生きている限りメモリを掴み続ける。 シナリオの切り替え・NPCの削除・画像の差し替えのたびに URL.revokeObjectURL() を呼ぶ。 解放漏れを防ぐため、作った URL は1箇所（objectUrlRegistry）で管理し、 まとめて破棄できるようにしている。

4. 書き出し／読み込み（JSON）

端末間のデータ移動は引き続きJSONで行う。 ファイルの形式は変えない（format: "trpg-scenario-editor" / version: 1）。

JSONの中では、画像は従来どおり base64 の data URL で持つ。 JSONにBlobは書けないうえ、この形式は他の端末・他のバージョンとの互換の窓口だからである。 書き出し時に Blob → data URL、読み込み時に data URL → Blob へ変換する。

この変換は非同期なので、exportScenarios() / importScenarios() は Promise を返す形に変えた（他の4メソッドは元から Promise を返していた）。

5. 既存データの移行

起動時に localStorage の旧データを検出したら、IndexedDB へ移す。利用者の操作は要らない。

移行元（localStorage）移行先
trpg_db_scenarios（無ければ旧 trpg_mock_db_scenarios）scenarios ＋ avatars
trpg_current_id / trpg_current_system / trpg_scenario_content / trpg_scenario_title / trpg_npcs_cacheworkspace
移行が完全に成功したことを確認してから、localStorage 側を削除する。 容量を空けるのが目的なので消す必要があるが、 途中で失敗したまま消すと復元できなくなる。 書き込みがすべて完了した後にのみ削除すること。

移行が失敗した場合は旧データに一切触れず、 利用者に「JSONで書き出してから再試行してほしい」と伝える。 黙って空のシナリオ一覧を見せてはならない。
移行は1回だけ走る。完了したら trpg_storage_migrated に印を置き、 以後は localStorage を見に行かない。

6. 起動処理が非同期になる

作業状態の復元が IndexedDB からの読み出しになるため、 DOMContentLoaded のハンドラは async になる。

DO

復元を待ってから updatePreview() と applySystemToUI() を呼ぶ。 設定（ショートカット・自由枠）は localStorage なので、待たずに読める。

DON'T

復元を待たずに描画する。空の本文でプレビューを描いた後に 中身が入ってくるため、一瞬ちらつく。 さらに、復元前に利用者が打ち始めるとその入力が復元データで上書きされる。

7. 容量超過の扱い

IndexedDB も QuotaExceededError を投げうる。上限が上がっただけで、無限ではない。

  • 明示保存の失敗は alert で伝える。利用者が保存したつもりのまま進むのを防ぐため。
  • 自動保存の失敗は alert を出さず、ヘッダーの状態表示に出す。 入力のたびに走る処理であり、ダイアログが出続けると執筆できなくなるため。
  • どちらの文言にも「JSONで書き出してから不要なシナリオや画像を消す」という次の一手を書く。
