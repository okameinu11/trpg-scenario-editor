記法設計書

独自記法をなぜその形にしたかを残す。記法の一覧そのものは 要件定義書 §4 にある。記法を足す・変えるときは先にここを読むこと。

1. このドキュメントの守備範囲

本エディタの記法は標準Markdownと互換ではない。GMがセッション中に読む紙面を作るための、 このアプリ専用の言語である。仕様が要件定義書に載っていても、 なぜ他の書き方を選ばなかったのかが残っていないと、 次に記法を足す人が同じ検討をやり直すことになる。

知りたいこと読む場所
どんな記法があるか・どう表示されるか要件定義書 §4
なぜその区切り記号・その構造なのかこのドキュメント
パーサがどこにあるか開発計画・設計書 §3.2

2. 記法の系統を区切り記号で分ける

記法はブロック記法とインライン記法の2系統あり、 使う括弧で系統そのものを見分けられるようにしている。

系統括弧掛かる範囲例
ブロック記法[ ] 段落の先頭に置き、その段落全体を1つの箱にする [判定:目星] [SAN:1/1D6] [NPC:田中]
インライン記法{ } 文中の一部だけを装飾する {赤:テキスト}
括弧で系統を分けたのは、パーサの構造がそもそも別だからである。 ブロック記法は parseElement() が段落の先頭を startsWith() で見て分岐する。 インライン記法は decorate() が段落の中身を正規表現で走査する。 同じ [ ] を両方に使うと、[判定:…] で始まる段落の中に [赤:…] が現れたときにどちらの規則が優先するかが読み手に分からなくなる。

2.1 却下した案

案却下した理由
**赤** のような記号だけの装飾 色は6種類あるので記号を色ごとに割り当てることになり、対応を覚えられない。 記号は「太字」のように種類が1つしかない装飾にしか向かない。
HTMLタグを本文に直接書かせる 本文は必ず escapeHTML() を通す設計で、これを緩めると シナリオのインポート経由で任意のHTMLが差し込める。 装飾のために全体の防御を下げる取引は割に合わない。
インラインも [赤:…] にする 既存のブロック記法と見分けが付かない。 [探索:…] のように「行頭なら箱、行中なら装飾」という 位置依存の規則が生まれ、書き手が結果を予測できなくなる。

3. 文字色 — 固定パレットと任意色の二段構え

色名（{赤:…}）を主とし、16進のカラーコード（{#88ccff:…}）も受け付ける。 実装上も扱いを分けており、色名はCSSクラス、16進は style 属性へ載せる。

指定生成されるHTML位置づけ
{赤:…}<span class="ic-red">推奨 濃さを実装側が保証する
{#88ccff:…}<span style="color: #88ccff;">任意 見え方は書き手の責任
DO

パレットの6色（赤・青・緑・橙・紫・灰）で足りるなら色名を使う。 PDFにしたときに読める濃さを実装側が保証できるのは色名だけであり、 複数のシナリオを並べたときに色の意味がぶれない。

DON'T

雰囲気で淡い色を指定する。本エディタの成果物は紙に出して卓で読む。 画面では読めても、印刷すると背景に溶ける。 任意色は「どうしてもその色でなければ意味が通らない」ときの逃げ道である。

3.1 なぜ任意色を残したか

パレットのみに絞る案も検討した。却下したのは、色そのものが情報を持つ場面があるため。 「青い液体」「緑色の光」のように、卓上で見せるハンドアウトの色を本文の色と揃えたいという要求は パレットでは満たせない。ただし既定では見えない場所に置き（モーダルの下段）、 淡い色の危険を文言で添えている。

3.2 CSSの詳細度を上げてある理由

色クラスのセレクタは #preview-area span.ic-red と、意図的に span を付けて詳細度を (1,1,1) にしてある。

#preview-area .ic-red に縮めてはいけない。 プレビューの各ブロックは #preview-area .result-text { color: … !important } のように 詳細度 (1,1,0) ＋ !important で文字色を固定している。 同じ詳細度だと記述順で勝敗が決まり、CSSを並べ替えただけで発色しなくなる。

3.3 入れ子を作らせない

{赤:{青:…}} という入れ子は解釈できない。 走査パターンが中身に波括弧を許さないため、外側が記法として認識されず、 波括弧がそのまま本文に出てしまう。

入れ子を解釈できるようにする案もあったが、色の入れ子には意味が無い（内側が必ず勝つ）ため、 パーサを複雑にする価値がない。代わりに入口の側で入れ子を作らせないことにした。 expandOverColorNotation() が、選択範囲を囲んでいる既存の色記法まで範囲を広げてから 囲み直す。結果、色の付いた文字を選んで別の色を押すと「付け替え」になる。

同じ理由で、色記法は1行に閉じる（走査パターンが改行を含まない）。 閉じ忘れた波括弧が後続の段落まで飲み込むと、被害が書いた場所から離れて原因が分からなくなる。

3.4 色として解釈できない名前は変換しない

{注:これは色ではない} のように、色名でも16進でもないものは記法として扱わず原文のまま残す。 本文に波括弧を書くこと自体は珍しくないため、取りこぼしより誤変換のほうが害が大きいという判断。 誤変換は書いた本人が気付きにくい。

3.5 装飾はブロックのレイアウトを壊しうる

インライン装飾を入れたことで、本文が「ただのテキスト」ではなくなった。 どのブロックの中にも <span> が現れうる。 プレビューのブロックを組むときは、この前提を崩さないレイアウトを選ぶこと。

本文を直接載せる要素に display: flex を使ってはいけない。 フレックスコンテナでは、子要素はそれぞれ独立したフレックス項目になり、 地のテキストだけが匿名の項目にまとめられる。 そのため あああ<span>色</span>いいい は3つの項目に割れ、 文が分断されて並び順まで崩れる。

探索可能箇所を縦並びにしたとき、目印（▶）を出すために 項目を display: flex にして実際にこれを踏んだ。 目印は絶対配置にして、項目そのものは display: block のままにしてある。 レイアウトのためにフレックスを使いたくなったら、 本文を内側の要素で1段包んでからにすること。

4. 変換の順序 — エスケープ → 装飾 → 改行

プレビュー用HTMLを組み立てる順序は3段で固定されている。 この順序は decorate()（エスケープ済みの文字列を受け取る）と renderInline()（生の文字列を受け取る）に閉じ込めてあり、 呼び出し側で手書きしない。

  1. escapeHTML() — 本文中の < や & を無害化する
  2. decorate() の色変換 — <span> を生成する
  3. 改行の <br> 化
順序を入れ替えると必ず壊れる。 装飾より後にエスケープすると、生成した <span> ごとエスケープされてタグが本文に出る。 改行を先に <br> にすると、そのあとのエスケープで <br> が無効化される。

これは机上の心配ではない。NPCカードのメモ欄は実際にエスケープが漏れており、 HP<5で逃走 という普通の記述で文字が消えていた。 同じ3行を7箇所に書き写していたことが原因であるため、 関数に閉じ込めて書き写せないようにした。

4.1 二重エスケープにも注意する

parseElement() は先頭で本文全体を1回エスケープし、以降はその文字列を切り出して使う。 切り出した断片を再度 escapeHTML() に通すと二重エスケープになり、 A & B が画面に A &amp; B と表示される （探索一覧の項目と判定の提示タイプで実際に起きていた。2026-09-01 に修正）。

DO

parseElement() の中で断片を出力するときは decorate() を使う。 エスケープ済みであることが関数名から分かる。

DON'T

escapeHTML() を「念のため」重ねる。 安全側に倒したつもりで、表示が壊れる。

5. 判定ブロックの結果を複数行にする

判定ブロック（[判定:…] / [SAN:…]）の結果テキストは、 - で始まらない行を直前の項目の続きとして連結する。 

[判定:目星]
- 成功: 引き出しの奥に鍵を見つける。
  鍵には「B-3」と刻印がある。   ← 直前の「成功」の続きになる
- 失敗: 何も見つからない。

5.1 なぜ継続行方式か

この方式だけが既存のシナリオを壊さないため。 改修前のパーサは - で始まらない行を continue で読み飛ばしていた。 つまりこの位置に書かれた文字はもともと画面に出ていなかった。 継続行として拾うようにしても、表示が変わるのは「消えていた文字が出るようになる」方向だけである。

却下した案理由
\n のようなエスケープ記号 書き手が改行を「文字として」打てない。エディタで見た形とプレビューの形が乖離する。
継続行の先頭に専用記号（| など）を要求する 覚える記号が増える。素直に改行して字下げする書き方が既に自然に行われていた。
結果テキストを別のブロック記法にする 1つの判定が複数のブロックに割れ、プレビューの箱も割れる。
判定ブロックの終わりには空行を置くこと。 段落は空行で区切られるため、判定ブロックの直後に空行を置かずに本文を続けると、 その本文が最後の結果行の続きとして箱の中に取り込まれる。 改修前は読み飛ばされて消えていたので、古いシナリオにこの書き方が残っている可能性がある。

6. システム固有の記法をどう扱うか

共鳴判定（エモクロア）とSANチェック（クトゥルフ神話TRPG）は、片方のシステムにしか存在しない。 これらは入口とパーサで扱いを変える。

層扱い実装
入口（パネルのボタン・ショートカット） そのシステムのときだけ出す applySystemToUI() が hasResonanceRoll / hasSanCheck で表示を切り替える
パーサ 常に受け付ける parseElement() はシステムを見ずに [共鳴:…] / [SAN:…] を解釈する
パーサを出し分けない理由。 シナリオのシステムは作成時に固定されるが、JSONで受け渡したシナリオを別システムで開き直すことは起こりうる。 そのときパーサまで出し分けていると、記法が解釈されずに [SAN:1/1D6] という文字列が そのまま紙面に出る。読めない箱より、色の違う箱のほうがましである。 GM向け情報ブロックで [DL] と [KP] の両方を常に受け付けているのと同じ考え方。

6.1 SANチェックを判定ブロックと同じ構造にした理由

SANチェックは [SAN:成功時/失敗時] のヘッダに、判定ブロックと同じ - 枠: 本文 の結果行が続く。1行のボックス（共鳴判定と同じ形）にする案もあったが、 SANチェックは成否で起きることが変わるのが本体であり、 減少値だけを示しても本文に「成功したら／失敗したら」を書き直すことになる。

結果行のパースは parseRollResultLines() で技能判定と共用している。 複数行対応やバッジの色分けが片方だけ古くなるのを防ぐため。 一方で枠の一覧は分けて持つ（rollTiers と sanTiers）。 SANチェックに「スペシャル」は無く、成功・失敗の2つで足りることが多いため。

配色は赤系。骨格が技能判定と同じである以上、 色だけが「この箱は普通の判定ではない」という手掛かりになる。 青い技能判定の箱がいくつも並ぶ紙面で、危険な判定を拾えるようにするため。 共鳴判定（resonance-box）も赤系だが、 あちらはエモクロア専用・こちらはCoC専用で、同じシナリオに両方が出ることはない。

7. 記法を足すときに触る場所

1つでも漏れると「ボタンからは入るがプレビューに出ない」「記法は効くが入口が無い」状態になる。

7.1 ブロック記法を足す場合

  • parseElement() — 記法をHTMLに変換する
  • insertTemplate() または専用モーダル — 下部パネルから挿入する
  • DEFAULT_SHORTCUTS — ショートカットの割当と設定画面のラベル
  • updateAssistantPanelShortcutLabels() / executeShortcutAction() — パネルとキー操作の配線
  • システム固有なら GAME_SYSTEMS のフラグと applySystemToUI() の出し分け
  • 要件定義書 §4 の記法一覧

7.2 インライン装飾を足す場合

太字・傍点・マーカーなどを足すときも { } の系統に載せる。 decorate() の走査パターンは {名前:中身} という形しか見ておらず、 名前が色として解釈できなければ素通しにしているので、 名前の解決を色以外にも広げるだけで足せる。

装飾を増やす前に、入れ子を許すかどうかを決めること。 現状は「入れ子は解釈しない・入口で作らせない」で統一している（§3.3）。 色だけなら入れ子に意味が無いので成立するが、 {太字:{赤:…}} のような組み合わせに意味が出た時点でこの前提は崩れる。 そのときは走査パターンを1段深くするのではなく、 装飾を並べて書ける形（例: {赤+太字:…}）を先に検討すること。 入れ子を許すと、閉じ忘れの被害範囲が段落全体に広がる。
