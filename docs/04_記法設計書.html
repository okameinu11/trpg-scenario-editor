記法設計書

独自記法をなぜその形にしたかを残す。記法の一覧そのものは 要件定義書 §4 にある。記法を足す・変えるときは先にここを読むこと。

1. このドキュメントの守備範囲

本エディタの記法は標準Markdownと互換ではない。GMがセッション中に読む紙面を作るための、 このアプリ専用の言語である。仕様が要件定義書に載っていても、 なぜ他の書き方を選ばなかったのかが残っていないと、 次に記法を足す人が同じ検討をやり直すことになる。

知りたいこと読む場所
どんな記法があるか・どう表示されるか要件定義書 §4
なぜその区切り記号・その構造なのかこのドキュメント
パーサがどこにあるか開発計画・設計書 §3.2

2. 記法の系統を区切り記号で分ける

記法はブロック記法とインライン記法の2系統あり、 使う括弧で系統そのものを見分けられるようにしている。

系統括弧掛かる範囲例
ブロック記法[ ] 段落の先頭に置き、その段落全体を1つの箱にする [判定:目星] [SAN:1/1D6] [NPC:田中]
インライン記法{ }（太字だけは ** **、リンクだけは [ ]( )。§14・§15） 文中の一部だけを装飾する・文中に目印やリンクを置く {赤:テキスト} {漢字|かんじ} **太字** {#目印} [表示](#目印)
括弧で系統を分けたのは、パーサの構造がそもそも別だからである。 ブロック記法は parseElement() が段落の先頭を startsWith() で見て分岐する。 インライン記法は decorate() が段落の中身を正規表現で走査する。 同じ [ ] を両方に使うと、[判定:…] で始まる段落の中に [赤:…] が現れたときにどちらの規則が優先するかが読み手に分からなくなる。

2.1 却下した案

案却下した理由
**赤** のような記号だけの装飾 色は6種類あるので記号を色ごとに割り当てることになり、対応を覚えられない。 記号は「太字」のように種類が1つしかない装飾にしか向かない （その太字は、この理由から Markdown と同じ **太字** にした。§14）。
HTMLタグを本文に直接書かせる 本文は必ず escapeHTML() を通す設計で、これを緩めると シナリオのインポート経由で任意のHTMLが差し込める。 装飾のために全体の防御を下げる取引は割に合わない。
インラインも [赤:…] にする 既存のブロック記法と見分けが付かない。 [探索:…] のように「行頭なら箱、行中なら装飾」という 位置依存の規則が生まれ、書き手が結果を予測できなくなる。

3. 文字色 — 固定パレットと任意色の二段構え

色名（{赤:…}）を主とし、16進のカラーコード（{#88ccff:…}）も受け付ける。 実装上も扱いを分けており、色名はCSSクラス、16進は style 属性へ載せる。

指定生成されるHTML位置づけ
{赤:…}<span class="ic-red">推奨 濃さを実装側が保証する
{#88ccff:…}<span style="color: #88ccff;">任意 見え方は書き手の責任
DO

パレットの6色（赤・青・緑・橙・紫・灰）で足りるなら色名を使う。 PDFにしたときに読める濃さを実装側が保証できるのは色名だけであり、 複数のシナリオを並べたときに色の意味がぶれない。

DON'T

雰囲気で淡い色を指定する。本エディタの成果物は紙に出して卓で読む。 画面では読めても、印刷すると背景に溶ける。 任意色は「どうしてもその色でなければ意味が通らない」ときの逃げ道である。

3.1 なぜ任意色を残したか

パレットのみに絞る案も検討した。却下したのは、色そのものが情報を持つ場面があるため。 「青い液体」「緑色の光」のように、卓上で見せるハンドアウトの色を本文の色と揃えたいという要求は パレットでは満たせない。ただし既定では見えない場所に置き（モーダルの下段）、 淡い色の危険を文言で添えている。

3.2 CSSの詳細度を上げてある理由

色クラスのセレクタは #preview-area span.ic-red と、意図的に span を付けて詳細度を (1,1,1) にしてある。

#preview-area .ic-red に縮めてはいけない。 プレビューの各ブロックは #preview-area .result-text { color: … !important } のように 詳細度 (1,1,0) ＋ !important で文字色を固定している。 同じ詳細度だと記述順で勝敗が決まり、CSSを並べ替えただけで発色しなくなる。

3.3 入れ子を作らせない

{赤:{青:…}} という入れ子は解釈できない。 走査パターンが中身に波括弧を許さないため、外側が記法として認識されず、 波括弧がそのまま本文に出てしまう。

入れ子を解釈できるようにする案もあったが、色の入れ子には意味が無い（内側が必ず勝つ）ため、 パーサを複雑にする価値がない。代わりに入口の側で入れ子を作らせないことにした。 expandOverColorNotation() が、選択範囲を囲んでいる既存の色記法まで範囲を広げてから 囲み直す。結果、色の付いた文字を選んで別の色を押すと「付け替え」になる。

同じ理由で、色記法は1行に閉じる（走査パターンが改行を含まない）。 閉じ忘れた波括弧が後続の段落まで飲み込むと、被害が書いた場所から離れて原因が分からなくなる。

3.4 色として解釈できない名前は変換しない

{注:これは色ではない} のように、色名でも16進でもないものは記法として扱わず原文のまま残す。 本文に波括弧を書くこと自体は珍しくないため、取りこぼしより誤変換のほうが害が大きいという判断。 誤変換は書いた本人が気付きにくい。

3.5 装飾はブロックのレイアウトを壊しうる

インライン装飾を入れたことで、本文が「ただのテキスト」ではなくなった。 どのブロックの中にも <span> が現れうる。 プレビューのブロックを組むときは、この前提を崩さないレイアウトを選ぶこと。

本文を直接載せる要素に display: flex を使ってはいけない。 フレックスコンテナでは、子要素はそれぞれ独立したフレックス項目になり、 地のテキストだけが匿名の項目にまとめられる。 そのため あああ<span>色</span>いいい は3つの項目に割れ、 文が分断されて並び順まで崩れる。

探索可能箇所を縦並びにしたとき、目印（▶）を出すために 項目を display: flex にして実際にこれを踏んだ。 目印は絶対配置にして、項目そのものは display: block のままにしてある。 レイアウトのためにフレックスを使いたくなったら、 本文を内側の要素で1段包んでからにすること。

3.6 マイパレット — 自分の色を登録しておく（2026-10-05 追加）

任意色（§3.1）を何度も使う書き手のために、色を登録しておけるマイパレットを置いた。 色を選べる場所（文字色の画面・NPCのセリフの色）のすべてで同じ一覧を使う。 登録した色を押すと、文字色では {#rrggbb:…} で囲み、NPCではその色をセリフの色にする。 記法そのものは変わらない（マイパレットの色は16進の任意色として書かれる）。

決めたこと理由
シナリオではなくこの端末の設定（localStorage の trpg_my_palette）に持つ 好みの色はシナリオをまたいで使うもの。ショートカットや判定の自由枠と同じ扱い（03 §3.1）。本文に書かれた色はシナリオ側に残るので、パレットを消しても本文の色は消えない。
色だけを持ち、名前は付けない 登録の手間を増やさないため。色の値は吹き出しに出る。名前が要るほど意味の決まった色なら、固定パレットの色名を使うほうがよい（§3 の DO）。
固定パレットと同じ色・登録済みの色は登録しない 同じ色が2か所に並ぶと、どちらを押しても同じなのに見分けが要る。固定パレットの色は色名で書けるので、そちらを使ってもらう。
24色まで 並べて見分けが付く数。超えたら「整理」で減らしてもらう。
削除は「整理」を押してから色を押す 指で操作するので、常に × を出すと押し間違える。整理中だけ × を重ねて、押すと消える状態にする。
  • 読み込むときは #rrggbb だけを受け付ける（normalizeNpcColor()）。色は style 属性へそのまま載せるので、壊れた値や任意の文字列を通さない。
  • どこかで登録・削除したら、画面にある色の欄をすべて描き直す（refreshMyPalettes()）。文字色の画面は開くたびにも描き直す。
  • 色を選べる場所を新しく足すときは、マイパレットも付けること。 その場所を data-mp-ctx="名前" の要素で包み、onMyPaletteAction()（押したときの動き・登録する色の取り方）と refreshMyPalettes()（描き直し）にその場所の処理を足す。操作は data-mp-act の委譲で受けるので、ボタンに処理を書かなくてよい。

4. 変換の順序 — エスケープ → 装飾 → 改行

プレビュー用HTMLを組み立てる順序は3段で固定されている。 この順序は decorate()（エスケープ済みの文字列を受け取る）と renderInline()（生の文字列を受け取る）に閉じ込めてあり、 呼び出し側で手書きしない。

  1. escapeHTML() — 本文中の < や & を無害化する
  2. decorate() の装飾 — 目印とリンク、ルビの <ruby>、太字の <strong>、色の <span> の順に生成する（目印とリンクが先の理由は §15.6、ルビは §13.3、太字は §14.2）
  3. 改行の <br> 化
順序を入れ替えると必ず壊れる。 装飾より後にエスケープすると、生成した <span> ごとエスケープされてタグが本文に出る。 改行を先に <br> にすると、そのあとのエスケープで <br> が無効化される。

これは机上の心配ではない。NPCカードのメモ欄は実際にエスケープが漏れており、 HP<5で逃走 という普通の記述で文字が消えていた。 同じ3行を7箇所に書き写していたことが原因であるため、 関数に閉じ込めて書き写せないようにした。

4.1 二重エスケープにも注意する

parseElement() は先頭で本文全体を1回エスケープし、以降はその文字列を切り出して使う。 切り出した断片を再度 escapeHTML() に通すと二重エスケープになり、 A & B が画面に A &amp; B と表示される （探索一覧の項目と判定の提示タイプで実際に起きていた。2026-09-01 に修正）。

DO

parseElement() の中で断片を出力するときは decorate() を使う。 エスケープ済みであることが関数名から分かる。

DON'T

escapeHTML() を「念のため」重ねる。 安全側に倒したつもりで、表示が壊れる。

4.2 SVGの中だけは decorate() を通さない（2026-09-08 追加）

[場面図] のように、出力がSVGになる記法では escapeHTML() だけを通し、decorate() は通さない。 能力値のレーダーチャートも同じ扱いである。

decorate() が作る <span> と <br> は、 どちらもSVGの中では効かない。SVGでは色は fill 属性、 改行は <tspan> で表す。通しても描画されないか、要素ごと無視される。

これは順序ルールの例外である。ここに書き残しておかないと、 「順序ルールに従っていない」と見えて後から decorate() を足され、図が壊れる。

結果として、SVGで描く部分では文字色の記法が効かない。 詳細は 06 場面ツリー設計書 §9.3 にある。

5. 判定ブロックの結果を複数行にする

判定ブロック（[判定:…] / [SAN:…]）の結果テキストは、 - で始まらない行を直前の項目の続きとして連結する。 

[判定:目星]
- 成功: 引き出しの奥に鍵を見つける。
  鍵には「B-3」と刻印がある。   ← 直前の「成功」の続きになる
- 失敗: 何も見つからない。

5.1 なぜ継続行方式か

この方式だけが既存のシナリオを壊さないため。 改修前のパーサは - で始まらない行を continue で読み飛ばしていた。 つまりこの位置に書かれた文字はもともと画面に出ていなかった。 継続行として拾うようにしても、表示が変わるのは「消えていた文字が出るようになる」方向だけである。

却下した案理由
\n のようなエスケープ記号 書き手が改行を「文字として」打てない。エディタで見た形とプレビューの形が乖離する。
継続行の先頭に専用記号（| など）を要求する 覚える記号が増える。素直に改行して字下げする書き方が既に自然に行われていた。
結果テキストを別のブロック記法にする 1つの判定が複数のブロックに割れ、プレビューの箱も割れる。
判定ブロックの終わりには空行を置くこと。 段落は空行で区切られるため、判定ブロックの直後に空行を置かずに本文を続けると、 その本文が最後の結果行の続きとして箱の中に取り込まれる。 改修前は読み飛ばされて消えていたので、古いシナリオにこの書き方が残っている可能性がある。

5.2 結果のラベルを押すと、その結果の文をコピーする（2026-10-14 追加）

判定ブロック（技能判定・SANチェック）の結果のラベル（「成功」「効果的成功」などのバッジ）を押すと、 その結果の文だけがコピーされる。GMは判定の結果をチャットに貼ってPLへ伝えるため（2026-10-14 の要望）。

決めたこと理由
ラベルそのものをボタンにする（<button class="result-label">） 結果ごとに「📋 コピー」のボタンを並べると、1つの判定に3〜5個のボタンが増え、紙面が操作の部品で埋まる。 ラベルは結果の行ごとに必ず1つあり、押す場所として迷わない。紙面の見た目はバッジのままなので、印刷・PDFにもそのまま出る。 押せることは、マウスを乗せたときの縁取りと吹き出し（「押すと、この結果の文をコピーします」）で示す。
コピーするのは結果の文だけ。ラベル（「成功」）や技能名は付けない PLはダイスの結果をすでに見ているので、チャットに要るのは「何が起きたか」の文だけ。 情報のコピーが「【題名】」を付けるのは、何の資料かが受け取った側に分からないため（§9.4）で、判定の結果には当たらない。
描いた文字から取る（rollResultCopyText()）。改行（<br>）は改行に戻す 文字色の記法はすでに外れている（探索可能箇所のコピーと同じ）。複数行の結果（§5）も、改行したままチャットに貼れる。
押したときの表示は「✓ コピー済」と短くする（.copy-compact） ラベルの幅は80pxに決まっていて、情報と同じ「✓ コピーしました」は収まらない。1.5秒で元のラベルに戻るのは情報のコピーと同じ。
  • ダブルクリックで原文へ戻る操作は、ボタンの上では働かない（11 §3.3）。結果の文のほうをダブルクリックすれば原文へ戻れる。
  • HTML出力でも残り、書き出したファイルでコピーできる（12 HTML出力設計書 §2・§5.1）。

5.3 判定を提示する条件 — 条件: の行（2026-10-15 追加）

[判定:目星/提示推奨]
条件: 探索者が本棚について言及したら
- 成功: 本の間に手紙が挟まっている。
- 失敗: 何も見つからない。

判定ブロック（技能判定・SANチェック）の見出しの次に 条件: で始まる行を書くと、 GMがいつその判定を出すか（トリガー）が、見出しと結果のあいだの「条件」の帯に出る（2026-10-15 の要望）。 それまでは [KP] の段落に「叔父の話になったら、次の説得を提示してください」のように書いており、判定の箱と条件が離れていた。

決めたこと理由
見出しの次、結果の行（- で始まる）より前に書く この位置の文は、以前は捨てていた（parseRollResultLines() の「ヘッダ直後の書きかけ」）。ここを読むようにしても、今までの台本の見え方は変わらない（§5.1 と同じ考え方）。 結果の行より後ろに 条件: と書いても、今までどおり直前の結果の続きになる。
頭の語は 条件:（全角の ： も可）。語の無い行は条件にしない 結果の行（- 成功:）とは頭の記号で見分けられ、原文で読んでも意味が分かる。条件: より前の文は今までどおり捨てる（書きかけのメモが紙面に出ないように）。
条件: の行は何本でも書ける。行ごとに「条件」のラベルを付けて並べる 「叔父の話になったら」「鷹野が手帳を取り出したら」のように、きっかけが複数ある判定がある。「または」などのつなぎは書き手が文で書く。
条件: の行のあとの、- で始まらない行は、その条件の続き（改行して出る） 結果の行の続き（§5）と同じ書き方。
帯は琥珀の地で、ラベルの幅を結果のラベル（80px）と揃える 条件はGMだけが読む注意書きなので、GM向け情報（[DL]/[KP]）と同じ色の系統にした。ラベルの幅を揃えると、条件の文と結果の文の頭が縦に揃い、1つの表のように読める。 ラベルはコピーのボタンにしない（条件はPLに伝えるものではない）。
SANチェックでも同じように書ける 「遺体の顔を覗き込んだら」のように、SANチェックにもきっかけがある。結果の行の読み方を技能判定と共用しているので、条件も共用した（rollConditionsHTML()）。
却下した案理由
結果の行と同じ形の - 条件: …原文では結果の1つに見える。「条件」という名前の結果の枠も作れなくなる。
見出しの3つ目に書く [判定:目星/提示推奨/本棚に言及したら]長い文や /・] を含む条件が書けない。提示タイプを省くと [判定:目星//…] になる。

どの書き方にするかは利用者に選んでもらった（2026-10-15）。

  • 入口: 技能判定の画面の「提示する条件」、SANチェックの画面の「チェックする条件」に書くと、見出しの次の行に 条件: … が入る。欄は複数行で、1行が1つの条件になる（readRollConditions()）。
  • 条件の中でも文字色・太字・ルビが使える。

5.4 判定の画面で直す（2026-10-15 追加）

プレビューの判定の箱（技能判定・SANチェック）をダブルクリックすると、技能判定（SANチェック）の画面が「直す」形で開く。 技能名・提示タイプ・条件・結果の枠と文が入った状態で開き、決定すると本文のその判定がまとめて書き換わる（Ctrl+Z の1回で戻る）。 表（13）と同じく、記法のまま直すより欄に分かれているほうが直しやすいため（2026-10-15 の要望）。

決めたこと理由
判定の箱のダブルクリックは、原文へ飛ばずに画面を開く。画面の「原文へ」で本文のその判定へ移れる 表と同じ扱い（11 §3.4）。原文で直したいときの道も残す。
結果のラベル（押すとコピーするボタン）の上のダブルクリックでも開く ボタンの上のダブルクリックは本来の動きに任せる決まり（11 §3.3）だが、ラベルは箱の中でいちばん目立つ所で、ここを押して「開けない」と感じる。1回押せばコピーになるのは変わらない（ダブルクリックでも2回コピーされるだけで害は無い）。
画面に結果の文の欄を足した。チェックした枠ごとに1つ（並びはチェック欄と同じ）。新しく入れるときも書ける 直すには文が要る。新しく入れるときは空のままでよい（今までどおり - 成功: だけが入り、あとで本文に書ける）。チェックを外して付け直しても、打った文は消さない（rollResultTexts）。
下部パネルの「🎲 技能判定」は、カーソルが判定の中にあっても新しく入れる（表の「📊 表」はカーソルが表の中なら直す） 判定は1つ書き終えた直後に、続けて次の判定を入れることが多い。そのときカーソルはまだ前の判定の中にあり、直す形で開くと邪魔になる。
書き換えるのは、段落の >> より前（判定の部分）だけ。右の段はそのまま残す 判定の段落に、右の段で「誰が判定するか」などを添えることがある（data-part の範囲を使う。11 §3.1）。
紙面に出ない行（条件: より前のメモ・コロンの無い - の行・見出しの ] の後ろの文）は、そのまま残す 欄に出せないものを、直したついでに黙って消さない（parseRollSource() が持っておき、buildRollSource() が書き戻す）。
画面の選択肢に無い提示タイプ・枠（本文に手で書いたもの）も残す 提示タイプはどれにも印を付けずに開き、選び直さない限りそのまま書き戻す。枠は、その判定を直すあいだだけチェック欄の後ろに足す（rollExtraTiers()。自由枠として保存はしない）。

書き戻すときに形が変わる所（どれも紙面の見え方は変わらないか、壊れる書き方を避けるためのもの）:

  • 結果はチェック欄の並び（システムの枠の順）に並ぶ。手で別の順に書いていた場合は並びが変わる。同じ枠が2つあれば、文をつないで1つにする。
  • 2行以上の条件は、1行にまとめる（欄は1行が1つの条件のため）。
  • 文の中の空行は詰め（段落が切れるため）、>> は ＞＞ に（右の段に割れるため）、続きの行の頭の - は － にする（結果の行と取り違えるため）。
  • 技能名の ] は ］ に、半角の / は ／ にする（見出しを途中で閉じる・提示タイプの区切りになるため）。SANチェックの減少値も同じ。
  • 以前の「 または 」でつないだ技能名は、／ の形になる（§5.5）。
  • 開いているあいだに書き換えを捨てて閉じようとすると（Esc・×・背景）、確かめる。新しく入れるときも、入力を変えていれば確かめる。
  • 原文の小窓（11 §4）を開いていれば、先に確定してから開く（表と同じ）。

5.5 複数の技能は「／」でつなぐ（2026-10-15 変更）

技能判定の画面で技能を複数選ぶと、押した順に ／（全角）でつなぐ（[判定:目星／聞き耳／図書館]）。 以前は「 または 」でつないでおり、3つ以上選ぶと「目星 または 聞き耳 または 図書館」と繰り返されて読みにくかった（2026-10-15 の要望）。

  • どれにするかは利用者が選んだ。「・」は短いが「どれか1つ」の意味が伝わりにくく、「最後だけ または」は長い。
  • 以前の「または」で書いた判定も、紙面では ／ の形で出す（normalizeSkillJoin()。原文は変えない）。判定の画面で直して確定すると、原文も新しい形になる。
  • 区切りは全角の ／。半角の / は提示タイプの区切りなので、手で [判定:目星/図書館] と書くと「図書館」が提示タイプのバッジになる。 判定の画面では、技能名の欄に打った半角の / を全角に直してから入れる。

6. システム固有の記法をどう扱うか

共鳴判定（エモクロア）とSANチェック（クトゥルフ神話TRPG）は、片方のシステムにしか存在しない。 これらは入口とパーサで扱いを変える。

層扱い実装
入口（パネルのボタン・コマンドパレット・ショートカット） そのシステムのときだけ出す 操作の表 ACTIONS の available が hasResonanceRoll / hasSanCheck を見る。3つの入口すべてに効く（07 操作の入口設計書 §5）
パーサ 常に受け付ける parseElement() はシステムを見ずに [共鳴:…] / [SAN:…] を解釈する
パーサを出し分けない理由。 シナリオのシステムは作成時に固定されるが、JSONで受け渡したシナリオを別システムで開き直すことは起こりうる。 そのときパーサまで出し分けていると、記法が解釈されずに [SAN:1/1D6] という文字列が そのまま紙面に出る。読めない箱より、色の違う箱のほうがましである。 GM向け情報ブロックで [DL] と [KP] の両方を常に受け付けているのと同じ考え方。

6.1 SANチェックを判定ブロックと同じ構造にした理由

SANチェックは [SAN:成功時/失敗時] のヘッダに、判定ブロックと同じ - 枠: 本文 の結果行が続く。1行のボックス（共鳴判定と同じ形）にする案もあったが、 SANチェックは成否で起きることが変わるのが本体であり、 減少値だけを示しても本文に「成功したら／失敗したら」を書き直すことになる。

結果行のパースは parseRollResultLines() で技能判定と共用している。 複数行対応やバッジの色分けが片方だけ古くなるのを防ぐため。 一方で枠の一覧は分けて持つ（rollTiers と sanTiers）。 SANチェックに「スペシャル」は無く、成功・失敗の2つで足りることが多いため。

配色は赤系。骨格が技能判定と同じである以上、 色だけが「この箱は普通の判定ではない」という手掛かりになる。 青い技能判定の箱がいくつも並ぶ紙面で、危険な判定を拾えるようにするため。 共鳴判定（resonance-box）も赤系だが、 あちらはエモクロア専用・こちらはCoC専用で、同じシナリオに両方が出ることはない。

7. 記法を足すときに触る場所

1つでも漏れると「ボタンからは入るがプレビューに出ない」「記法は効くが入口が無い」状態になる。

7.1 ブロック記法を足す場合

  • 変換をどちらに置くか決める — 本文カラムに収まる記法は parseElement()、 紙の幅いっぱいを使う記法は parseMarkdown()（下の注意を参照）
  • insertTemplate() または専用モーダル — 記法を組み立ててカーソル位置に入れる
  • ACTIONS に1行 — 下部パネルのボタン・コマンドパレットの候補・ショートカット・設定画面の名前がここから作られる。 書く項目は 07 操作の入口設計書 §6
  • システム固有なら GAME_SYSTEMS のフラグと、ACTIONS の available
  • parseMarkdown() に全幅のブロックを足したなら、描いた要素に原文での範囲（withSrcAttrs(html, src)）を付ける。 付けないと、その部分はプレビューのダブルクリックで原文へ戻れない（11 プレビュー連携設計書 §3.1。 parseElement() に足す記法は、本文の段の要素に付いているので要らない）
  • 記法の中にボタンなどの操作を置くなら、HTML出力で残すかを決める。書き手向けなら .no-print を付けるだけで書き出しから外れる。 読み手も使うなら EXPORT_KEEP_SELECTOR に足し、書き出したファイルで動く処理を用意する （12 HTML出力設計書 §2.1・§9）。紙面のCSSは #preview-area を付けて書く（同 §3）
  • 要件定義書 §4 の記法一覧
全幅で使いたい記法を parseElement() に足さないこと（2026-09-08 追記）。 parseElement() が返したものは本文カラム（幅72%）の中に入る。 図や表のように横幅を必要とするものは、紙に出したときの有効幅が130mm程度まで狭くなる。 見出しや [場面図] と同じく、parseMarkdown() のブロック処理に足して 段組みの外へ出すこと。

そのとき、扱う文字列のエスケープ状態が変わる点に注意する。 parseElement() は先頭で1回エスケープした文字列を扱うが、 parseMarkdown() のブロックは生の文字列である。 両方の入口で同じ引数（場面名など）を解釈すると、 & を含む値のときだけ結果が食い違う。 片方の入口では引数を読まないようにするのが安全である。

7.2 インライン装飾を足す場合

傍点・マーカーなどを足すときも { } の系統に載せる（太字だけは例外として **太字** にした。理由と、これ以上例外を増やさない決まりは §14.1）。 decorate() の走査パターンは {名前:中身} という形しか見ておらず、 名前が色として解釈できなければ素通しにしているので、 名前の解決を色以外にも広げるだけで足せる。

ただしこれは名前1つで決まる飾りに限る。ルビ（§13）は親文字と読みの2つを持つので、 {名前:中身} の形に収まらず、別の走査パターン（INLINE_RUBY_RE）で足した。区切りが : と | で違うので、色の記法とは見分けられる。

装飾を増やす前に、入れ子を許すかどうかを決めること。 現状は「入れ子は解釈しない・入口で作らせない」で統一している（§3.3）。 色だけなら入れ子に意味が無いので成立するが、 {傍点:{赤:…}} のような組み合わせに意味が出た時点でこの前提は崩れる。 そのときは走査パターンを1段深くするのではなく、 装飾を並べて書ける形（例: {赤+傍点:…}）を先に検討すること。 入れ子を許すと、閉じ忘れの被害範囲が段落全体に広がる。 （色と重ねる意味のあるルビと太字は、走査を深くせずに解いた。ルビは変換の順序で（§13.3）、太字は波括弧を使わない記号で（§14.1）。）

8. NPCのセリフ — [セリフ:NPC名]（2026-10-05 追加）

[セリフ:黒川 沙耶] 「あなたも、あの夜を見たの？」

[セリフ:黒川 沙耶/震える声で] 「……見たのね」      ← 「/」の後ろは備考（§8.5）

[セリフ：田中 & 佐藤]
「二人で来たんだ。」
「{赤:帰り道}は覚えている？」

段落の先頭に置くと、その段落がNPCの発言になる。 左にそのNPCのアイコン（立ち絵。無ければ名前の1文字目）、上に名前を出し、 発言はNPC管理の基本タブで決めたそのNPCの色で出す。 タグの後ろに続けても、次の行から書いてもよい。コロンは全角・半角のどちらでもよい。

8.1 なぜ専用のブロック記法にしたか

それまでNPCの発言は > 「…」 >> [NPC:名前] （情景描写の行＋サイドビューの小さなNPCカード）で書いていた。 誰の発言かを示すのが右の段のカードだけで、発言そのものには話し手の手がかりが無かった。 発言とサイドビューのNPCカードは役割が違う（前者は読み上げる台詞、後者はNPCの資料）ので、 カードを流用せず、発言の側にアイコンと名前を持たせた。 サイドビューのカードは、その場面で初めて話すときに資料として添えるだけにした（§8.6）。

案却下した理由
>（情景描写）の行頭にNPC名があれば発言とみなす 地の文の「黒川は言った」のような行まで発言に化ける。位置や中身で意味が変わる規則は、書き手が結果を予測できない（§2.1 と同じ理由）。
@黒川 沙耶「…」 のような新しい記号 ブロック記法は [ ]、インライン記法は { } という系統分け（§2）の外に、3つ目の系統を作ることになる。
インライン記法 {セリフ:黒川:…} 発言は段落を単位に、アイコン付きの箱として出すもので、文中の一部を飾るものではない。複数行の発言も書けなくなる。

以前の書き方（> 「…」 >> [NPC:名前]）で書かれた本文は、これまでどおりの表示のまま使える。 NPC管理の「🗣️ セリフ用タグ」が挿入するものだけを、新しい記法へ切り替えた。

8.2 色はNPCが持つ

色は記法の引数ではなく、NPCのデータ（npc.color）として持つ。 発言のたびに色を書かせると、同じNPCの発言で色がばらつき、後から変えるときに全部を直すことになる。 NPCで持てば、色を変えると本文中のそのNPCの発言がすべて追従する。

  • 候補は文字色と同じパレット6色を先に並べ、任意の色は最後に置く。 印刷して読める濃さを保証できるのはパレットの色だけだから（§3）。 基本タブには白地での見本を出し、淡い色の読みにくさを選ぶ時点で分かるようにしている。
  • 色は style 属性へそのまま載せるので、読み込み時に #rrggbb 以外を捨てる（normalizeNpcColor()）。 インポートしたJSONに任意の文字列が入っていても、CSSを差し込ませないため。
  • プレビューへは CSS 変数 --npc-color で渡し、名前・発言・アイコンの縁で共有する。 色が未設定なら、各所は既定の色（本文と同じ色・灰色の縁）に戻る。 発言の中の {赤:…} は、その部分だけがさらに上書きされる。

8.2.1 見た目は「台本の1行」にする（2026-10-05 改訂）

最初は情景描写（>）にならい、薄い灰色の箱に入れ、左にNPCの色の線を引いていた。 これをやめ、箱・左の線・内側の余白を付けない形に改めた。

  • 会話は何往復も続く。1発言ごとに箱と余白（箱の外16px＋段落の16px＋箱の中10px）が付くと、 数行の会話が画面の大半を占め、流れを追えなかった。
  • 左の線は、誰の発言かをアイコン・名前・色で示していることの繰り返しで、 書き手から見て「何のための線か」が読み取れなかった。意味の説明できない装飾は置かない。
  • セリフが続くあいだだけ段落の間隔を約8pxに詰める （.row:has(セリフ) + .row:has(セリフ) に負の上余白を付け、段落の下余白と相殺させる）。 地の文との間は通常の段落と同じ間隔のままにして、会話のまとまりが目で区切れるようにしている。
  • サイドビューの小さなNPCカードは段落の行の高さを決めてしまうので、下余白を外してある。 カードはセリフ1行より少し背が高いので、カードが付く段落（その場面の初登場）だけ、わずかに間隔が広がる。

8.3 名前の照合とエスケープ

parseElement() が扱う文字列はエスケープ済みなので、記法から取り出したNPC名もエスケープ済みである。 NPCの名前と比べるときはNPC側もエスケープしてから比べる（escapeHTML(n.name) === name）。 生の名前と比べると、「田中 & 佐藤」のように & を含む名前のNPCが見つからない。 [NPC:名前] のカードはまさにこの比べ方をしていて、該当するNPCが「未登録」と表示されていた（同日に修正）。

登録されていない名前でも、発言そのものは出す。名前の横に「未登録のNPC」の印を付けるだけにしている。 NPCを登録する前に本文を書き進めることは普通にあり、そのたびに台詞が紙面から消えるほうが困るため。

8.4 入口

入口は2つあり、どちらも insertNpcSpeech() で [セリフ:NPC名] 「」 を入れ、カーソルを「」の間に置く。

入口使う場面
NPC管理の「🗣️ セリフ用タグ」 NPCを編集しているついでに、そのNPCの発言を入れる
「🗣 NPCのセリフ」（下部パネル・コマンドパレット・Alt+Q）→ NPCを選ぶ画面 本文を書いている途中で発言を入れる。NPC管理を開かずに済む

記法を入れる前にどのNPCかを決める必要があるが、ACTIONS は引数を取らない操作しか表せない。 そこで ACTIONS には「選ぶ画面を開く」操作として載せ、NPCは開いた画面で選ばせている （07 操作の入口設計書 §6）。 選ぶ画面の見た目と操作（名前で絞り込み・↑↓・Enter）はコマンドパレットと揃え、キー操作の処理も共用している（bindChooserList()）。 選ぶ画面には備考欄があり、絞り込み欄から Tab で移れる（§8.5）。

8.5 備考 — [セリフ:NPC名/備考]

タグの中の最初の /（全角の ／ も可）より後ろは備考になる。 「震える声で」「小声で早口に」のような、GMへの読み上げ方の指示（ト書き）を書くためのもので、 名前と発言の間に灰色の小さな文字で出す。発言の一部ではないので、発言の色にはしない。 

[セリフ:黒川 沙耶/震える声で。
途中で一度言葉に詰まる] 「あなたも、あの夜を見たの？」
  • 備考は改行してよい（2026-10-05 追加）。タグの中の改行を許している（SPEECH_TAG_RE）。 色記法は1行に閉じる（§3.3）のに、こちらを許したのは、ブロック記法が見るのは1つの段落（空行で区切られた単位）だけで、 閉じ忘れてもその段落の外へ被害が広がらないため。 ただし備考の中に空行は書けない。空行で段落が分かれ、タグが閉じないまま切れて、記法がそのまま紙面に出る。
  • 最初は名前の横に小さなラベルとして出していたが、複数行に対応したときに名前の下の行へ移した。 ラベルでは2行目以降の置き場所が無い。1行の備考も同じ見た目にそろえている。 枠付きの欄にした時期もあったが、セリフ全体を詰めたとき（§8.2.1）に枠を外し、色と文字の大きさだけで発言と分けている。
  • 区切りを / にしたのは、[NPC:名前/簡易] と同じ書き方にそろえるため。 その代わり、NPC名に / は使えない（[NPC:] と同じ制約）。
  • 発言の本文に「（震える声で）」と書く案は採らなかった。読み上げる台詞と、読み上げない指示が同じ色・同じ書体で並ぶと、 GMがセッション中にうっかり指示まで読み上げる。
  • 備考の中でも文字色の記法は使える（エスケープ済みの断片なので decorate() を通す）。
  • 選ぶ画面の備考欄は複数行の欄で、Enter で挿入、Shift+Enter で改行する。 入れるときは、タグを途中で閉じてしまう ] を取り除き、空行を詰める（上の理由）。

8.6 サイドビューのNPCカードは、場面ごとに初めて話すときだけ出す

[セリフ:NPC名] の段落で、サイドビュー（>> の右の段）に何も書いていなければ、 そのNPCの小さなNPCカードを自動で添える。ただし同じ場面ですでにカードを出したNPCには出さない。 場面の区切りは #（シーン見出し）で、##（探索小見出し）では区切らない。

サイドに [NPC:名前] と手で書いたカードにも、同じ「場面ごとに1回」の規則を当てる。 以前のセリフ用タグは発言のたびに >> [NPC:名前] を入れていたので、 既存の本文では同じカードが発言ごとに並び、右の段を埋めていた。 カードの役目は「この人は誰か」を示す資料であり、その場面での初登場の位置で一度示せば足りる。

場合サイドビュー
その場面で初めて話す（自動・手書きのどちらでも）小さなNPCカードを出す
同じ場面で2回目以降出さない（空ける）
サイドに補足など別のものを書いた段落書いたものを出す（その段落ではカードを出していないので、次の発言で出る）
未登録のNPCのセリフ出さない（本文側に「未登録のNPC」の印が出ている）
サイドに手書きした未登録のNPCの [NPC:名前]従来どおり「未登録」の警告を出す
この判定は parseMarkdown() が段落を順に処理しながら行う（resolveSideNpcCard()）。 ここは未エスケープの生文字列を扱う側なので、NPC名は生のまま比べる（§8.3 の parseElement() 側とは逆）。 本文の段に置く通常のNPCカード [NPC:名前] は資料そのものなので、この規則の対象外であり、毎回表示する。

8.7 発言のコピー（2026-10-14 追加）

名前の行の後ろに「📋 コピー」のボタンを置き、押すとその発言だけがコピーされる。 GMはセッション中、NPCの台詞をチャット（ココフォリアなど）に貼って演じるため（2026-10-14 の要望）。

決めたこと理由
名前の行に、文字の付いたボタンを置く（情報・探索可能箇所と同じ .info-action を小さくしたもの） 情報・探索可能箇所（§9.4）と同じ「📋 コピー」なので、何をするボタンかが見て分かる。 会話では何行も並ぶので、名前の行に収まる大きさにし、色を淡くして発言より目立たせない（マウスを乗せると同じ青になる）。 名前の行の高さはほぼ変わらないので、セリフを詰めた並び（§8.2.1）も崩れない。
紙面には出さない（.no-print）。HTML出力では残す 情報・探索可能箇所のコピーと同じ扱い。印刷・PDFでは名前だけの元の見た目になる。
コピーするのは発言だけ。名前と備考は付けない チャットではNPCとして発言する形で貼るので、名前は貼った側のツールに出る。 備考（§8.5）はGMへの読み上げ方の指示で、PLに見せるものではない。 発言に書いた「」は、書いたとおりにコピーする（付けるかどうかは書き手が本文で決める）。
描いた文字から取る（speechCopyText()）。改行は改行に戻す 判定の結果（§5.2）と同じ関数（renderedCopyText()）を使う。文字色の記法は外れ、複数行の発言も改行したまま貼れる。
却下した案理由
名前そのものをボタンにする（判定の結果のラベル §5.2 と同じ作り） 一度この形で作ったが、「直感的に分からない」と利用者から指摘された（2026-10-14）。 判定の結果のラベルはバッジの形で押せそうに見えるが、名前はただの文字で、マウスを乗せるまで押せることが分からない。
マウスを乗せたときだけボタンを出す 乗せるまでボタンがあることが分からず、上と同じ問題が残る。タッチの端末では出す手段も無い。
アイコン（立ち絵の丸）を押すとコピー 名前と同じく、押せることが見て分からない。押したときの表示（「✓ コピーしました」）をボタンの文字で出す仕組み（copyWithFeedback()）なので、文字を載せる場所の無い丸には合わない。
  • 以前の書き方（> 「…」 >> [NPC:名前]。§8.1）の発言には名前の行が無いので、ボタンは付かない。
  • HTML出力でも残り、書き出したファイルでコピーできる（12 HTML出力設計書 §2・§5.1）。

9. プレイヤーへ渡す情報 — [情報:題名]（2026-10-05 追加）

[情報:古い日記]

日記・手紙・調べて分かったことなど、セッション中にプレイヤーへ渡す情報を台本に載せる記法。 GMは台本を読みながら、該当する情報をコピーしてチャット（ココフォリアなど）に貼る。 既存の [DL]／[KP] は「GMだけが読む情報」であり、役割が逆なので別の記法にした。

9.1 中身は情報一覧に持ち、本文には参照だけを書く

情報の中身（題名・公開対象・本文）は、シナリオのデータ infos: [{ id, title, target, body }] に持つ。 本文には [情報:題名] と参照だけを書き、プレビューで中身を展開する。NPCと [NPC:名前] の関係と同じである。

  • 情報は「一覧で管理し、書くときは一覧から選んで入れる」使い方を前提にしている（2026-10-05 の要望）。 本文に中身を直接書く方式だと、一覧は本文から拾い集めた写しになり、一覧から追加・編集できない。
  • 中身を本文に書かないので、情報の本文には空行を含められる。 本文に直接書く方式では、空行で段落が分かれてブロックが切れるため、終わりの印（[/情報] など）が必要になる。
  • 同じ情報を複数の場面で参照してよい（手紙を二度読み返す場面など）。中身は1か所なので、直せばすべての参照に効く。
案却下した理由
本文に [情報:題名/公開対象] と中身を直接書き、一覧は本文から拾い集める 一覧から追加・編集ができない。複数段落の情報には終わりの印が要り、書き忘れると後続の段落まで飲み込む。最初はこの形で設計したが、一覧から追加・選択したいという要望を受けて切り替えた。
参照を題名ではなく id で書く（[情報:#a1b2]） 本文を読んで何の情報か分からない。題名の変更には §9.3 の書き換えで追従できる。

9.2 公開対象

公開対象は自由入力で、入力欄に候補（「全員」と、そのシナリオで使った対象）を出す（<datalist>）。 「HO1」「目星成功者」のように、シナリオごとに呼び方が違うので、決め打ちの選択肢にはしなかった。 プレビューと一覧ではバッジで出し、色を3通りに分ける。

公開対象バッジ理由
全員緑そのまま全体チャットに貼ってよい
それ以外（HO1・目星成功者など）琥珀貼る先（秘匿チャットなど）に注意が要る
未設定赤「公開対象 未設定」決め忘れに気づかせる
新しく作った情報の公開対象は「未設定」にする。「全員」を既定にしない。 既定を「全員」にすると、秘匿のつもりで作った情報を、決め忘れたまま全員に送る事故が起こりうる。 取り返しがつかないのは「送ってしまった」ほうなので、赤いバッジで目立たせて決めてもらう。

9.3 題名は参照のキー

  • 一覧で題名を変えると、本文の [情報:旧題名]（全角コロンの書き方も）を [情報:新題名] に書き換える（commitInfoTitle()）。 書き換えは入力中ではなく確定したとき（change）に行う。入力のたびに反映すると、打っている途中のプレビューで参照が「未登録」にちらつく。
  • 空の題名と、ほかの情報と同じ題名は受け付けず、元に戻す。どちらも参照を1つの情報に解決できなくなるため。
  • 参照先が見つからない [情報:題名] は、プレビューに「登録されていません」と出し、その場で登録できるボタンを付ける。 情報を削除するときは、本文で何か所参照しているかを確認の文に出す。
  • 照合はエスケープ済みの文字列どうしで行う（§8.3 と同じ理由）。

9.4 コピー

  • コピーされるのは「【題名】」の行＋本文。チャットに貼ったとき、何の情報かが受け取った側に分かるようにするため。 文字色などの記法は取り除く（チャットでは装飾にならず、記号のまま残る）。
  • Clipboard API が使えない環境（安全でない文脈など）では、一時的な textarea を選択してコピーする古い方法に落とす。 押したボタンに「✓ コピーしました」を1.5秒出す。
  • コピーボタンはプレビューと一覧の両方に置き、印刷・PDFには出さない（公開対象のバッジは、GMの手元資料として紙にも残す）。HTML出力では残り、書き出したファイルでもコピーできる（12 HTML出力設計書 §5.1。2026-10-10）。
  • 探索可能箇所一覧（[探索:エリア名]）にも同じコピーボタンを置く（2026-10-09 追加）。 GMは「調べられる場所」もチャットでプレイヤーに示すため。コピーされるのは「【探索可能箇所：エリア名】」の行＋項目を「・」付きで1行ずつ （エリア名を書いていない [探索] では「【探索可能箇所】」）。 項目はプレビューに描いた文字から取るので、文字色の記法はすでに外れている。押したときの表示・古い方法への切り替え・印刷に出さないことは情報と同じ。

9.5 入口と情報一覧パネル

入口できること
「📄 情報」（下部パネル・コマンドパレット・Alt+I）→ 選ぶ画面 登録した情報を、題名・公開対象・本文の言葉で絞り込んで挿入する。 まだ無い題名を打てば、その場で登録して挿入し、中身を書けるよう情報一覧で開く。 新規登録の候補は一致した情報の後ろに置く（先頭だと、公開対象の言葉で探して Enter を押したとき、その言葉を題名にした情報が作られる）。
「📑 情報一覧」（下部パネルの「資料」グループ・Alt+L・コマンドパレット） 情報の追加・編集・削除・コピー・本文への挿入。題名を押すと、プレビューのその情報へ移動する。 情報は本文で最初に参照している場面（# 見出し）ごとにまとめ、参照していない情報は最後にまとめる。
  • 情報一覧はエディタ側（左）に重ねて開く。セッション中は右の台本を読みながら使うので、台本を隠さない側に置いた。 縦画面（768px以下）ではエディタとプレビューが上下に並ぶので、全幅で開く。
  • 開閉ボタンは下部パネルの「資料」グループに、NPC管理と並べて置く（v1.9.1）。 どちらも「シナリオの資料を管理する」入口だから。開いている間はボタンを押された状態に見せる。 v1.9.0 ではプレビュー上端に細い帯を作ってボタンを置いたが、プレビューは台本の紙面を見る場所であり、 そこに操作が混ざるのは不自然だったため移した（操作のボタンは下部パネルに集めるという既存の配置にも反していた）。
  • 一覧の外をクリックすると閉じる（Esc・×・開閉ボタンでも閉じる）。ただし開閉ボタン自身と、モーダル（選ぶ画面など）の中のクリックは除く。 開閉ボタンを除くのは、パネルのボタンが mousedown で実行されるため。除かないと、開いた直後の click を外側のクリックとして受け取り、すぐ閉じてしまう。 外側のクリックで閉じたときは本文へカーソルを戻さない（シナリオ名の欄などをクリックした場合に、その入力を奪わないため）。 判定はクリックの捕捉段階で行う。一覧の「編集」などは一覧を作り直すので、ボタン側の処理が先に走ると、 押した要素がもう画面に無く「外側のクリック」と誤判定する。
  • 一覧は本文の変更に追従して作り直すが、一覧の中で入力している最中は作り直さない（フォーカスと入力途中の文字が失われる）。 そのあいだは、入力しているカードの見出し行（公開対象のバッジ・本文の冒頭）だけを書き換える。
  • どの場面で参照しているかは、本文を parseMarkdown() と同じ規則（空行で段落を区切り、>> より前が本文の段）で読んで調べる（scanInfoUsage()）。

10. 目次 — [目次]（2026-10-05 追加）

[目次]

# 導入
…

本文の見出し（# と ##）と巻末の見出しから、目次を自動で作る。 見出しを足したり変えたりすれば、目次も一緒に変わる。前後を空行で挟んだ、その行だけの段落として書く（場面図と同じ）。

10.1 書いた場所に出す記法にした理由

案判断
本文に [目次] と書いた場所に出す（採用） 書かなければ今までの台本が変わらない。置き場所（ふつうは本文の先頭＝表紙の直後）を書き手が決められる。
表紙の直後に必ず出す（出す／出さないを設定で切り替える） この機能より前の台本に、ある日突然目次が増える。切り替えの設定を置く場所も要る。
画面の横に一覧を出す（印刷しない） 台本・PDFに目次が残らない。要望は「目次を作る」で、紙面の一部としての目次だった。

どれにするかは利用者に選んでもらった。載せる深さ（# と ##）と、巻末を載せるかどうかも同じ。

10.2 載せるもの

  • 本文の #（シーン見出し）を太字で、##（探索小見出し）を字下げして小さく載せる。見出しの文字だけを載せ、文字色の記法は外す。複数行の見出しは1行にまとめる。
  • 巻末のFAQと、あとがきなどの節の見出しを、本文の見出しの後ろに少し空けて載せる。権利表記は奥付なので載せない（09 巻末設計書）。
  • 見出しが1つも無いときは、プレビューにだけ案内を出す（印刷しない）。
  • 段落の途中に書いた [目次] は目次にせず、書き方の案内を出す（場面図と同じ）。

10.3 ページ番号は出さず、見出しへのリンクにする

紙の目次にはふつうページ番号が付くが、ブラウザの印刷には「この見出しが何ページ目に来るか」を知る手段が無い （CSSの target-counter() は主要なブラウザが対応していない）。そのため番号は出さず、 各項目を見出しへのリンク（href="#toc-h-0"）にした。

  • プレビューでは、押すとその見出しまでスクロールする。リンク本来の動き（アドレスの # を書き換える）は止める。アドレスに # が残ると、再読み込みのたびにそこへ飛ぶため。
  • PDFでは、目次の項目がそのまま見出しへのリンクとして残る（Chromium の PDF 出力で確認した。目次の項目の数だけ、見出しを指すリンクが入る）。
  • HTML出力（2026-10-10）では、リンク本来の動きに任せる。アドレスに # が付くが、読むための文書なので、ブラウザの「戻る」で目次へ戻れる利点を採った（12 HTML出力設計書 §5.2）。

10.4 見出しの id は「何番目の見出しか」で振る

  • 目次はふつう見出しより前に書くので、parseMarkdown() は描き始める前に見出しを拾い（collectTocHeadings()）、 描くときに同じ順で id（toc-h-0、toc-h-1 …）を見出しへ付ける。 拾うときと描くときは同じ段落の並びを同じ条件（# で始まるか）で見るので、番号はずれない。
  • 見出しの文字から id を作らなかったのは、同じ名前の見出し（各場面の「## 探索」など）が重なりうるため。 番号なら、見出しを増やしても重ならない（リンク先は描き直すたびに振り直す）。
  • 巻末の見出しは toc-faq・toc-bm-番号（あとがきなどの節の並びの位置）。巻末は本文の外で描くので、updatePreview() が appendixTocEntries() を parseMarkdown() へ渡す。
見出しの段落を判定する条件を変えるときは、collectTocHeadings() と parseMarkdown() の両方を揃えること。 片方だけ変えると番号がずれ、目次の項目が別の見出しへ飛ぶ。

11. 右の段（>>）は本文の段落の横に並べる（2026-10-06 追加）

探索者が扉を開けると、冷たい風が吹き込む。

>> [TIPS] 風は地下室から吹いている。

本文は段落ごとに「本文の段（左）」と「右の段」の2列で組む。>> より後ろが右の段で、TIPS や補足を置く。 上の例のように、空行のあとに >> だけの段落を書いても、直前の本文の段落の右に並ぶ。

以前は、同じ段落の中に書いたときだけ横に並び、空行を挟むと「本文の段が空で、右の段だけがある行」が単独で出ていた。 TIPS は必ず何かの本文に添える補足なので、右の段だけの行が並ぶことに意味は無い。 一方で、本文とTIPSの間に空行を入れて書くのは自然な書き方で、サンプルシナリオを書いたときにも実際にそうしていた。 書き方のほうに合わせ、どちらで書いても横に並ぶようにした。

右の段だけの段落の置き場所理由
同じ章の中で、いちばん近い前の本文の段落の右 補足は、補足する本文のあとに書くのがふつう。その段落にすでに右の段があれば、その下に積む（右の段は縦に並べられる）。
前に本文の段落が無ければ（章の頭など）、次の本文の段落の右 章の頭に書いた補足は、その章の最初の本文に添えるもの。
見出し（#・##）はまたがない 別の章の本文の横に並ぶと、何の補足か分からなくなる。章の中に本文の段落が1つも無いときだけ、今までどおり単独の行にする。
場面図・目次・表はまたぐ 全幅のブロックで右の段を持たないため。図や表の補足は、その上か下の本文の段落の横に並ぶ。
  • 実装は parseMarkdown()。段落を描くたびにHTMLを足すのをやめ、行（本文の段と右の段の一覧）を積んでから最後にまとめてHTMLにする。後から右の段を前の行へ足せるようにするため。
  • 右の段に複数のもの（小さなNPCカードとTIPS、TIPSが2つなど）が積まれたときは、間を10px空ける。
  • 1つの段落の中に >> を2つ書くことはできない（最初の >> より後ろはすべて右の段の文になる）。右の段に2つ置きたいときは、空行で区切った段落に分けて書けばよい。

12. 表 — [表] / [表:題名]（2026-10-14 追加）

[表:進行の目安]
| 場面 | 目安 |
| 導入 | 25分 |
| 探索 | {赤:175分} |

進行の目安・場所ごとの危険・水位の時刻表のような一覧を、罫線の表にする記法。 「導入　25分／探索　175分／…」のように1行に詰めたり、全角の空白で桁を揃えたりしていた書き方を置き換える（2026-10-14 の要望）。

  • [表] の次の行から、1行が表の1行。セルは | で区切る。両端の | は省いてよい。
  • 1行目が見出しの行になる（<thead>）。1行目か2行目に Markdown の区切りの行（|---|---|、|:-:| など）があれば、列の寄せとして読み、中身からは外す（§12.4）。
  • 列の数は、いちばんセルの多い行に揃える。足りない行は空のセルで埋める。
  • セルと題名の中で文字色（{赤:…}）が使える。題名は表の上に太字で出る（<caption>）。
  • 段落の全体が表になる。空行で表が終わる。
  • 2026-10-14 に、寄せ・セルの中の改行・見出しの指定（§12.4）と、セルの結合（§12.5）を足した。手で書かなくても、表の編集画面（13）でマス目に書いて作れる。

| 導入 | 25分 | 省けない<br>短くしない |   ← <br> でセルの中を改行

12.1 区切りの記号と見出しの行

決めたこと理由却下した案
ほかのブロック記法と同じく、段落の先頭の [表] で始める 記法の系統を括弧で見分ける決まり（§2）に揃える。題名（[表:進行の目安]）を書く場所にもなる。 | で始まる段落を自動で表にする（Markdown と同じ）。表のつもりの無い段落を表にしてしまいうる。題名を書く場所も無い
セルの区切りは |。全角の ｜ も受け付ける | は Markdown の表で広く知られている。日本語入力のまま打つと全角になるので、打ち直さなくてよいようにした。 その代わり、セルの中に縦線そのものは書けない（文字色の記法の中に書いても区切りになる。ルビの記法 {漢字|かんじ} の中の縦線だけは区切りにしない。§13.4）。 タブ区切り。エディタでタブを打つとフォーカスが移る環境があり、目でも見分けられない。 表計算ソフトから貼ったタブ区切りの行は、挿入のときに | へ直す（§12.3）
既定では1行目を見出しの行にする（/見出しなし で外せる。§12.4）。区切りの行は書いても書かなくてもよい 台本の表（進行の目安・場所ごとの危険など）は、ほぼ必ず見出しの行を持つ。「1行目が見出し」なら覚えることが1つで済む。 区切りの行を読み飛ばすのは、よそで書いた Markdown の表を貼ったときにそのまま使えるようにするため。 Markdown と同じく、区切りの行があるときだけ見出しにする。区切りの行を打つ手間が毎回かかり、忘れると見出しが本文と同じ見た目になる
区切りの行として読むのは、1行目か2行目にある、半角の - と : だけでできたセルの行の、最初の1つだけ 見出しのある表では2行目に、見出しの無い表（§12.4）では1行目に書くため。 「-」で「なし」を表す表もあるので、3行目より後ろの「| - | - |」は中身として残す。全角の「ー」も中身として扱う。 中身の最初の行が「| - | - |」になる表は、表の編集画面が区切りの行を先に書いて守る（13 §3.2）。 どの行でも区切りの行を読み飛ばす。中身の行が消える

表は場面図・目次と同じく、段組みの外に出す全幅のブロックとして parseMarkdown() が描く（§7.1 の注意どおり。 本文の段（幅72%）に入れると、紙では130mm程度しか使えず、3列以上の表が窮屈になる）。 ただし表の幅は中身に合わせる（width: auto）。2列の表が紙の端まで間延びしないようにするためで、中身が多ければ紙の幅で折り返す。

  • 段落の中に >> があっても右の段に分けない（段落の全体が表）。右の段の補足は、表の前の本文の段落に添える。 空行のあとに >> だけの段落を書いても、表をまたいで前の本文の段落の右に並ぶ（§11）。
  • 右の段（>> [表]）に書いたときは、表にせず書き方の案内を出す（場面図・目次と同じ）。
  • 中身の行が無い [表] は、プレビューにだけ書き方の案内を出す（印刷しない）。
  • 印刷では、1行の途中でページを切らず、見出しの行を次のページの頭にも出す。
  • 読みやすさのため、本文の行を1行おきに薄く塗る。ただし縦に結合したセル（§12.5）がある表では塗らない（結合したセルの途中で色が切り替わり、行を読み違える）。

12.5 セルの結合（2026-10-14 追加）

セルに < の1文字だけを書くと左のセルと、^ の1文字だけを書くと上のセルと1つになる。 左上のセルに中身を書き、結合する残りのセルに印を書く（2行×2列なら、右上に <、左下に ^、右下に <）。

  • 読み方（computeTableMerges()）: 印のセルは、左（<）か上（^）のセルの仲間になる。仲間をたどって印でないセルを親にし、 親ごとの仲間が長方形をきっちり埋めていれば、1つのセル（rowspan・colspan）にする。
  • 長方形にならない（L字など）・左や上にセルが無い・見出しの行と本文の行をまたぐ印は、結合せず、書いた文字のまま出す。 書き手が結合できていないことに、プレビューで気づける。見出しの行をまたげないのは、HTML の thead と tbody をまたいで結合できないため。
  • < や ^ の1文字そのものを表に出したいときは、全角（＜ ＾）で書く。表の編集画面は自動でそうする（13 §3.2）。
却下した案理由
印を全角の矢印（← ↑）にする 本文で見て意味が分かりやすく、提案ではこちらを勧めた。利用者が、Markdown を拡張した表記の流儀に近い半角の < ^ を選んだ（2026-10-14）
空のセル（||）を左と結合する（MultiMarkdown の書き方） 台本の表では、空欄のセル（まだ書いていない・該当なし）がふつうにある。空欄のつもりのセルが結合されてしまう
結合を記法に書かず、表の編集画面だけで扱う 本文で書いた人・手で直した人には結合が見えず、貼った表やコピーした表で結合が消える。記法に残せば、本文がそのまま正になる

  • 記法に指定を足すとき（列の幅など）は、parseTableSource()（読む）と、表の編集画面の tableModelToSource()（書き戻す）の両方を直す。片方だけ直すと、編集画面で確定したときに指定が消える（13 §6）。

13. ルビ — {漢字|かんじ}（2026-10-15 追加）

{黄泉比良坂|よもつひらさか}へ向かう。
{狂気|マッドネス}に呑まれる。          ← 当て字の読みも書ける
{赤:{黒川|くろかわ}}が振り返る。      ← 色の中にルビを入れられる（§13.3）
{漢字|かん|じ}                         ← 読みを | で字数ぶんに区切ると1字ずつ

文中の文字にルビ（ふりがな）を付けるインライン記法。親文字の上に小さく読みを出す（<ruby>）。 難読の地名・人名や、当て字の読みを台本に書くため（2026-10-15 の要望）。 変換は renderRuby()（decorate() の最初の段）、記法の形は INLINE_RUBY_RE にある。

13.1 書き方を選んだ理由

案判断
{漢字|かんじ}（採用） でんでんマークダウンと同じ書き方。インラインの { } の系統（§2）に載り、色の記法 {名前:中身} とは区切りの記号（: と |）で見分けられる。よそで書いた原稿を貼ってもルビが生きる。 表のセルの区切り（|）とぶつかる点は、表の側で手当てした（§13.4）。
｜漢字《かんじ》（小説投稿サイトの書き方） 小説を書く人には馴染みがあるが、[ ] と { } の系統の外に3つ目の記号を作ることになる（§8.1 で @ を却下したのと同じ理由）。《》 は打ちにくい。 縦線を省く 漢字《かんじ》 は「漢字が続く範囲」を推し量る規則になり、書き手が結果を予測できない。
{ルビ:漢字:かんじ}（色と同じ {名前:中身} の形） 区切りに | を使わないので表とはぶつからないが、毎回「ルビ:」と書くぶん長い。 ルビは名前1つで決まる飾りではなく、親文字と読みの2つを持つので、{名前:中身} の形にそもそも収まらない（§7.2）。

どれにするかは利用者に選んでもらった（2026-10-15）。

13.2 細かな決まり

決めたこと理由
縦線は全角の ｜ も受け付ける 日本語入力のまま打てるように（表のセルの区切りと同じ）。
親文字にコロン（: ：）・波括弧・縦線は書けない 色の中身に縦線がある {赤:A|B} を、今までどおり色として読むため。ルビの画面は、親文字にこれらがあると理由を出して確定させない。
色と同じく1行に閉じ、中に波括弧を含めない §3.3 と同じ。閉じ忘れた波括弧の被害を、書いた行の外へ広げない。
親文字か読みが空白だけなら記法として扱わない（isRubyNotation()） { | } のような書き方を消さない。取りこぼしより誤変換を避ける（§3.4 と同じ）。
読みを | で区切った数が親文字の字数と同じなら、1字ずつのルビにする。違えば区切りを外して、親文字全体に1つのルビ でんでんマークダウンと同じ。1字ずつのルビは、行の折り返しが親文字の途中でも起きる。字数はエスケープした文字（&amp;）を1字と数える。
読みが親文字より長いと、親文字の字間が空く ブラウザの既定（ruby-align: space-around）のまま。JIS の組版でも、熟語ルビが長いときは親文字を割り付ける。前後の仮名にルビを掛ける組み方は CSS ではできない。
読みは親文字の半分の大きさで、太字の見出しの中でも細字。line-height: 1 ルビの付いた行だけ行間が広がるのを抑える。本文の行間（1.8）の内側に収まり、ルビのある行と無い行の間隔が揃うことをプレビューと印刷で確かめた（2026-10-15）。

13.3 色との組み合わせ — ルビを先に変換する

decorate() の装飾の中では、ルビを先に <ruby> にしてから色を見る（§4 の2段目）。

  • {赤:{黒川|くろかわ}}（色の中のルビ）は描ける。ルビを変換したあとは波括弧が残らないので、外側が色の記法として読める。読みも同じ色になる。
  • {{赤:黒川}|くろかわ}（親文字だけに色）は描けない。親文字に波括弧を書けないため。色を付けた名前に読みを振るなら前者で足りる。
これは §3.3・§7.2 の「入れ子は解釈しない」の例外である。 色だけなら入れ子に意味は無いが、ルビは色と重ねる意味がある（色を付けた名前に読みを振る）。 それでも走査パターンを深くせず、変換の順序で解いたので、どちらの記法も1行に閉じたまま、閉じ忘れの被害範囲は広がらない。
  • 生の文字列から色を外す stripColorNotation() は、ルビの記法をいったん印に置き換えてから色を外す（withRubyMasked()）。 置き換えないと、{赤:{黒川|くろかわ}} は中身に波括弧があるので色の記法として見つからず、色が外れない（文字色の画面の「色を外す」・目次）。
  • 文字色の画面で、ルビの付いた文字を選んで色を付けると、ルビを残したまま外側を色で囲む。

13.4 表の中のルビ

表のセルは | で区切る（§12.1）が、ルビの記法の中の縦線は区切りにしない。 splitTableRow() が、ルビの記法を印に置き換えてから行をセルに分ける（withRubyMasked()）。 表の編集画面がセルの中の縦線を ¦ に替えるとき（13 §3.2）も、ルビの記法の中は替えない。

  • 記法として読めない書き方（親文字が空など）の中の縦線は、今までどおりセルの区切りになる。
  • 読む側と書き戻す側で同じ判定（INLINE_RUBY_RE と isRubyNotation()）を使うので、編集画面で開いて確定してもルビは崩れない。

13.5 コピーするときは「漢字（かんじ）」にする

判定の結果・セリフ・情報・探索可能箇所のコピー（§5.2・§8.7・§9.4）では、ルビを「漢字（かんじ）」にする。

却下した案理由
親文字だけにする当て字（{狂気|マッドネス}）の読みが失われ、意味が伝わらなくなる。
｜漢字《かんじ》 にするこの書き方でルビを出せるチャットツールなら読みやすいが、出せないツールでは記号のまま残る。どこに貼っても読める形を利用者が選んだ（2026-10-15）。
  • 描いた文字から作るコピー（判定の結果・セリフ・探索可能箇所）は renderedCopyText() が <ruby> を、生の文字列から作るコピー（情報）は plainInlineText() が記法を変換する。1字ずつのルビも「漢字（かんじ）」にまとめる。
  • <ruby> には <rp>（</rp> と <rp>）</rp> を入れてある。プレビューの文字を選んでコピーしたときも括弧付きで写る（1字ずつのルビは「漢（かん）字（じ）」になる）。
  • 情報一覧の本文の冒頭（1行の要約）も plainInlineText() で作る。

13.6 入口 — ルビの画面

下部パネルの「本文」タブの「ふ ルビ」（コマンドパレットでは「ルビ」、既定のキーは Alt+R）で、ルビの画面を開く（openRubyModal()）。 読みを打つ欄が要るので、記法を直接入れずに画面を開く（07 §6）。

何も選んでいないどちらも空で、親文字の欄から。決定でカーソルの位置に入る
ルビの記法の上（カーソルが波括弧の内側にある・記法の一部か全体を選んでいる）「ルビを直す」。親文字と読みを入れて開き、「🧹 ルビを外す」も出す（外すと親文字だけが残り、選んだ状態になる）

場所理由

13.8 将来拡張の入り口

  • 表の編集画面にルビを付けるボタンを足すなら、セルの入力欄の選択範囲を {…|…} で囲む処理を足す（文字色のボタンと同じ考え方。13 §6）。
  • 場面図でルビを見せるなら、SVG の <text> の上に小さな <text> を重ねて描く必要がある。見出しにルビを書くことは少ないと見て見送った。
  • 記法の形を変えるとき（区切りの記号を増やすなど）は、INLINE_RUBY_RE を使う箇所（変換・コピー・色を外す処理・表の区切り・ルビの画面）がすべて同じ形を見ていることを崩さないこと。表の区切りだけ古い形のままだと、表の中のルビが割れる。

14. 太字 — **太字**（2026-10-15 追加）

扉は**内側から**閉ざされている。
{赤:**危険**}                  ← 赤い太字（色の内側でも外側でも書ける）
**{黄泉|よみ}の国**            ← ルビを含めて太字

文中の一部を太字にする。変換は decorate()（ルビのあと、色の前）、記法の形は INLINE_BOLD_RE にある。

14.1 { } に載せなかった理由

§2・§7.2 では、文中の装飾を { } の系統に載せると決めていた。太字はその例外にした。どちらにするかは利用者が選んだ（2026-10-15）。

案判断
**太字**（採用） Markdown と同じ書き方で、多くの人が知っている。打つ文字が少なく、よそで書いた Markdown を貼っても太字が生きる。 波括弧を使わないので、色・ルビと重ねても入れ子の問題が起きない（§14.2）。 §2.1 で「記号は種類が1つしかない装飾にしか向かない」とした理由は、裏を返せば太字には当てはまらない。
{太字:…}（§7.2 どおり） 系統はそろうが、色と重ねるには {赤:{太字:…}} の入れ子か、{赤+太字:…} のような並べ書きの形（§7.2 の注意）を新しく作る必要がある。打つ文字も多い。
記号の系統はこれ以上増やさないこと。 次に飾り（傍点・マーカーなど）を足すときは、今までどおり { } に載せることを先に検討する。 ** を例外にできたのは、Markdown で広く知られていて覚える負担がほぼ無いからである。 知られていない記号を足すと、§2.1 の「対応を覚えられない」問題がそのまま出る。 （同じ理由で、リンクも Markdown の [表示](#名前) を例外として認めた。§15.1）

14.2 細かな決まり

決めたこと理由
1行に閉じる色・ルビと同じ（§3.3）。閉じ忘れた ** の被害を、書いた行の外へ広げない。
中身の両端に空白を置けない（** 空白 ** は太字にしない）。空の **** も太字にしない「2 ** 3」のような、太字のつもりの無い ** を太字にしない。CommonMark と同じ考え方。取りこぼしより誤変換を避ける（§3.4）。
***強調*** は外側の * が1つずつ残る斜体は持たない。日本語の書体には斜体が無く、斜めに歪めた字は読みにくい。
変換はルビのあと、色の前波括弧を使わないので、色の内側（{赤:**危険**}）でも外側（**{赤:危険}**）でも効く。ルビの親文字の中（{**漢字**|かんじ}）にも書ける。
太字の書体は、そのブロックの書体の太字明朝のブロック（情景描写・セリフなど）では明朝の太字になる。Noto Serif JP は 700 を読み込んでいる。
太字と色を互い違いに書く（{赤:危**険}だ**）書き方は扱わないHTML の要素が交差する。ブラウザが組み直すので大きくは崩れないが、どう見えるかは保証しない。
この機能より前に本文へ ** と書いていた所は、太字に変わる。表示が変わるのは「記号のまま出ていた所が太字になる」向きだけである。 サンプルシナリオの本文に ** は無かった（2026-10-15 に確認）。

14.3 コピーと目次

  • コピー（判定の結果・セリフ・情報・探索可能箇所）では、太字の記法を外して文字だけにする（色と同じ扱い。§9.4）。描いた文字から取るコピーには <strong> の文字がそのまま入り、生の文字列から作るコピー（情報）は plainInlineText() が外す。
  • 目次は見出しの文字だけを出すので、太字の記法も外す（色と同じ。§10.2）。

14.4 入口 — 押すたびに付ける・外す

下部パネルの「本文」タブの「𝐁 太字」（コマンドパレットでは「太字」、既定のキーは Ctrl+B）。 画面を開かずに、その場で記法を付け外しする（toggleBold()）。ワープロの太字ボタンと同じく、押すたびに付ける・外すを切り替える。

本文の状態押したとき
太字でない文字を選んでいる** で囲み、中身を選んだままにする（もう一度押せば外れる）。選んだ範囲の両端の空白は記法の外に出す
太字に一部かかるように選んでいるその太字まで範囲を広げ、1つの太字にまとめる
太字の中の文字を選んでいる選んだ所だけ太字を外し、前後は太字のまま残す。全体を選んでいれば記法ごと外す
太字の中にカーソルがあるその太字を外す
何も選んでいない**** を入れてカーソルを中に置く（続けて押すと取り消す）
行をまたいで選んでいる行ごとに囲む（太字は1行に閉じる）。中身のある行がすべて太字なら外す
  • 色と違って画面を開かないのは、選ぶものが無いため（太字は1種類しかない）。
  • キーを Ctrl+B にしたのは、ワープロやブラウザの編集欄で広く使われているから。Alt+B はシナリオ基本情報に割り当て済み。
  • 書き換えは replaceRange() を通すので、Ctrl+Z で戻せる。原文の小窓を開いているあいだはそちらに入る（insertionTarget()）。

14.5 将来拡張の入り口

  • 斜体や打ち消し線を求められたら、Markdown の記号（*…*・~~…~~）に寄せるか { } に載せるかを、§14.1 の注意に照らして決める。* 1つは本文で「※」の代わりや掛け算に使われやすく、誤変換の害が大きい。
  • 表の編集画面のマス目には太字のボタンが無い（色・ルビと同じ。13 §6）。

15.1 書き方を選んだ理由

案判断
リンク [表示](#名前)・目印 {#名前}（採用） リンクは Markdown と同じ形で、表示する文字をリンク先の名前と別に書ける。目印は、見出しの行末に書く形（## 書斎 {#書斎}）が Pandoc の見出しの id と同じ。利用者が選んだ（2026-10-15）。
{リンク:名前}・{目印:名前} { } の系統に収まり言葉で意味が分かるが、表示する文字をリンク先の名前と別にできない。提案では推したが、利用者は Markdown の形を選んだ。
{→名前}・{★名前} 短いが、記号の意味を覚える必要があり、利用者から「その記号は微妙」と言われた。
リンクはブロック記法の括弧 [ ] を使うが、ブロック記法とは取り違えない。 ブロック記法のタグの後ろに ( が続くことは無く、ブロック記法の判定はどれも語の次の :・] まで見ている。 ただ1つ、探索可能箇所の一覧だけは語の先頭（[探索）しか見ておらず、「[探索の手引き](#…)」で始まる段落を一覧と取り違えた。 リンクを足したときに、語の次を :・：・] に限った（SEARCH_LIST_RE）。 §14.1 の「記号の系統を増やさない」の例外であり、Markdown の形で広く知られていることを理由に利用者が選んだ。

15.2 リンク先は目印だけ。名前が重なったら飛ばない

  • 見出しの名前では飛ばない。見出しをリンク先にするときは、見出しの行末に目印を付ける（「🔗 リンク」で見出しを選ぶと自動で付く。§15.5）。 見出しの名前で飛ぶ案は、「## 本棚」が別の場面にもあるとリンク先を取り違えるので採らなかった（利用者も同じ心配を挙げた）。
  • 目印の名前が2か所以上にあるときは、その名前へのリンクをリンクにせず、プレビューで波線の印を付ける（押しても飛ばない。吹き出しに理由）。 目印の側にも「⚠ 目印「…」が2か所」を出す。どちらも印刷・PDFには出さない。間違った所へ黙って飛ぶより、飛ばないほうが害が小さい。
  • 目印が見つからないリンクも同じく波線の印を付ける（目印をあとで置く書き方を許すため）。
  • 目印の名前に { } : ： ( ) は使えない。色の記法 {#88ccff:…}（コロンがある）と、リンクの (#名前) の閉じ括弧と見分けるため（ANCHOR_RE）。
  • 本文の外（表紙・巻末）に書いた目印はリンク先にならない（記法だけ消える）。リンクは表紙・巻末にも書け、本文の目印へ飛ぶ。

15.3 探索可能箇所へ戻るリンク

探索可能箇所の一覧の項目にリンクを書くと、そのリンクのリンク先の目印に「↑ 探索可能箇所へ」を添える（見出しなら右端、段落なら右上）。押すと一覧へ戻る。

  • 画面のプレビューとHTML出力だけに出し、印刷・PDFには出さない（利用者が選んだ。紙では押せないため）。HTML出力に残すのは EXPORT_KEEP_SELECTOR（12 §5.2）。
  • 同じ目印へリンクしている一覧が2つあれば、目印より前でいちばん近い一覧へ戻る（buildLinkContext()）。
  • 一覧の id は段落の位置で振る（search-位置）。描く前に拾うときと、描くとき（parseMarkdown()）で同じ位置になる。
  • リンクが1つだけの項目は、行のどこを押してもそのリンクへ飛ぶ（2026-10-15 の要望。マウスを乗せると行全体が淡い青になる）。 描くときにリンクを数えて .search-item-link を付け、リンクの ::after を項目の枠いっぱいに重ねる。 スクリプトではなくCSSにしたのは、HTML出力したファイルでも同じように押せるようにするため。 行全体が押せることは、マウスを乗せたときの行の色で示すので、リンクの青と下線は付けず、ほかの項目と同じ文字にする（文字色の記法で囲んでいればその色。紙面でも普通の項目に見える）。 リンクが2つ以上ある項目は、行のどこを押したらどれへ飛ぶのか分からないので、リンクの文字の上だけにし、リンクの色も残す。 その代わり、リンクのある項目では行の文字を選ぶこと・ダブルクリックで原文へ戻ることができない（押すと飛ぶため。一覧の見出しの行や枠の余白をダブルクリックすれば戻れる）。
  • 項目を自動でリンクにはしない。項目と同じ名前の小見出しへ自動でリンクする案も出したが、同じ名前のリンク先が複数あると取り違える心配から、 利用者は「書いたときだけ」を選び、その代わり一覧を作るときの手助けを求めた（§15.4）。

15.4 探索可能箇所を作る・直す画面

下部パネル「構成」タブの「🔍 探索一覧」（Alt+3）で、エリア名と、場所ごとのリンク先を決める画面を開く（openSearchModal()）。 プレビューの探索可能箇所の一覧をダブルクリックすると、同じ画面がその一覧を「直す」形で開く（openSearchEditorFromPreview()。判定・表と同じ。「原文へ」で本文へも移れる）。 記法は [場所](#名前) のままで、リンク先を画面で選ぶ（2026-10-15。項目を自動でリンクにする案に対し、利用者が「記法は今のままで、画面で決めさせればよい」とした）。

リンク先の欄はボタンで、押すと「🔗 リンク」と同じリンク先を選ぶ画面（ピッカー）がこの画面の上に開く（openLinkModal(行)）。選んだものはその行に入れるだけで、本文は決定のときに書き換える。

選ぶもの入るもの

  • 画面の説明は短くする（利用者の指定。「そこまで説明しなくても分かる」）。行の欄に何が入るかはボタンの文字（「＋ 新しい小見出し」「リンクなし」「📍 名前」）で示し、 それだけで分からないとき（見出しに目印を付ける・新しい名前の小見出しを入れる・目印がまだ無い）だけ、欄の下に短く添える。 最初は「リンク先を選んでいない場所には小見出しを入れる」のチェック欄で空の行の意味を切り替えていたが、説明が長くなるので、行ごとに選ぶ形にした。
  • 新しい小見出しは、作るときは一覧のすぐ後ろ、直すときは一覧の段落（右の段 >> を含む）の後ろに入れ、下に描写を書く空いた行を残す。

  • リンクのある項目は1回押すと飛ぶので、直す画面は一覧の見出しの行や枠の余白のダブルクリックで開く。

15.5 入口 — 目印とリンク

入口動き
「📍 目印」（「構成」タブ・コマンドパレット。既定のキーなし） 名前を打つ画面を開く（openAnchorModal()）。カーソルが見出しの行にあれば行末に付け、名前に見出しの文字を入れて開く。それ以外はカーソルの位置に入れる（文字を選んでいれば、その文字を名前の候補にする）。 カーソルが目印の上・目印のある見出しの行にあれば「名前を変える」になり、本文のリンク (#旧) も一緒に書き換える（取り消しは1回）。重なる名前は、理由を出して入れない。 原文の小窓（11 §4）で名前を変えたとき、小窓の外の本文にも (#旧) へのリンクがあれば、小窓を確定して本文ごと書き換える（小窓の中だけ変えると、外のリンクが切れるため）。外にリンクが無ければ小窓の中だけを書き換える。
「🔗 リンク」（「構成」タブ・コマンドパレット・Alt+K） リンク先を選ぶ画面を開く（openLinkModal()。見た目と操作はコマンドパレットと同じ）。本文の目印と、目印の無い見出しが並ぶ。 見出しを選ぶと、その見出しの行末に目印を付けてからリンクを入れる（1回の取り消しで両方戻る）。一覧に無い名前を打てば、まだ置いていない目印へのリンクとして入れられる。 本文で文字を選んでいれば、その文字がリンクの表示になる。 カーソルがリンクの記法の内側にあれば「リンク先を変える」になり、表示の文字はそのままでリンク先だけを差し替える（いまのリンク先には「いまのリンク先」と添える）。 リンクのすぐ後ろ（記法の外）にカーソルがあるときは、新しいリンクを入れる（続けてリンクを並べられるように）。
  • ブロック（判定・セリフ・情報など）をリンク先にするときは、その前に空行で区切って目印だけの段落を置く。目印だけの段落は紙面に何も出さず（高さ0）、飛ぶとその次のブロックが光る。ブロックの見出しの行に目印を書くと、ブロックとして読まれなくなるため。
  • 目印だけの段落は、場面図・目次と同じく右の段（>>）の寄せ先を切らない。

15.6 プレビューでの動き・ほかの記法との関係

  • 押すと、目次と同じくプレビューの中でなめらかにスクロールし（アドレスの # は書き換えない。§10.3）、飛んだ先を一瞬光らせる（flashJumpTarget()）。リンク先は画面の上端から少し下（16px）に止める。
  • PDFでは、リンクがそのまま押せるリンクとして残る（目次と同じ）。紙では青い点線の下線の文字になる。
  • decorate() では、目印とリンクを最初に変換する（§4）。リンクの表示の文字の中で、ルビ・太字・色が使える（[{黄泉|よみ}](#…)）。色や太字でリンクを囲むこともできる。
  • コピー（情報・判定の結果・セリフ・探索可能箇所）では、目印を消し、リンクは表示の文字だけにする（stripLinkNotation()）。目次も同じ。描いた文字からコピーするもの（renderedCopyText()）は、目印に添える「↑ 探索可能箇所へ」や重なりの警告（.no-print）を外してから文字を取る。
  • 見出しに付けた目印は、場面ツリーのカードの名前に含めない（付け外ししてもカードとのつながりが切れない。06）。

15.7 将来拡張の入り口

  • どこから飛んできても戻れるようにする（ブラウザの「戻る」のような、飛ぶ前の位置へ戻るボタン）なら、initTocLinks() で飛ぶ前のスクロール位置を覚えておき、プレビューの隅に戻るボタンを出す。今は探索可能箇所からだけ戻れる（静的な戻るリンク）。
  • 情報（[情報:題名]）やNPCカードをリンク先にするなら、目印を置かずに飛べる形（その id を描くときに付ける）を、§15.2 の「名前が重なったら飛ばない」に照らして検討する。
